# 用户计划修改建议

以下七项均为拟议修改，未应用到 [用户计划](user-plan.md)。用户计划与 [原稿快照](research/user-plan.original.md) 保持原字节一致。建议只做局部增补，保留原有结构、论述、措辞和模型分级。

## 1 补足低成本的范围

位置：「记忆系统 → 核心目的」第 3 项。

原文：

> 低成本。包括建库时的低成本，以及使用时的低成本。

拟改为：

> 低成本。包括初次建库、后续维护和日常使用的低成本，并考虑这些环节合起来的总成本。

理由：旧项目的维护负担可能超过查询负担，低查询成本不足以说明整个工具便宜。

## 2 补充更正与过期

位置：「记忆系统具体内容」末尾新增一项。

拟新增：

> 记忆应能随项目变化而更新。来源变化、结论被更正或决定被替代后，检索结果应反映当前有效的信息，并能回查原来的依据。

理由：旧项目出现过旧状态与新状态混淆的问题。这里只提出应有的行为，版本与保存方式放执行计划。

## 3 区分已知必读与探索发现

位置：「记忆系统具体内容」第 1 项之后补充一句。

拟新增：

> 已经明确必须阅读的信息应能可靠提供；文字、向量和图检索也要帮助发现尚未意识到的相关信息。

理由：旧项目有必要资料被排序或预算裁掉的案例。这项提案不要求增加通用规则平台或额外审核流程。

## 4 完善资源协调系统的目标

位置：「资源协调系统」现有 GPU 优先及其两条理由之后补充一段，原文保留。

拟新增：

> 协调多个项目纳入系统的重任务，根据任务需求和可用的 GPU、显存、内存、CPU 等资源安排执行。任务应能等待、取消，并在结束或失败后释放资源，减少项目之间相互挤占和等待资源时的无效工作。

理由：原稿已说明为什么优先 GPU，需要再说明工具要解决什么问题、具备哪些基本能力。HTCondor 接入方式和本机认证问题留在执行计划。

## 5 完善分层协作的交付原则

位置：「ai agent 的组织体系」两条性能目标之后补充一段。

拟新增：

> 下级 agent 向上级返回结论、直接相关的依据或链接，以及尚未解决的问题。组织规模随任务需要调整；简单任务可以不设协调层，避免协作本身成为主要负担。

理由：补足分层协作应如何控制上下文与组织成本。具体团队人数、任务包格式和宿主操作不写入用户计划。

## 6 增加共同的效果判断原则

位置：「适用于所有项目的要求」新增一项。

拟新增：

> 以实际工作效果判断工具是否有用，包括重要信息遗漏是否减少、工作质量是否提高、主 agent 的上下文负担是否降低，以及建库、维护和使用的总成本。扫描量、节点数和安装成功不能代替这些效果。

理由：旧项目有许多工程能力与局部检查通过，但未证明完整系统的质量或成本净收益。具体题目、指标计算和验收方式仍放执行计划。

## 7 补入轻量分发要求

位置：「适用于所有项目的要求」新增一项。

拟新增：

> 工具应便于向新项目部署和复用。上传到 basePack 仓库的文件总量应小；通用依赖和模型可以共享，项目资料、记忆数据库和大型运行产物另行保存。

理由：这是用户本轮已明确提出的交付要求，原稿尚未写入。具体目录、大小预算和发布步骤留在执行计划。
