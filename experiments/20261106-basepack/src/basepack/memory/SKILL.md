# Project memory

## Start and stop

Follow the project's generated `.basepack/instructions.md#startup` for its Python, explicit config and task-start steps. Initialize only the parameters and UTF-8 settings needed by each new shell; retain the same task's brief across later reads, edits, feedback and cleanup. Refresh the brief when the task goal or context materially changes. Invoke commands with `-X utf8 -m basepack --config <absolute-config> memory ...`.

The client reads `memory.username` and the UTF-8 `memory.password_file` (default: the resolved memory directory's `password.txt`; BOM accepted). Use `config show` for its resolved path; restore the correct credential after a missing-file, permission or authentication error. `guide` and `rank` need no config or credentials. Ownership actions need project config but no database, credentials or preceding brief. Knowledge actions require the project's authenticated local SurrealDB server.

Before first `memory init`, choose this project's physical directory, endpoint and unique project_id. Another project may use the same exe but needs its own directory/port/UUID; for example A uses 18080 and B uses 18081. Ordinary `basepack init` creates configuration and entry instructions, without starting or creating a database. After a hidden launcher call has ended, verify `/ready` in a separate call, then use the target config for `init`/`brief` to enforce project identity. Keep the actual launcher, cwd, logs and Python locatable in the project's ignored memory directory. First deployment prepares one strong random password file for a new database; the launcher reads that same file and username and binds only to loopback. Reuse existing credentials. Editing the file does not rotate the database's stored account.

Run Python with `-X utf8` and write JSON with UTF-8. Save `.ps1` scripts as UTF-8 with BOM for Windows PowerShell 5.1 to decode Chinese source/path text; program-written JSON and originals use ordinary UTF-8. Each dependent native command must succeed before the next: use `subprocess.run(..., check=True)` or check PowerShell `$LASTEXITCODE` immediately and throw on nonzero. An apply failure ends that chain before embed/search/read; preserve its original error.

Brief directly reads published mandatory information, overview entries and known gaps. It performs no embedding or task search and does not scan originals. Its bounded structural sample receives exact access hints, conservatively sorts within groups by interval bounds, and interleaves groups; selected clues preserve model/cursors/intervals and explicit omissions. UTC-day rotation changes only display sampling, without persistent state or changes to J/C, hits or age. Low weight never hard-filters knowledge. Reading the existing summaries and projection still has a cost, and this sample does not establish complete semantic coverage. Keep mandatory content; stale mandatory information is an obligation to recheck rather than a current fact. Use retrieval below for task-specific discovery. Open the evidence when a fact matters.

When the business task intuitively takes at most ten minutes, skip the entire automatic `maintain`, including preflight and ownership. For an obviously longer task, start once alongside business work when the host supports cancellable subagent handles and task start/completion events. Report brief and maintenance-start failures independently; a failed brief must not silently skip an otherwise due start. Reassess when scope materially expands; a short task may then start its first maintenance run without waiting for a timer. Dispatched agents follow their briefs and rendered prompts rather than recursively starting maintenance. An explicit request to maintain memory uses manual maintenance regardless of duration.

Collect new Codex originals independently with `memory collect --output <collection.json>` before maintaining them. Collection has no maintenance owner and reports its own outcome. For a Codex-bound project, choose `maintain --collection <collection.json>` or explicitly `maintain --retained`; retained originals leave current chat freshness unknown. An unbound file-only project needs neither option. See [source selection](#maintain-sources).

Allocate a fresh control under the configured memory directory's `maintenance/` and run `maintain --mode automatic --holder <host-thread-identity> --control <path>` with that source selection. If the host already exposes available subagent capacity, add `--available-subagents <A>` after other occupied slots, including retrieval workers, but before the script's business reserve. The command atomically acquires project ownership before preflight. If `acquired=false`, report the existing owner and continue business. Use the default whole-project workset. With ownership and `needs_semantic=true`, follow the handoff below. The coordinator continues until business completion, exhausted fixed candidates or an actual blockage. One reader or batch is not completion. Hosts lacking this lifecycle report automatic maintenance unavailable and use an explicit maintenance task.

At business completion run `memory stop --control <own-path>`, cancel the coordinator and descendants, then inspect `memory owner` and run `memory release --control <same-path>` after publication has ended. Run this cleanup independently of brief or database availability. Stop arbitrates admission; an admitted commit may still be running. Release refuses active or uncertain publication. Keep the owner and original error when outcome is unresolved, and report this remainder without indefinitely delaying the business answer. Only the holder releases its ownership; control paths are capabilities and must never be reused. For an abandoned owner, independently verify the old host task has ended and publication is resolved, then explicitly use `memory recover-owner --run-id <id> --owner-ended --publication-resolved`. File age is not recovery evidence. Published work and originals remain for later tasks. An explicitly requested maintenance task reports what the authorized scope actually resolved and what remains blocked; another owner or a few priority batches do not satisfy it.

## Retrieve in one delegation

When a task names a few known files, read them together directly. Before judging project status, remaining work, pending decisions or historical requirements, use one complete retrieval delegation to establish prior decisions before forming options. Read named chats directly and follow related publication work. Use retrieval also to discover locations, prerequisites and cross-material evidence. Parent summaries supply missing context rather than repeat selected chunks.

Run the unified entry with the project's Python/config prefix:

```text
memory retrieve --question 'How have the requirements changed?'
memory retrieve --question 'Which documented constraints apply?' --scope 'devDoc/'
```

The default scope is `''` (the whole project) and the default text-character budget is 6000 (`--budget` overrides it). Scope is strictly a project-relative path prefix, supporting Chinese and spaces; put business restrictions in `question`. A worker may broaden a path filter within the same question, stating which filter changed. `retrieve` creates `tmp/basepack-retrieval/<uuid>/request.json` with a stable `delivery_id`, and returns `request`, `work`, `delivery_receipt` and dispatch details. Resume that request with `retrieve --request <path>`; omit `--question` then. A call without a question or request returns the required input and starts no work.

The CLI prepares dispatch; it cannot spawn the host's agents. The host must actually create the returned `task_name` with the returned `model` and `reasoning_effort` (configured retrieval tier, default tier1), clean history, and receive its final result. Pass only this bootstrap and the returned command:

```text
Run the following command and follow the `prompt` field in its JSON output:
<render_command>
```

Use `--available-subagents <A>` when the host exposes shared capacity and distinct `--slot` indices for independent concurrent questions. Reuse an owned handle for further rounds of the same question. An explicit `--tier <tier>` changes the configured mapping. Preserve name, capacity and mapping errors. `prepared`/`started=false` is not a dispatched worker. When `executor='main'` or the host cannot spawn, the main agent executes the same rendered flow and reports the actual executor. Retrieval uses no maintenance owner/control and shares host capacity with maintenance.

One executor owns all search rounds, current-state evidence, reading, integration, scoring and ranking. Run `memory freshness` and inspect its new, possibly changed, covered and unknown classes, receipt and endpoints; for relevant candidates and named chats run `memory freshness --thread <id>` to read and compare actual paginated text. Use the host chat reader for named or linked chats outside this project, including publication follow-ups. Timestamps and endpoints are clues, not proof of body equality; unknown candidates, non-text parts and semantic acceptance remain explicit. This probe does not acquire an owner, capture sources, embed or publish knowledge. Return the per-chat cutoff, known uncaptured/changed material, actual supplementary reads and unknowns with the answer:

1. Run `retrieval-start --request <request.json>` once before behavioral selection. It saves and reuses the independent base-search anchors, equal logical-ID shares, base quality, per-version observation cutoff, query/episode, budget and policy, then returns behavioral candidates under the observed model. Keep its anchor package unchanged across internal rounds. Supplement with `search --text <terms>` and inspect `matches` and `vector_coverage`; add every actually observed candidate version to a UTF-8 `candidates.json` array. Scope has the same path-prefix meaning in search. Search defaults to the project's `memory.search_mode`; `--mode vector|hybrid` overrides it. For identifiers, filenames or intact phrases use `--mode hybrid --literal`; direct substring matches carry `lexical_rank` before semantic supplements. Keep configuration, model and compatible-index errors visible.
2. Preserve every candidate's observed `id` and `knowledge_revision`. Use `knowledge <id> --knowledge-revision <version>` for that accepted representation, `history <id>` for available versions, and `neighbors <id> --knowledge-revision <version>` for relationships; `--include-stale` explicitly includes stale relationships. Check applicability using accepted evolution relations, task conditions and necessary original evidence, distinguishing user requirements, working assumptions, implementation facts and experiment observations. Follow each saved `basis` through `read <basis.member> --knowledge-revision <observed-version> --source-version <basis.source_version>` plus its saved line range or image `--locator`; open `original.image_path` for images. A knowledge version identifies the representation; `source_version`/`revision` and locators identify its original evidence. Only provably retained versions are available; history does not promise complete reconstruction at every past time.
3. Read before scoring. Use access-weight intervals, behavioral support and their model/cutoff as auxiliary history-of-use clues; relevance, applicability and evidence value determine one 0–100 comprehensive score. Low weight leaves knowledge available through base search, the graph and original evidence; it does not override accepted replacement/retraction. If needed, `access-hints --input <items.json>` takes `[{"id":"<observed-id>","knowledge_revision":"<observed-version>"}]`. Search, brief, read and access hints are read-only; compiling a projection is an explicit operation.
4. Actually save a UTF-8 `scored.json` array using the host's file tool or local Python. Each item retains observed `id`, `knowledge_revision`, native `kind`, `title`, `text`, any returned `private`, numeric `score` and a short `reason`, plus the observed `private` marker when present. Members use `record_type:'member'` (or omit it), `path`, `revision`, `source_version`, `start_line` and `end_line`; images use null line fields and the actual `locator`. Nodes use `record_type:'node'`; semantic relationships use `record_type:'semantic'`. Those graph representations may be pathless: retain their actual `basis`/`endpoint_versions` without inventing source paths or line ranges. Copy original evidence text and locators from verified `original` and identify summaries as summaries.
5. Run `rank --input <scored.json> --budget <text-characters> --output <ranked.json>`. Rank uses the comprehensive score directly for sorting, deduplication and budget selection; it adds no second access weighting and records no delivery. Run `retrieval-receipt --request <request.json> --ranked <ranked.json> --candidates <candidates.json> --output <delivery.json>` to preserve the fixed anchors and full candidate manifest. Candidates is an array of observed `{id, knowledge_revision}` records, including base, behavioral, supplementary and selected versions. Keep returned `access_model`, `access_compiled_j`, `access_fact_j` and `access_interval`; retain multiple observations when snapshots differ. The receipt saves them in `context.access_observations`, while `context.model` identifies behavioral candidate discovery. A concurrent model switch may make those snapshots differ. Return usable selected content, the same observed versions, source locators, receipt path and unresolved gaps. Keep reading pointers for budget omissions rather than truncating conditions.

The host confirms which final content it actually received, preserves the generated receipt's context and records only those exact item versions with `memory delivery --input <delivery.json>`. The required context contains anchors with `alpha` and `base_quality`, per-version `knowledge_cutoff`, query, episode, candidates, budget, policy and actual model. A final partial result may reduce the items to what was received while retaining the observation context. Each first accepted delivery, including an empty one, advances fact cursor J; only nonempty delivery advances opportunity clock C and rewards its exact versions. An identical retry advances neither; the same ID with changed content fails. There is no propagation to parents, evidence, neighbors or newer versions. Search/read/rank and internal errors are not delivery.

Report completed stages from evidence. If saving or ranking fails, preserve the original error and already read evidence and name the unfinished stage; a prepared request, unsaved array or rank file is not a complete retrieval or observed host delivery. A final partial delivery with exact observed identities can still be recorded after host receipt. Report problems through [use feedback](#use-feedback).

Record the selected tier and actual model when available; do not invent usage or price. Keep reading, ranking and batch intermediates under the project root's `tmp/<task-or-run>/`, uniquely named for concurrent work. Retain selected long-term evidence under root `artifacts/runs/<run>/`. Configuration, credentials, database, managed originals/assets, active controls, receipts and capture identity records stay in their configured persistent locations. Cleanup must preserve current and historical source references and unresolved publication state.

Members use program-generated UUIDs; reuse their returned IDs unchanged. Other record tables may use string or integer keys; reuse their full returned IDs, especially when a key contains a colon. A missing read target reports the requested ID and fails.

## Private sources and publication

The program computes `private: true|false` for new sources, source snapshots, members, nodes and semantic relationships. Source flags use the normalized project-relative root `private/` path. Members include their own source version and pinned basis; nodes use pinned basis; relationships include basis and pinned endpoint versions. Any private dependency makes the whole record private, including mixed public/private knowledge. Use the referenced versions rather than their current flags. Stale, retired and retained historical records preserve their flags. An optional private-path reference in public text alone does not establish use of private content. Authors declare actual evidence; the program derives this metadata rather than accepting an author-selected privacy classification.

Preserve returned flags through search, brief, read, scoring, rank and handoff with their observed knowledge versions. `read.original.private` describes the selected source snapshot and can differ from a member with private cross-source evidence. An absent legacy flag is unknown, not verified public. Treat `private` as a distribution boundary covering privacy, confidentiality, copyright and licensing restrictions under the project's rules. Publicly accessible papers may be private; the flag neither determines a license nor grants redistribution rights. Public outputs may include only material and conclusions the project's publication rules permit. Keep restricted originals and manually maintained derivatives inside the project's private boundary. Managed memory snapshots/assets and reading/batch/ranking packages remain in their existing ignored persistent or temporary locations and are private local runtime material.

Flags provide neither access control nor automatic redaction. Native exports and complete backups retain public and private content. A future public sharing copy must filter actual snapshots, assets, historical records, `change.previous`, and chat/feedback/delivery context as well as current knowledge; no public-export helper is provided. Scoped legacy metadata upgrades use confirmed source mappings and pinned evidence, preserving identities, knowledge/input versions and unchanged vectors; keep unconfirmed coverage explicit.

## Maintain sources

When requesting new Codex collection, obtain the current host project's ID and the complete `list_projects` result. Save a UTF-8 JSON object in the task's temporary work directory with `project_id`, `other_project_roots` (other registered local project roots) and `registry_complete: true`, then run `memory collect --codex-registry <path> --output <collection.json>`. Refresh the registry for each collection; current configured `[memory.codex]` is an alternative. If unavailable, keep the binding gap explicit. The CLI lists active/archived threads, checks explicit IDs or root/worktree membership against other roots, and captures available bodies. A readable local image is an independent source. Collection acquires no maintenance owner. It writes success or failure evidence and preserves the original failure; discovery/capture is separate from semantic acceptance and vector coverage.

For a Codex-bound project, maintain explicitly consumes `--collection <collection.json>` or `--retained` in either mode. Loading a successful collection receipt verifies project ownership and the recorded original-file hashes; changed originals require another collection or an explicit retained choice. The receipt records per-chat observations, not an immutable global snapshot. `--retained` selects already retained owned originals without claiming current freshness and can be chosen after collection failure within the authorized scope. Unbound file-only projects need neither selector. Report collection and semantic results separately. A known maintenance-start failure cleans up only ownership acquired by that process before semantic dispatch and with no active or uncertain publication; unresolved ownership or cleanup errors remain visible for recovery.

For managed chat images, the maintenance receipt's optional `codex` object supplies `project_id` (the host-assigned project), `receipt` (this run's full capture receipt, when available), `capture_dir` (retained framed chat sources) and `attachment_dir` (managed images). Look up `managed_attachment` in `capture.threads[].locations[]` of the capture receipt; that path is relative to the memory directory, the parent of `capture_dir`. For a retained attachment absent from this run's receipt, walk `capture_dir/*.txt` as UTF-8 records using each header's `byte_length` to locate the next header. In either input, use a record only when its `project_id` matches the handed-off `codex.project_id` and its resolved `managed_attachment` matches the assigned image. An unavailable project ID leaves an origin gap; foreign or unknown records cannot establish ownership. Copy each verified matching record's project/chat-part identity and origin fields into the image member's `locator`, retaining multiple owned origins when they share one image. Keep unavailable origins unresolved rather than reconstructing identity from filenames. Reader hints carry the same pointers and project ID; the identity records remain in their capture receipts and framed originals.

The default workset includes Git-tracked and nonignored untracked files, explicit `memory.source_scope` includes, all registered sources (including missing ones), pending work and owned Codex captures; a non-Git project uses its declared `source_scope`. Discovery also includes tracked and nonignored files from the root `private/` independent Git repository under the same project UUID, respecting its ignores. An absent private directory completes normally. Exclude `.git/`, generated state, environments and caches throughout. `--scope <files-or-directories>` restricts the actual workset, including registered, missing and captured sources, to those project-relative paths; out-of-scope pending work remains pending. Use the reported discovery boundaries and gaps; an inventory is not proof of semantic coverage. Avoid recursively scanning `.` through caches, databases and unsupported binaries.

1. Allocate the fresh persistent control before asynchronous `maintain --mode automatic --holder <host-thread> --control <path>`, adding the explicit collection/retained selection and available capacity. Explicit maintenance uses `--mode manual` (the command default). Ownership covers mechanical preflight and semantic work. An occupied project returns `acquired=false` with the existing `owner`; each thread can still brief, report feedback and do business. An acquired run completes proven mechanical changes and returns `receipt`, `control`, `discovery`, `needs_semantic`, fixed `layout` and, when needed and capacity permits, `worker`. Preserve actual preflight errors and inspect owner/publication status before recovery. Detailed evidence stays in the receipt. `changes` inventories differences and `sources` gives registered metadata; Git status does not establish freshness.
2. When `needs_semantic` is true and `worker` is present, set `worker.task_name`, `worker.model` and `worker.reasoning_effort` as explicit host parameters before spawning the coordinator with clean history. Send exactly one English bootstrap followed by `worker.render_command`:

   ```text
   Run the following command and follow the `prompt` field in its JSON output:
   <worker.render_command>
   ```

   The subagent executes the command itself. `memory prompt --receipt <receipt> --control <control> --team 0` renders the publisher prompt; `--team <t> --role reader --reader <r> --paths <files...>` renders a reader's prompt. Other coordinator teams require bounded `--paths` too: replace the source placeholder in their returned render commands with the assigned real files before dispatch. Names, parent-child placement, quotas, model and effort come from the script; role and tier stay separate (coordinator defaults to tier2, reader to tier1). Rendering reads configuration, templates and the fixed receipt layout only; it does not access credentials, the database or models, or write state. Configuration changes affect a new run, not this layout. Detailed role work belongs to the rendered templates.
3. Follow the saved `layout`, sized from actual work items and available capacity. Capacity is a ceiling; enable only the returned workers. Automatic maintenance uses team 0; manual maintenance may use additional bounded groups. With zero readers, the coordinator personally prepares, reads originals, generates all knowledge and publishes. Team 0's coordinator is the sole publisher and feedback resolver; other teams return drafts, hashes, coverage and remainders through its subtree. All teams share one owner/control/receipt. Reuse known owned handles across batches within a stage; use [stage continuation](#stage-continuation) for a long run's clean handoff. Names alone never authorize reuse.
4. If the host rejects capacity, stop new dispatch and retain the original error and unstarted slots. With newly known capacity, `pending-dispatch --receipt <path> --available-subagents <A> --started-task-names <names...>` reduces only the unstarted list; retain existing names, permissions and layout. Without capacity, pending work remains pending. Follow [source-group delivery](#source-group-delivery) using the same control. The receipt fixes candidate identities and collection observations; each prepare pins the actual versions read. Prioritize user constraints, current-stage sources and stable result entry points within that fixed set, then historical work. Report preserved originals separately from semantic acceptance, including accepted versions, later unaccepted results with their current original locations, unresolved feedback, coverage and deferred refinement. Changing the candidate set is a separate scope change by the original host after resolving the old run; business closure follows its stop boundary. Historical candidates require no separate deep-maintenance request.

### Source-group delivery

Assign manageable semantic co-reading groups, using multi-path prepare where useful. Each author owns original reading, chunking, interpretation, relations and ordinary repairs, then returns one ordered set of completed references. Assign each shared node, edge and other graph write target one owner; separate paths alone do not make writes independent. Co-read cross-group targets and their evidence with that owner. Preserve mandatory information, actual read coverage, deferred refinement and unread gaps. The sole publisher integrates ready references and combines already-decided steps in one host call when useful. Author judgment and successful program publication complete ordinary creation, maintenance and feedback repair.

The receipt fixes candidate identities and source scope. Its `current_revision` is the discovery observation, and `accepted_source_version` identifies prior acceptance. Within those candidates, prepare and accept the then-current version, reporting its actual accepted revision and coverage; conflicts return to the author for current prepare and normal repair. A later edit after acceptance does not automatically reopen that stage. Record later unaccepted changes, new paths and other out-of-receipt candidates with original locations and a later limited scope. Receipt success does not establish final disk freshness.

Read only the needed workflow sections and receipt slices. Observe owned handles or the maintenance subtree; collect host completion events or use bounded waits while other work proceeds. After an unchanged timeout, continue waiting. Intermediate messages report original errors, dependencies or changes needing early action.

An explicit delivery through an owned handle identifies the completed assignment and fixed `{path, file_sha256, assignment}` references, with represented/read ranges, deferred refinement, gaps and errors. File appearance alone leaves a draft. Confirm each delivered reference once: an explicit message and the host's later automatic final for the same references are one completion, triggering publication and subsequent dispatch only once. Use the references already received for this recognition. A new hash is a new delivery. Keep delivered files fixed; return repairs to their author for current prepare/necessary reading and a new file/hash.

### Stage continuation

For long maintenance, finish a bounded topic/source group, save its fixed drafts and publication results, and establish publication's terminal state under the current identity. The coordinator owns that group's dispatch, dependencies and ordinary repairs; the original host receives the stage result and necessary decisions. A stage ends only its group: original receipt candidates, unread ranges, relations, feedback and discovery gaps remain explicit. Keep partially handled sources in `remaining` and preserve their ranges in the handoff. The active stage's `remaining` set bounds subsequent assignments; consult the original receipt for its gaps and evidence.

The coordinator returns stage results and handoff inputs. After it and its descendants end, the original host confirms their handles and saves a fixed UTF-8 handoff JSON: `completed` and `remaining` each contain `paths`, `relations`, `feedback` arrays that exactly partition the previous scope; `workers` lists every started owned worker as `{task_name, handle, status:"ended"}`, including the old publisher; `completed_drafts` carries `{path, file_sha256, assignment}` references; `publication_results` carries fixed `{path, file_sha256}` E result references; `errors` and `jobs` preserve original errors, unresolved ranges and needed job/authority details. Use empty arrays for absent items, then run:

```text
memory stage --receipt <same-receipt> --control <same-control> --handoff <handoff.json> --workers-ended --available-subagents <current-free-seats> --output <new-stage.json>
```

For another continuation, add `--previous-stage <current-stage.json>`. Pass current free seats when available; the next bounded stage sizes its layout from remaining work and capacity. The command checks fixed references, the scope partition and owner/publication boundary, saves new stage identities and returns `worker`; it does not spawn the host's agents. The host must actually create that worker with its returned `task_name`, model, effort and `fork_turns="none"`, keep its cancel handle under the original parent stop, and send the normal bootstrap/render command. Generated render commands carry `--stage <new-stage.json> --stage-sha256 <returned stage.file_sha256>`; preserve both in manual prompt or pending-dispatch calls. Capacity changes also pass the original `--control` to pending-dispatch.

Keep one dispatcher/publisher active at a time, the same receipt and owner/control, and the original parent's stop authority. Stage handoff leaves the run open and performs no whole-run stop/release or new collection. When reader handles cannot transfer, finish the old group and create new readers using the new layout. A same-context summary or compression is not a clean handoff. If the host cannot create the new identities with clean history and cancellation authority, report that continuation as blocked; retain remaining scope under the original lifecycle. At business completion follow normal stop, cancellation, publication resolution and release.

### Direct batch interface

For an explicit batch, run `prepare --paths <affected-files-and-related-material> --output <reading.json>`, including evidence and both relation endpoints. Read the new/old numbered originals and relevant neighborhood; use `read` or extend prepare to verify additional originals. Reading units are location hints; long-line text units carry exact 0-based `start_col`/exclusive `end_col` locators within their 1-based line range. Choose semantic chunk boundaries, file/section summaries, nodes and edges in the same reading, with conditions and evidence. Preserve original wording inside chunks. When a relation intentionally uses an observed old endpoint, pass `--historical-versions <versions.json>`, a JSON array of `{id, knowledge_revision}`, to prepare and retain that endpoint's private marker.

A zero-line text source needs no text member: registering its prepared source revision is sufficient when it has no active knowledge. When an existing source becomes empty, retire its old text members and resolve dependent knowledge through retirements or corrected evidence in the same batch. Text member ranges remain 1-based and inclusive; an empty source has no valid range.

Acquire project ownership as above and write one semantic proposal per author. Each draft contains `prepare:{path,file_sha256}` referencing the exact saved reading-package bytes. Select sources by path and express semantic content, positions, references, dispositions and retirements; the compiler derives source revisions, expected dependency closure, UUIDs and private propagation. An author must choose the evidence: compilation follows expressed dependencies and creates no semantic claims. Follow source-group delivery above; the publisher chooses the ordered grouping. Write the completed draft references as a UTF-8 JSON array:

```json
[{"path":"draft1.json","file_sha256":"<SHA256 of final file bytes>","assignment":"<specific completed assignment reference>"}]
```

Use `memory publish --completed <completed.json> --output <new-frozen.json> --control <same-path> --result <result.json>`. Paths are relative to the calling process. The helper checks every file hash, preserves separate scopes in list order, invokes freeze/validate, exclusively saves the new frozen file, then calls the original apply. One ready draft may publish immediately; multiple calls are individually atomic. Python uses the same implementation: `from basepack.memory import publish; publish(memory, completed=references, output=path, control=control, result=result_path)`.

To resume an unchanged saved batch, use `memory publish --frozen <saved-frozen.json> --control <same-path> --result <result.json>` or Python `frozen=` without completed/output. Preserve its batch ID, UUID mapping and file. Apply recognizes an already committed identical batch and returns the database receipt, which is authoritative. The local result is a projection: batch ID, frozen path/`frozen_file_sha256`, completed references (null on resume), and the full `apply` result including invalidated IDs. The compact return carries paths and write/invalidation counts. A local result-write failure also resumes the same frozen; it does not justify a new batch. File-byte `file_sha256` and `frozen_file_sha256` differ from apply's canonical database `batch_hash`.

A changed author delivery requires a new freeze. Keep invalidated IDs as facts and query current state when useful. Preserve original errors; an unknown commit retains its marker and owner until explicitly resolved. Report uncovered ranges, dispositions, deferred refinement and remaining candidates.

Direct `prepare`, `read`, `neighbors`, prompt rendering, `freeze --drafts ... --output <new-frozen.json>` and `apply --batch <frozen.json> --control <same-path>` remain available. Known next steps may use ordinary sequential or conditional Python in one host call; return to agent judgment when needed. `freeze_file` and CLI freeze compile hash-pinned proposals; pure Python callers use `basepack.memory.draft.compile_proposals(proposals, config=memory.config)` when they need the compiled object. Apply checks fixed sources, knowledge and parent dependencies, prepares candidate vectors and publishes knowledge with matching vectors atomically. Successful publication completes the ordinary batch; failed or uncertain publication remains unresolved.

Draft fields (freeze resolves scoped member references into the persisted batch):

- For a new member omit `id`. For an update use its UUID returned by prepare; never invent one. `{"member": 0}` refers to the first member in the same draft. To refer to another draft, use `{"draft": 1, "member": 0}`: both indexes are zero-based and `draft` follows the completed-reference list (or direct freeze's `--drafts` order). Each reader retains a separate draft scope; a coordinator co-reads cross-reader evidence before authoring relations. Identical titles or positions across scopes do not identify the same object. Duplicate updates and conflicting expected revisions fail rather than merge.
- References in member `parent`/`evidence` and node/edge `evidence`, edge `in`/`out` accept these scoped objects or existing IDs from prepare. Source dispositions and historical endpoint pins refer only to already published IDs and versions.

Other fields:

- `prepare`: `{path, file_sha256}` for the reading package. Keep that file fixed; changed source/evidence requires new prepare, necessary rereading and a new draft. `expected`, source revisions, private fields and permanent IDs for new records are program output. Apply checks the compiled versions of written, retired and corrected targets, actual evidence, parent references and relation endpoints. On a stale conflict, prepare and read the affected material again.
- `sources`: paths selected from prepare, either a path string or `{path, dispositions?, deferred_refinement?}`. The compiler fills identity, revision, kind and accepted deletion metadata; include a prepared missing path to accept its deletion.
- A source may add `dispositions: [{kind:'no_knowledge'|'duplicate', start_line, end_line, reason, representations:[{id, knowledge_revision}]}]` for actually read ranges. Images use `whole_image:true` instead of line ranges. Duplicate representations require their current versions from prepare. Valid same-version dispositions avoid repeated initial work; partial reading covers only its ranges. Source changes invalidate old dispositions; relevant representation changes reopen duplicate work.
- `deferred_refinement: [{start_line, end_line, reason, gaps:[{member, gap, knowledge_revision}]}]` records read coverage whose finer representation is deferred, separate from unread gaps and dispositions. Images use `whole_image:true`. Each gap names the exact current fresh member version and exact `coverage_gaps` text; changing that member in the same batch requires publishing it before deferring its gap. Deferred text counts as handled only where current fresh file/section summaries cover it; a chunk plus defer cannot stand in for coarse delivery. Existing selected chunks still support summaries. Preserve unique facts and fine knowledge, and explicitly retain mandatory flags when rewriting members. Same-version omitted dispositions/refinement remain; a new source revision does not inherit them.
- `members`: `{kind, path, parent, start_line, end_line, title, text, evidence, mandatory, coverage_gaps}` plus `id` only for an existing member; optional `conditions` and `claim_type` state applicability and claim identity. The program pins `parent_version` to the accepted parent. Text kinds are `file`, `section`, `chunk`; line ranges are 1-based and inclusive. Optional text `locator:{start_col,end_col}` selects exact 0-based character boundaries with exclusive end. A full file summary spans line 1 through the source's final line, including framing/header lines; its evidence chunks may cover the meaningful body. A partial file summary declares actual `coverage_gaps`. Summary evidence names the covered chunks. For chunks, omit text and let the program take exact original bytes/line endings; explicitly supplied text is strictly checked. Images use `kind:'image'`, actual visual description/OCR as text, and `locator` for page/region/origin as available; no invented line range. Mark only explicitly required startup information mandatory.
- `nodes`: optional `{id, kind, text, evidence, conditions, claim_type}` for entities, decisions and conditions.
- `edges`: optional `{id, in, out, kind, text, conditions, evidence}`. Endpoints name `member:<id>` or `node:<id>`; evidence names member IDs read together. Optional `endpoint_versions:{in:{id,knowledge_revision},out:{id,knowledge_revision}}` links retained historical endpoints; when omitted the program pins the actual versions accepted in this batch. Edit an existing edge by its ID; adding one preserves other edges.
- `delete_members`, `delete_nodes`, `delete_edges`: explicit IDs retired by this batch. `corrections`: `{id, target, reason}`; the program captures the previous record.
- `context`: actual available `chat`, `turn`, `root_chat`; leave unavailable fields absent.

### Minimal batch

Use an initialized disposable project, the configured shared embedding service available, and `memory.search_mode` set to `vector` or `hybrid`. This standalone example creates exactly four UTF-8 lines. Choose a fresh work directory and source filename; the file/section/chunk ranges are inclusive, all parents and evidence exist in the same batch, and chunk text comes from the original. The example summaries describe this fixed source; actual material requires the same reading and judgment described above.

```powershell
$ErrorActionPreference = 'Stop'
$OutputEncoding = [Text.UTF8Encoding]::new($false)
[Console]::OutputEncoding = $OutputEncoding
$python = '<instructions absolute-python.exe>'
$config = '<absolute-project-config>'
$projectRoot = '<absolute-project>'
$work = Join-Path $projectRoot 'tmp/example-<unique-name>'
$control = '<absolute-memory.data_dir>/maintenance/example-<fresh-unique-name>.control'
function memory {
    & $python -X utf8 -m basepack --config $config memory @args
    if ($LASTEXITCODE -ne 0) { throw "memory command failed ($LASTEXITCODE)" }
}
New-Item -ItemType Directory -Path $work | Out-Null
memory maintain --mode manual --holder '<this-host-thread>' --control $control --retained
# Proceed only when acquired=true; an occupied project belongs to the returned owner.
$source = Join-Path $projectRoot 'memory-example.md'
New-Item -ItemType File -Path $source | Out-Null
[IO.File]::WriteAllText($source, "# 试用说明`n## 约定`n试用问题 A-17 留在开发记录。`n项目数据库按项目隔离。`n", [Text.UTF8Encoding]::new($false))
$reading = Join-Path $work 'reading.json'
$draft = Join-Path $work 'draft.json'
$batch = Join-Path $work 'batch.json'
memory prepare --paths 'memory-example.md' --output $reading
@'
import hashlib, json, sys
from pathlib import Path
reading = json.loads(Path(sys.argv[1]).read_text(encoding="utf-8"))
source = reading["sources"][0]
print(source["numbered_text"])
path = source["path"]
batch = {
    "prepare": {"path": str(Path(sys.argv[1]).resolve()),
                "file_sha256": hashlib.sha256(Path(sys.argv[1]).read_bytes()).hexdigest()},
    "sources": [path],
    "members": [
        {"kind": "file", "path": path, "parent": None,
         "start_line": 1, "end_line": 4, "title": "试用说明",
         "text": "试用问题 A-17 留在开发记录；项目数据库按项目隔离。", "evidence": [{"member": 2}]},
        {"kind": "section", "path": path, "parent": {"member": 0},
         "start_line": 2, "end_line": 4, "title": "约定",
         "text": "保留试用记录，并使用独立项目数据库。", "evidence": [{"member": 2}]},
        {"kind": "chunk", "path": path, "parent": {"member": 1},
         "start_line": 3, "end_line": 4, "title": "试用与隔离约定", "evidence": []},
    ],
}
Path(sys.argv[2]).write_text(json.dumps(batch, ensure_ascii=False, indent=2), encoding="utf-8")
'@ | & $python -X utf8 - $reading $draft
if ($LASTEXITCODE -ne 0) { throw "Batch creation failed ($LASTEXITCODE)" }
memory freeze --drafts $draft --output $batch
memory apply --batch $batch --control $control
memory search --text 'A-17' --mode hybrid --literal
memory search --text 'memory-example.md' --mode hybrid --literal
$frozen = Get-Content -Raw -Encoding UTF8 $batch | ConvertFrom-Json
memory read $frozen.members[2].id
memory neighbors $frozen.members[1].id
memory stop --control $control
memory release --control $control
```

Apply encodes the candidate members before publishing them with matching vectors. The function above stops on any failed dependency, including model errors. A text member missing start_line/end_line reports its batch position, member ID and field; correct the input and rerun. Failed batches leave no partial database writes.

## Behavior model and access projection

`memory behavior-train` requires the optional `behavior` installation extra. It trains standard KL-NMF only from immutable co-delivery logical-ID baskets, freezes a model artifact and replays raw facts before switching the derived projection. `--rank`, `--epsilon`, `--beta` and `--strength` select the frozen parameters. Rank 8, epsilon .001, beta .2 and strength 8 are engineering starting values, not validated optimums. No model or reliable co-delivery partners means unknown behavioral evidence; base retrieval remains available.

`memory behavior-compile` explicitly catches the projection up to the fact head. Gaussian similarity is computed for each fixed anchor and then averaged by its original share; unknown shares are not renormalized. The incremental state uses sparse H, unknown mass R and per-exact-version scalar baselines. Retraining replays original facts in the new model rather than converting old weights. `memory behavior-candidates --input <anchors.json>` reads a fixed anchor array; regular retrieval obtains it through `retrieval-start`.

Access is driven by real nonempty deliveries, with no calendar clock. A hit resets that exact version's shared access state; a hit on an old version does not reward its revision. Very low weight retains originals, history, graph/index entries and training IDs, and leaves base search eligible. Semantic stale/retired status still governs applicability. First acceptance records a fact-head baseline without inventing usage; migrated records with unknown old acceptance keep an explicit legacy observation origin.

## Use feedback

Retrieval workers and calling agents use the same lightweight report action: `feedback-report --kind knowledge|retrieval --issue <concern>`. For a target, add `--target <returned-id> --observed-revision <observed-knowledge_revision>`; preserve the version seen in search/brief rather than replacing it with a later read. This is the observed knowledge version; put the software version in the issue description. For a miss without an ID, provide `--query <query>` or `--source <expected-source-or-locator>`. Optional `--reporter <host-identity>` identifies the observer. Report the concern and available evidence; a separate audit or complete repair proposal is unnecessary. Continue business using reliable evidence and expose relevant gaps.

`feedback-list` returns unresolved reports (`--all` includes results). Reports persist in the project database and native exports, never become discoverable business sources, and trigger the next owner maintenance even with unchanged originals and no other candidates. Reporting does not require ownership. Only the maintenance owner judges and repairs current knowledge using normal apply/corrections. Resolve with `feedback-resolve <id> --control <same-path> --outcome fixed|invalid|duplicate|obsolete --result <reason>`; for a target include its current `--expected-revision`. Preserve stale-report conflicts and unresolved outcomes. A retrieval/ranking problem is not automatically a knowledge error.

## Manual audit

Only an explicit user intent to audit the memory system starts an audit. Interpret intent rather than matching an exact phrase; discussing audit, asking ordinary maintenance, or reporting a problem does not trigger one. Fix the authorized scope and cutoff, read the requested evidence and record findings through the same feedback interface. Read-only audit/reporting may coexist with maintenance; writing repairs acquires the single project owner. Resolve findings according to the user's request and report unexamined scope. Ordinary creation and repair remain complete after author judgment and successful program submission.

When an authorized maintenance run also serves as a real-use trial, observe the normal author-to-publication flow and actual retrieval. Report real problems under the owning project task, repair within authorization and verify the affected operation. A bounded sample is neither an additional semantic audit nor a formal benchmark; its size does not replace the run's authorized coverage or become a product limit.

Back up with SurrealDB's native export and restore into a separate project directory. Include configuration, public/private original documents/images, the independent private Git and needed files it ignores, managed chat/attachment originals and identity receipts, assets, and `memory.data_dir/behavior/<sha>.json` model artifacts referenced by the database. A database export alone does not contain all these files. Exports preserve available knowledge versions/evolution, private flags, source dispositions/refinement, feedback, immutable delivery facts, access projections and delivery deduplication IDs; an older backup cannot restore later state or unrecorded history. Retain needed controls and receipts while publication or recovery depends on them. Rebuilding vectors uses accepted representations and retained image snapshots; delivery accounting does not rebuild them. Numeric model coordinates and IDs retain the project's distribution boundary. Choose backup location and retention for an explicit recovery need, and keep complete recovery material within its private sharing boundary.

The shared embedding service encodes text as title plus accepted text, and images as original image bytes. Descriptions do not substitute for image vectors. `embedding_identity` and input revisions gate compatibility; equal dimensions do not. A missing compatible index is an explicit error: index accepted members with `embed`. Keep summaries short. HTTP 422 reports 0-based input indices and token counts; candidate errors add the member key, path and range. Preserve the unpublished batch and original error, then return over-limit text to the same reader: split original chunks at semantic boundaries or shorten summaries and prepare again, retaining coverage and exceptions. Resume from the reported path/range without truncating originals, raising the service limit or automatically resubmitting. Other model errors retain their original details. A timeout only ends waiting and does not cancel shared inference.
