# Resources

Read the project's `.basepack/instructions.md` and its indicated config (normally `.basepack/config.toml`, project schema 2). Invoke `runtime.python` with `-m basepack --config <absolute-config>`; the machine config supplies the service endpoint and Condor paths. On first setup or an environment change, use `config show` and the relevant `doctor --facility`; ordinary calls go straight to the action.

- **Embedding:** `embed --text <text>` or `embed --image <absolute-image> --caption <text>`. Use `--inputs <UTF-8-JSON-array>` for batches and `--output <project-file>` to keep vectors out of the conversation. Query and bulk work share one persistent model hosted by the machine's Windows service. Clients only connect; ask the machine administrator to start a missing service. `--timeout` ends client waiting and does not interrupt shared inference or trigger a retry; the service's queue timeout is separate.
- **Heavy work:** write a UTF-8 JobSpec with an absolute `executable`, an `arguments` array, project-relative `cwd`, `cpus`, `memory_mib`, `disk_mib`, and bounded `queue_timeout`/`run_timeout`. For GPU work add `gpu_memory_mib`, including context, caches and workspace. Use `jobs run --spec <file>` for one submit-and-wait call.
- **Long work:** `jobs submit --spec <file>`, then `jobs wait <cluster.proc> --timeout <seconds>`. Observation expiry leaves the job running. Use `jobs status <cluster.proc> --analyze` for queue/hold diagnostics and `jobs cancel <cluster.proc>` to cancel that job.

Keep generated tool data in the project's `.basepack/`; preserve business input and explicit export paths. HTCondor owns ordinary-job capacity and scheduling; `jobs capacity` shows extra `MachineResources` under their original names and units when both total and remaining quantities are published. The client checks standard CPU/RAM totals. GPU specs become official `request_gpus=1` and `gpus_minimum_memory=<peak> MB` requests; the schedd applies site policy for memory reservations and shared slots. On this site, native GPU memory must resolve to a positive number at submission; an omitted attribute reserves the whole pool, while explicit `undefined`, invalid or excessive requests are rejected. Valid requests queue when resources are busy. GPU counts may represent shared slots on one physical device. Cap application threads and framework allocations to the declared estimates and preserve Condor's `CUDA_VISIBLE_DEVICES`. Reservations do not provide GPU memory isolation. Background capacity is reserved even before embedding loads.

Check application exit code and meaningful output, and report job `cleanup_confirmed` separately from timeout. Preserve original errors and log locations. Machine `embedding --machine-config <file> status` uses native health/info endpoints; `stop` sends a Windows service stop request, whose completion the administrator observes through SCM. Python uses `EmbeddingClient(project.machine).embed(inputs, timeout=...)` and `CondorClient(project)`; vectors carry `embedding_identity` for index compatibility.
