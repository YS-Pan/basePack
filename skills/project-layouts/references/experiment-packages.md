# 实验分包布局

适合并行比较多种方法、原型或实验路线，解决源码、依赖、状态和结果相互缠绕的问题。这里的“实验包”首先指独立实验工程单元，不等同于必须发布的 Python 软件包。

## 工程单元与一次运行

一个工程单元承载独立演进的方法、依赖和生命周期。修改随机种子、参数或重复次数，通常在同一工程中产生新 run；方法、依赖或交付边界确实独立时，再建立新的实验单元。

```text
项目/
  AGENTS.md                     共同约定与直接入口
  README.md                     实验索引与共同目标，沿用已有入口
  devDoc/                       当前共识、共同计划与结论
  experiments/
    YYYYMMDD-short-topic/
      .git/                     独立仓库方案；保留已有 Git 边界
      README.md                 假设、状态、入口、依赖、复现和缺口
      AGENTS.md                 仅必要的实验局部约定，按需
      pyproject.toml等          实际技术栈的依赖与运行声明
      src/                      有对应代码时采用，遵循语言生态
      tests/                    必要验证与小夹具
      configs/                  实验配置，按需
      data/                     小输入或数据来源、版本与恢复位置
      runs/<run-id>/            一次执行的配置、版本、日志与输出
      RESULTS.md                结论、比较、失败、限制及证据链接
  test-cases/                   真正共享的固定输入与评测协议，按需
  test-runs/                    独立评测执行的输出，按隔离需要
```

示例中的名字可调整。自有配置、知识、数据库、缓存和结果归所属实验；大数据、模型与环境可保存在项目外，通过配置和版本信息定位。协调层保存共同方向、实验登记和影响决策的结论，原始运行细节继续由所属实验维护。

## 选择隔离与打包程度

| 条件 | 建议 |
| --- | --- |
| 小脚本验证，沿用同一项目环境即可 | 脚本、配置、必要输入与结果入口成组；依赖按现有机制声明，无需完整软件包骨架 |
| 需要独立入口、依赖、复用或分发 | 建立语言生态支持的工程声明、代码和必要测试；Python 可采用 `pyproject.toml` 与 `src/包名/` |
| 已有独立 Git 和未提交实验工作 | 保留仓库与 WIP；父项目登记入口，沿用其子仓库管理方式，迁移不等于合并历史 |
| 多个包在一个仓库共同演进 | 可以沿用单仓库或已有 workspace，固定整体版本与声明的依赖；无需为套模板再拆 Git |
| 依赖冲突或复现边界独立 | 按实际需要隔离环境；兼容环境、固定权重和缓存允许显式共用 |

共享代码只有一个维护源，通过声明依赖或明确版本引用；独立实验应能说明如何恢复其依赖，避免依赖兄弟实验的可变源码、数据库或只在原机器上成立的链接。共享环境不意味着共享项目记忆或业务状态。

## 入口与证据

实验 README 说明问题或假设、当前状态、运行命令、依赖、输入身份、结果入口、限制和下一步。相关配置或报告可直接引用，避免把所有说明复制到 README。

一次 run 应能关联代码版本、实际配置、输入身份、环境以及结果位置，必要时保留种子和硬件条件。已有程序生成这些信息时沿用其输出，不再维护重复清单。数据、方法和输出的生成关系要能解释；目录存在或有依赖锁均不代表实验已经成功复现。

基准题集与答案、裁判材料的可见范围按评测需要隔离。实验内的运行与独立评测的执行可以分开，数据读取范围不能由一个新目录名自动保证。

## 已有实验迁移

先登记待迁的独立实验及其根目录、Git/WIP、依赖、数据位置、运行入口和活动进程依赖。按确定的旧新路径映射分批整理，保留日期名或稳定标识，关联配置和结果一起核对。检查路径、导入、命令、工作目录、忽略规则及外部工具引用；不要用重跑昂贵实验来代替引用检查。

实验目录本地自包含其职责，不要求把共享权重和环境全部复制进来。活动运行仍依赖旧路径时，记录具体受影响部分并在安全窗口迁移；其它部分可先整理。结束后先汇总结果和恢复条件，再按项目需要归档。可重新生成不等于允许删除已有证据，清理按实际保留需求另行处理。

## 依据与适用范围

本方案继承旧项目“独立尝试有自己的工程边界、状态和证据，再集中到 experiments”的思路；不继承其任务状态、业务授权或已验收结论。多种工具链可以实现此布局：

- [Research compendium 原论文](https://faculty.washington.edu/bmarwick/PDFs/Marwick-Boettiger-Mullen-2018-TAS-research-compendia.pdf) 支持数据、方法、输出分离及环境说明，不要求每个单元都成为正式软件包。
- [PyPA src 与 flat 布局](https://packaging.python.org/en/latest/discussions/src-layout-vs-flat-layout/) 说明打包和导入的取舍；[脚本元数据](https://packaging.python.org/en/latest/specifications/inline-script-metadata/) 提供小脚本依赖声明的另一种方式。
- [uv workspaces](https://docs.astral.sh/uv/concepts/projects/workspaces/) 展示同仓库多包的共享锁与依赖边界，不适合所有环境隔离需求。
- [Cookiecutter Data Science](https://cookiecutter-data-science.drivendata.org/#directory-structure) 与 [Snakemake](https://snakemake.readthedocs.io/en/stable/snakefiles/deployment.html) 展示数据阶段、配置、工作流和结果的职责分离；其完整目录和工具链按需要选择。
