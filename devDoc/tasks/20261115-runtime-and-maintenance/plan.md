# cuDNN、协调者流程与持续整改计划

2026-11-15，讨论稿。用户要求先讨论并制定计划，不实施。本轮只保存计划与入口；以下命令名是拟议接口，当前产品不提供。源码、prompt、AGENTS、机器配置、共享服务和记忆发布流程均未改。

## 目标、已定方向与待选项

| 项目 | 本轮确定的方向 | 待确定／待验证 |
| --- | --- | --- |
| embedding | CUDA 采用 cuDNN attention，模型32k上限不截断；9 GiB是柔性运行目标，允许偶发超标／失败 | 代表性负载、32k功能与批次／部署参数，不设逐请求9 GiB硬门槛 |
| 协调者 | 减少确定性步骤的模型往返、重复正文和短轮询，保留必要语义工作 | 下列A–D组件及近期案例新增的E／F落地选择仍待用户选择 |
| 持续整改 | 在正常任务接触相关材料时处理分散的小问题；条目有失效时间，发现到期即归档 | 推荐下述 ongoing 目录、默认7天与触发合同，尚未启用 |

不以协调者／reader 的固定 token 比例作为目标。已有调查中协调者兼任作者、整合、发布和恢复，缓存输入反复累计；要减少的是可定位的无效往返和上下文负担。模型档位暂不作为本轮改变对象。

用户补充的工程取舍：工具面向能判断并调整操作的 AI agent，允许偶发资源超标与请求失败。程序应保留原始错误和可接续状态，不为兜住每个极端情况增加预检、调度层或隐式重试。这不放宽模型上下文限制、知识版本与原子发布合同。

## 一、embedding：cuDNN 与模型上限

### 拟议行为

- 保留现有 Windows、Sentence Transformers、PyTorch 和同一模型 revision／FP16／前处理／pooling。CUDA 显式选择 `CUDNN_ATTENTION`；CPU 保留原有可用路径。CUDA 后端不支持时保留原始错误，不静默转回高显存 math。
- 实际上下文上限为 **32768 token**，包含模板、指令和图片 token。在固定 Qwen embedding 适配层单处声明官方支持上限；不从底座 `max_position_embeddings=262144` 推断。退役机器配置中独立的 `max_length=2048` 及其现行说明，按实际 attention_mask 在 forward 前执行模型上限检查。
- 继续关闭截断，保留原请求顺序的超限索引与实际 token 数。tokenizer 的配置值／warning 不代替服务拒绝；不通过截断掩盖来源分块问题。
- **9 GiB是柔性目标**：初始期望例如约99%的正常使用情形落在该目标以内，少数长输入／大批次可以超过；99%是经验目标，不是已测结论、逐请求保证或新增上线门槛。分别记录allocated／reserved及可得的进程占用口径，不能把分配器指标冒充进程总量；先用有限标定和真实使用反馈调整，不建设专门的百分位监控系统。
- 当前代码用 `gpu_memory_mib` 调用 `torch.cuda.set_per_process_memory_fraction`，实际会在配额处主动OOM。实施时取消把9 GiB用作该分配器硬上限的行为，将其明确为容量规划／运行观察目标，同步配置和管理员说明。普通Condor作业仍沿原配额机制；embedding可短时使用空闲物理显存，资源重叠时接受显式OOM，不另建逐请求资源协商。
- 不再为最坏的32k×4负载把全局批次强制降到1；建议先保留 **batch4**，沿代表性负载调优。已有10k×4 reserved约6.74 GiB。调用agent遇到偶发OOM可减少请求项、分批、调整任务或等资源空闲后显式再调用；工具不静默截断、无限重试或自动改写输入。若超标／失败变成常态，再调整默认批次或日常预留。
- 一次突发请求若让空闲缓存长期高于目标，可在请求结束后释放未使用缓存，使突发占用能回落；不逐请求无条件清缓存，不把释放空闲缓存说成能释放仍使用的张量。先核实际缓存行为，复用PyTorch能力即可。
- 文本字节、图片文件／像素等请求限制独立于 token 上限。实施时核对现有 64 KiB 文本限制是否妨碍目标输入，明确保留或调整的请求边界；不宣称改了 token 上限就取消全部输入限制。
- `/info` 可直接呈现实际设备、attention 路径和支持上下文，避免用户从 `sdpa` 字样猜后端。运行设置不另造向量身份；旧输入未变时，沿当前 identity／input_revision 合同复用旧向量，必要数值检查不以 identity 相同替代。

### 证据与实施后的完成条件

已测 cuDNN 的 10k 单条／batch4 张量峰约 4.49／6.02 GiB，后者 reserved 约 6.74 GiB。22 组文本／2k／图片／图文配对最低余弦约 0.9999889；6 查询×16 候选的新查询接旧索引及全新向量组合，完整排序均一致。这些是局部工程证据，生产仍是 math／2048／batch4，32k 尚未实测。

实施时按顺序：

1. 在唯一源码适配层接 cuDNN、模型上限及相关配置／文档，保持 CPU 行为；只为改变的行为补必要回归。
2. 按作业实际资源申报做有限隔离检查：代表性batch4、实际32768-token单项、超一token的forward前拒绝、混长padding、图片／图文与既有数值兼容。跟踪实际kernel，逐case重置显存峰值，区分allocated／reserved／进程总量。极限样例超过9 GiB本身不判失败，也不为证明99%另造大规模测试。
3. 完成选定功能与代表性负载检查后，构建普通wheel、排空共享请求并按既有管理员流程部署。核普通安装、共享健康、实际后端、上限诊断、旧索引查询及资源归还；少数负载的资源失败如实报告，不能宣称所有合法32k输入在本机都保证成功。

若正常负载反复失败，保留真实错误并重估批次／目标；偶发失败交调用agent处理，不因此强制收紧所有调用。模型允许32k与当时物理显存能否满足是两项事实，10k成功不代替32k检查。仅换kernel／拒绝阈值不安排全量重算；改变分块或实际输入的条目单独重编码。

## 二、协调者：A–D组件与E／F落地选择

当前成功链包含：作者完成 → 必要共读／跨稿整合 → freeze → 文件 hash → apply → 手记台账 → 下批 prepare／render。`freeze` 已有结构校验；`apply` 已有 batch 身份、规范化 hash、幂等回执、版本检查与原子发布。组合层复用这些能力，不能再造一套发布合同。

| 选项 | 具体改变 | 主要减少的负担 | 相对成本 |
| --- | --- | --- | --- |
| A：一次发布 | 完成稿清单交给一个命令，连续验文件 hash、freeze、保存固定 batch、apply、输出紧凑回执 | 每批 freeze／hash／apply／台账之间原本分开的约四次调用，成功路径合为一次模型往返 | 小 |
| B：一轮派工包 | 协调者一次给出多个明确 assignment，脚本准备各 reading 包并生成派工清单；正文直接交 reader，协调者拿短索引 | 逐份 prepare／render、重复读取完整 receipt、reading 包后再读相同原文件 | 中 |
| C：作者负责检查与修稿 | 作者交付路径／hash／覆盖；可机械判断的格式检查共用现有规则，作者范围内的错误包直接回原 reader | 协调者代修作者稿、接入大段 traceback／正文，再转述给 reader | 小至中 |
| D：完成事件驱动一轮推进 | 宿主有完成／需处理事件时，一次脚本组合已获语义允许的发布、修订包和已决定的下轮准备 | 短 wait、重复状态汇总，以及每个小步骤唤醒一次协调者 | 中至大 |

### A：最小改动，独立可做

拟议调用：

```text
memory publish --completed completed.json --output frozen.json --control owner.control --result result.json
memory publish --frozen frozen.json --control owner.control --result result.json
```

第一种用于首次冻结并发布，第二种只使用已有固定 batch 接续。完成稿清单保存作者／assignment／路径／文件 hash；完成事实来自宿主已结束的作者事件及 owned handle，文件存在本身不构成交稿。

脚本保存冻结文件后才进入发布副作用；stdout 返回 batch 身份、状态、必要错误和明细位置。文件字节 SHA 与 apply 内部规范化 hash 分开命名。数据库中的 batch receipt 是发布权威，本地结果文件是投影；提交成功但本地回执写失败时，可按原 batch 核定并恢复投影，不能因此重新 freeze 或重投新 batch。

### B：减少协调者反复装载正文

```text
memory prepare-dispatch --receipt fixed.json --control owner.control --assignments assignments.json --output round.json
```

每个 assignment 的来源范围、reader slot 和需要共读的依赖由 agent 明确决定。脚本批量调用现有 prepare、写各自 reading 包并调用现有纯 prompt 渲染；原 prompt 渲染函数不新增隐式数据库访问。外层索引只含路径／版本、scope、private 标记、包位置、精确 task_name／model／effort 和原始错误。

reader 直接使用准备包，依合同补读必要依据；准备后发生变更仍由发布版本检查拒绝。协调者需要原文判断关系时按需共读，不把“减少重复读取”变成禁止阅读。

**脚本不能代替宿主派出订阅 agent。** 清单是待派工，宿主仍须实际 spawn／followup，保留已启动名称、名额、handle 与生命周期。不要通过新增 LLM API、数据库任务队列或调度服务规避这个边界。

### C：错误回原作者，发布权保持

共用结构规则，而不是再运行一遍完整 apply 或增加模型审稿。可选 `draft-check` 从 freeze 提取共用形状检查，输出最小错误定位及完整原错文件；不调用 embedding、不认定语义合格、不提交临时 UUID。

格式、原作者证据／覆盖、语义切块等修订回原 reader，重新 prepare 后生成新路径与 hash。跨稿 expected 冲突、重复 source、关系两端或结论冲突，仍由协调者共读整合。脚本不自动改 expected、接受 stale evidence 或机械截短原文。

### D：按完成事件推进，一次做完已决定的机械步骤

D是A/B及修订材料准备的薄组合层：协调者决定要做什么，脚本把这些确定性动作一次做完后退出。没有持续运行的后台调度器，不在脚本里再调用模型，也不把Python脚本当成宿主的spawn／followup／wait／cancel工具。

#### 一轮的实际流程

1. reader显式完成或报告需要处理的问题，回传assignment、最终路径／hash、覆盖与原错位置；运行中的临时路径不算交稿。
2. publisher根据现有作者合同和已知assignment，明确哪些稿可独立发布、哪些必须合并／共读、哪些回原作者以及下批安排。对独立且已完成的稿可直接接受，不新增逐条语义审稿。**作者完成事件不是脚本自动决定发布组或关系成立的许可。**
3. 一次cycle执行已决定的验hash、按组freeze／apply／回执、修订包和下轮reading包准备，最后返回短索引。每组独立事务，整轮不是一个事务。
4. 协调者处理结果中真正需要判断的事项，使用宿主工具实际followup／spawn；其它reader继续工作。一个reader ready即可推进，不等全队交齐，也不为凑批延误错误。
5. 使用宿主完成事件等待下一次变化；无新事件不反复读取全队状态。必须看结果才能决定的语义步骤，留给下一次agent判断，不提前猜答案。

#### 拟议输入输出

```text
memory cycle --receipt fixed.json --control owner.control --input cycle-plan.json --output cycle-result.json
```

`cycle-plan.json`最少表达以下明确决定，字段名仍为设计示意：

```json
{
  "completed": [{"assignment":"r1-a", "author":"bp_mem_read_00", "draft":"a/final.json", "file_sha256":"..."}],
  "publish_groups": [{"group":"g1", "assignments":["r1-a"], "frozen":"g1/frozen.json"}],
  "repair_requests": [],
  "hold": [{"item":"relation-b-c", "reason":"等待B/C两端原证共读"}],
  "next_assignments": [{"author":"bp_mem_read_00", "paths":["E.md"], "after_confirmed":"g1"}]
}
```

宿主完成事实及owned handle沿现有派工所有权建立；脚本不从文件存在推断完成。多稿组保留原顺序和scope，不拼接member数组。修订请求写明原作者、受影响范围及原错位置；脚本只准备材料，不代做修订。下批路径由agent选择；若依赖某组成功，最多支持这种明确前置条件，不先建通用依赖引擎。

输出只列 `published / repair_required / dispatch / held / not_started` 及对应身份、路径和原错；大正文、完整trace和回执留文件。dispatch附现有layout要求的task_name、model／effort及命令，但仍表示待派工。每组单独保留固定frozen与程序回执后再推进，不只依赖最后一份汇总说明先前发生过什么。数据库batch receipt继续是发布权威，本地cycle结果只是部分成功／未执行项的可恢复索引。

#### 四个reader的例子

设R1读A、R2读B、R3读C、R4读D，B/C存在待核关系：

| 到达的事件 | 一次脚本可做 | 留给agent／宿主 |
| --- | --- | --- |
| R1先完成A | 发布A、记回执、准备已决定的E阅读包 | followup R1去E；不等待其余三人 |
| R2与R4完成 | 按明确组发布B/D；B→C关系留hold；准备已决定的独立下批 | 宿主继续派工；若D版本被拒，publisher决定回原R4修 |
| D的修订决定已作出 | 按请求准备当前D、错误包，与本轮其它机械步骤合并 | R4重读并生成新稿，脚本不改expected |
| R3完成C | 发布C、按明确要求准备B+C共读包与下批 | publisher共读两端原证、决定关系并生成整合稿 |
| 修订稿与关系稿完成 | 按各自明确组依次freeze／apply／回执 | 仅处理新的实际冲突；普通成功批不追加审计 |

本地知识稿与待整合关系须由作者明确分开；若一份draft不可分，就hold整稿或请原作者拆稿。脚本不得删edge让本地稿先过。已独立接受的B/C后来建关系时，使用其当前UUID／expected与共同阅读依据，不能沿用旧草稿位置当长期身份。

表中cycle是可合并的工作点，不是强制流转阶段。若只有一个作者需修订，直接followup其按现有prepare／修稿流程处理即可，不为经过cycle再多做一轮调用。

#### 失败与停止

- 明确的格式／版本拒绝：返回受影响组、原作者和原错，按已有明确计划才继续无关项；已确认成功不返工。不能自动改expected或重新freeze重试。
- 数据库已提交、本地结果文件写失败：据原frozen与数据库回执核定并恢复本地索引，不把它变成全队修稿。
- 提交结果未知：保留原frozen、marker和owner，停止本次后续发布与依赖步骤，返回未执行项；先核原发布，不盲重试、不自动release。shared owner因此仍被占用，不能承诺完全不影响其他排程。
- 主任务stop：结束整个维护生命周期，未admission项停止，已admission事务按既有合同确认结束；宿主取消后代，确认发布结束才release。
- 没有明确处理方法的非预期错误继续抛出，保留原错和先前成功记录，不用统一“失败”或空数组掩盖。

#### 相比A+B+C，额外能省什么

```text
分开调用：agent已决定发布g1和准备E → A → 模型重入 → B → 模型重入 → 宿主followup
D：       agent已决定发布g1和准备E → 一次组合脚本    → 模型重入 → 宿主followup
```

可消除的是A/B之间没有新判断的模型重入，以及多项同时完成却逐项装载全队状态的重复；真实派工、跨源共读、修稿和未知发布核定仍需要agent。工具操作数不等于模型用量事件数，不能据此声称固定token节省。

**建议先简版D**：紧凑完成回报＋宿主事件等待，把已决定的A/B放在同一次host exec，先不新增cycle CLI。若A/B已经这样合并，完整cycle额外节省的模型往返可能很少，甚至为零；它的新增价值主要是固化重复编排、统一部分成功与未执行结果。真实日志仍反复出现手写多组发布／下批准备／记账时，再选完整cycle；不为接口名称先建一套调度机制。


### 近期实际维护后的补充选择E／F

[案例分析](research/d-flexibility-20261115.md)实时回读11/14显式维护与近期自动维护聊天。现稿D的薄组合定义可承载实际流程，但源变化后的拆组／重读、语义分块和新增失效依赖都需要结果后新决定；D不能根治权限、owner占用或源竞争。完整cycle相对A/B已同exec时的额外收益没有实证。

- **E：专用发布helper＋原子工具自由组合（推荐起点）。** 先只固化A的稳定发布契约，prepare／read／neighbors／render等仍可直接用；agent在一次host exec写普通顺序代码或条件分支，执行到下一个真正需要判断的位置即返回。不必填写全轮cycle-plan、hold或未来assignment；原作者可直接修稿，独立组可随时拆合。这是简版D的具体实现形态，不是另一套调度框架。
- **F：单次发布附定点判断材料（可选）。** 若失败定位仍反复占往返，再附已有来源／成员／范围、版本、token数、原错位置及必要材料；invalidated可附当前状态。只报告事实，不自动派修或解释语义，不为覆盖所有错误建通用恢复器。

### 建议选择与共同完成条件

建议以**E**为实现起点：先做稳定发布helper，保留原作者修稿与宿主事件等待，再按真实重复加入B／C的专用接口或F；完整cycle仍为可选包装，未获用户选择。不更换协调者模型，不添加一层LLM发布员，不强制协调者／reader用量比例。

所有选项保留：单 owner／control、唯一 publisher、作者 scope、语义关系两端共读、原文与知识版本检查、实际向量准备、private 边界、原始异常、未知发布保留所有权，以及 stop 后已获准发布结束才 release。错误局限于受影响批；无关已确认成功不返工。反馈只有在 agent 明确判断 outcome／依据后才能结案，发布成功不自动清空反馈。

所选实现只做对应必要回归：跨稿引用与身份不变、固定 batch 幂等、冻结后中断、数据库已提交但本地回执失败、局部版本冲突、stop 前后 admission 和未知结果恢复。普通维护由作者生成与程序提交闭环结束，不新增发布后逐项语义审计。

效果沿后续真实维护日志核对：协调者模型事件／上下文、全队 token 分项、原始错误和返工、有效覆盖、停止响应及耗时分别记录。不预报节省百分比，不为证明省 token 另开全项目维护或本机模型质量对照；真实收益继续由用户使用反馈判断。

## 三、随任务进行的持续整改

### 推荐的最小结构与触发

```text
devDoc/tasks/ongoing/
  README.md                          短索引：主题、expires_at、匹配职责／路径、状态、链接
  YYYYMMDD-short-topic/plan.md        时间元数据、缘由、客观命中、边界、验证及结束条件
```

复用tasks的持续目标子类，不新增顶层archive或另一套维护服务。每主题一份短计划即可，**必须有有限的失效时间**；一次小修不使主题自动完成，也不使它自动续期。

未来 AGENTS 只增加一条指针，候选文字：

> 修改代码、配置或开发文档时，本任务读一次持续整改索引，发现到期项先归档，再按已确定的工作范围选择有效主题；遇到具体命中时，按主题边界顺手修复或记录。

按主任务读一次索引，必要主题随子任务 brief 交接。在本来就需要的阅读与验证中，按主题的客观信号核对当前范围；发现可证明的问题，再核直接调用方、消费者和相邻测试／文档，作局部完整修复。用户要求只读、讨论或不实施时，这个机制不增加修改授权。

### 有效期与发现时归档

- 沿旧项目默认取 **创建后7天（168小时）**，每主题可明确指定其他有限期限。本版不提供persistent豁免。主题头保存不可变的`created_at`和明确的`expires_at`，使用带时区的ISO 8601，不依赖mtime、最近编辑／命中时间或文件名推算。
- 示例（不是本轮新建主题）：

```yaml
created_at: 2026-11-15T12:00:00+08:00
expires_at: 2026-11-22T12:00:00+08:00
```

- 采用`now >= expires_at`即失效。旧合同使用严格晚于截止时刻；本项目按用户“到了失效时间”的表述采用到期即失效，不保留相等瞬间例外。无需秒级执行，在下一次正常读索引时发现并处理，不建定时任务。
- 主题头为时间字段的维护源；短索引展示`expires_at`投影，创建或明确改期时同步。先从索引找出到期候选，只核这些主题元数据与未完摘要，不为判断到期全读所有主题正文。
- 确认到期后，agent直接把整个主题目录移入现有`devDoc/archive/`，核源／目标冲突，保留原时间，补实际归档时间、原因与未完范围；移除活动索引项并修复直接引用，不覆盖既有归档。此动作不表示完成原目标。
- **到期未完成就标“到期归档，未完成”**。不自动刷新日期、续期、复制新主题或继续按失效指令整改；未来是否重新启动由新的需求决定。普通编辑／修复不续期，明确改期保留原created_at。用户明确禁止任何写入时，先报告到期而不违背当前只读约束。

经记忆检索得到的旧主题同样先核期限与活动状态，不能绕过到期规则；归档内容只作历史参考。

### 范围、记录与退出

- 不为找命中而全仓扫描，不要求每轮收尾比较所有主题；无命中不写“已检查无问题”的记录或汇报。
- 以一个明确问题、当前职责和可独立验证的完整修复为边界，不硬设一至两个文件上限而留下半迁移。需要独立调查、改变公共合同、数据迁移、生产部署或跨项目动作时，记录后转普通任务，沿既有授权处理。
- 具体发现与处置只沿当前任务 progress／结果及现有 change_log／Git 保存。主题文档不复制每次事件台账；无所属任务沿总进度登记，后续只有新证据／状态变化才重报。
- 一次命中以修复和相称验证完成为止；主题到期、用户撤销、合同替代或有边界目标真正完成时归档，区分到期失效与目标完成。没有命中次数、行数下降或额外审计的验收指标。
- 记忆返回／漏检的知识疑点继续走 `memory feedback-report`；本机制承接源码／配置／现行文档的整改目标，不另造与记忆反馈竞争的问题队列。

首批建议两个主题：①清理已失用的应用层重复控制／无独立职责的回退；②补齐现行入口与已完成切换的一致性。依据是本项目已处理的 Condor 重复计时／PID 确认、UUID／旧协议切换及退役试验入口，不宣称当前仍普遍有这些缺陷。历史原证、恢复材料、真实协议字段和仍有效的旧命名不因看似过时被改写。

当前先做项目局部机制，不新增通用 skill。若以后实际跨项目复用，再考虑把通用布局／触发方式并入 file-structure，保留项目主题与状态在本项目。

## 拟议实施顺序与本轮结束

1. 用户选择协调者选项组合，并确认持续整改的目录／触发方案；以上是具体可评审稿，尚非实施指令。
2. 优先完成 embedding 的隔离实现与32k验收，再部署共享服务；同步相关源码、必要测试、模板／现行说明和实际机器配置。
3. 完成所选协调者确定性接口及短 prompt，按局部合同验证后普通安装。部署不自动触发一次全项目维护。
4. 启用ongoing短索引、带失效时间的首批主题、AGENTS单条指针及documentation归属／到期归档说明；只启用机制，不借机全仓整改。

每个完整修改按既有 main 提交约定交付。实施结果另记录实际检查与余项，不把本讨论稿、探针成功或节点数量当作功能交付。

初次规划及柔性预算／到期规则修订只读核对当前源码、既有token／显存调查、旧auto合同并保存讨论稿；当轮跨历史检索完成原证阅读、评分与rank，7项入选，未运行GPU、产品测试、部署或自动记忆维护。freshness沿既有Codex状态库权限问题未取得全局回执／逐聊天截止点，相关当前入口与源码另有直接核读，不作全历史现行性结论。后续D案例分析及其并行普通维护的独立收尾见[分析报告](research/d-flexibility-20261115.md)。计划检查只核UTF-8、链接／锚点与Git差异。

后续讨论已按用户要求改为柔性显存目标、补齐D的事件过程／接口／失败边界，并采用ongoing默认7天与发现到期归档。只是计划修订，生产仍有原分配器硬限制，新接口与ongoing机制均未启用。
