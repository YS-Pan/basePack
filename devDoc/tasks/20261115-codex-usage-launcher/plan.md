## 实施顺序

### 1. 固定起点

在用量统计原项目核 Git 状态、已有媒体修改、解释器与安装副本，记录实际版本。保留原启动器和相关配置的恢复定位；读取必要路径键即可。确认没有本次需要结束的 GUI／更新进程，不擅自停止用户在途统计。当前结果可支持启动器修改，无须迁移或重建缓存。

### 2. 修改原启动器

只在该脚本的 `setlocal` 范围内设置 `CODEX_USAGE_REPORT_DIR=%~dp0codex_usage_report`，在切换工作目录之前形成绝对报告路径。保持解释器选择规则与 `%TEMP%` 下调用安装包的方式。

从选中的 console Python 同目录定位 `pythonw.exe`，以 `start "" "<pythonw 完整路径>" -m codex_usage gui` 分离启动，不使用 `/wait`。缺少对应 `pythonw.exe` 时明确报错，不另选其他环境。成功派出后结束本批处理；凡已成功 `pushd` 的分支，包括预检或派出失败，均先 `popd` 再 `exit /b`，恢复调用方工作目录。

分离前用同一 console Python 运行轻量的 `-m codex_usage gui --help`，让缺包、Tk 导入与路径配置错误在 cmd 内显示并暂停；只抑制正常帮助文本，保留错误原文。该检查不安装依赖、不生成报告，也不把 FFmpeg／完整动画依赖作为打开 GUI 的门槛。

`start` 成功只证明进程已派出，不能当作 GUI 就绪。实际窗口验收覆盖 Tk 启动；若遇到启动后的异常，用同一解释器前台运行 GUI 获取原错。不为此增加启动握手文件、常驻监护或重试协议。

### 3. 同步说明并验证

在原项目 `docs/usage.md` 和 `docs/installation.md` 说明可选 `.cmd` 的项目内结果目录及窗口行为，通用命令仍按既有配置运行。核 README／开发入口对启动器的直接描述，有冲突时定点同步。路径规则继续由既有 `paths.py` 维护，不另造一套配置。

优先扩展现有 `tests/test_installed_paths.py`、`tests/test_cli.py` 或 `tests/test_user_entrypoints.py` 中适合的回归：在新进程导入 GUI，确认报告环境变量只覆盖报告路径，设置与缓存仍来自所选状态根。保留能复现启动器问题的 Windows 进程验证，不用脚本文本匹配代替行为验收。

预计改动集中在 `.cmd`、相关说明和定点回归；不修改包内路径／GUI 实现，因此无须重建 wheel 或重装系统包。实施时若发现必须改包内代码的真实缺陷，先记录证据并据此调整范围。
