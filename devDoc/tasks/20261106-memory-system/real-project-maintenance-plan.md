## 修改顺序与完成条件

### M1 修正记录 ID 往返

唯一修改源为 active 工程的 [store.py](../../../experiments/20261106-basepack/src/basepack/memory/store.py) 中 `_record` 及其调用合同。当前仅剥离 `⟨⟩`，SurrealDB 4 返回的 ``member:`brief-order` `` 被当作含反引号的原始键；[vectors.py](../../../experiments/20261106-basepack/src/basepack/memory/vectors.py) 因而核查了错误记录。修复必须覆盖所有共享此转换的读写路径，保留真正的并发版本冲突检查。

先用隔离库复现原始失败，再以底座实际返回值建立小型往返回归：普通字母数字、连字符、纯数字字符串、空格及需要转义的字符。明确原始 key 与 canonical record ID 的输入语义及类型，保留原记录身份；不以全局去引号、改名或重建业务记录修复问题。

**完成条件：** 原始失败 ID 可完成 prepare/apply → embed → search/read → neighbors/更正，返回 ID 可再作为输入，parent/evidence/语义两端仍指向同一记录；第二次 embed 复用未变向量。更正期间真实发生版本变化时仍明确失败。文字往返使用真实 SurrealDB；向量路径先做确定性回归，再至少用一组特殊 ID 完成共享服务实际编码。现有业务项目已退役的旧记录及审计继续保留，恢复支持不等于恢复其当前状态。

### M2 简化接入与失败定位

- 在 [项目接入](../../../experiments/20261106-basepack/docs/setup-project.md) 与 [管理员说明](../../../experiments/20261106-basepack/docs/administrator.md) 中，将独立目录、project_id 和端口选择放到 memory init 前。沿现有配置显式选 endpoint，让启动示例使用同一个值；用两个项目分别占用 18080/18081 的例子说明共享 exe、独立数据的边界。
- 普通用户隐藏 launcher 的检查包含：启动调用结束后，下一次独立调用仍可访问 `/ready`，再以目标配置执行 init/brief 核对项目身份。日志、cwd、凭据加载和解释器入口可定位；仅检查所需设施。进程存续受宿主限制时保留实际错误和可用启动方式。
- 在 [记忆说明](../../../experiments/20261106-basepack/docs/memory.md) 与随包 skill 提供一个完整最小批次：file/section/chunk 的准确行范围、从 prepare 原样沿用的 expected，以及实际存在的 parent/evidence。缺字段报出成员 ID、字段与批次位置；不存在的 read ID 报出目标，不继续解引用 None。只处理这两类可纠正输入，不建设通用校验框架。
- 示例及项目调用脚本在依赖命令后立即核退出码，apply 失败即停止 embed/search/read；编码与取证脚本明确使用 UTF-8。Git 初始化与阶段先后仍由业务项目计划承担。

**完成条件：** 一个干净项目能按短文档完成接入，另一项目保持原状；同项目另开调用能继续 brief。错误项目身份被拒绝；缺字段或缺失 ID 能直接定位，返回失败且不留下部分批次。调用链失败后没有下游成功回执混淆结果。T04 的普通用户 Condor 成功作为环境差异证据，不作为修复沙箱的要求。

### M3 交付可识别的普通安装版本

试用基线与当前 main 均标为 0.6.0，但内容不同。[618749d 的修复记录](../../change_log/minor/20261109_170434_reconcile-memory-contracts.md) 已包含并发依赖、初始化事务及入口路径修复，尚未重建 wheel 或重装稳定客户端；它也未修复 T07。历史安装版 108 项通过与后续源码 117 passed / 3 skipped 的对象和开关不同，不能合并为新包验收。

M1、M2 完成后合并这些已有修复，一次构建可区分的新补丁版本，建议 0.6.1。记录源码 commit、wheel SHA256、安装解释器与实际导入位置；按受影响范围跑回归，并在源码外普通安装后验证首次接入、特殊 ID、小批更新与恢复。共享 embedding 协议/身份不变时复用现有服务。

**完成条件：** 源码、wheel、源码外安装及检查记录能一一对应，真实编码的跳过情况明确。先在独立环境/项目验包，再备份并升级现有业务客户端，核项目配置、知识身份及 read/search；保留原 wheel 与原生备份供回退。同步 README、产品文档、skill 和系统说明中的实际行为。远端发布另按既有联合发布流程处理。

### M4 在原小项目补齐持续使用证据

不重新制作整套 PPT。保留一份冻结的业务材料/知识快照，围绕现有交付做下列小循环；影响现用知识的破坏性场景放在本项目备份恢复出的隔离副本中。

| 场景 | 任务与验收 |
| --- | --- |
| 新任务启动 | 新开无答案历史的聊天，提出“继续修改汇报”等不点名约束的任务。启动实收并采用“试用问题不进正文/备注”“源码与安装验证不可混算”等必要前提，核结果与原文；仅打印 brief 不算通过。 |
| 正常增量 | 变更一处交付事实或研究结论；检查 changes → 同读维护 → 重新检索。新结论可回源，旧句不作为当前事实，相关摘要/关系同步核实，未变成员和向量复用。 |
| 更正与删除 | 更正一条有条件关系，再移除一份支持材料；按剩余证据决定保留或退役，历史和审计可查，其他有效关系保持。 |
| 原生恢复 | 使用现有 export、对应版本原件、配置和必要 assets，在另一物理目录/端口恢复；核摘要、依据、历史、图邻域、read/search 与必要向量重建。现有 backup 脚本和 hash 核对是输入，不是恢复成功证明。 |
| 简单效果对照 | 从真实任务选少量已知定位、跨材料取证和未知前提题，比较直接文件、短提示加文件、完整记忆。冻结资料与预期答案，限制相同最终上下文预算并记录实际初始上下文；已知少量文件仍可直接批量读。 |

效果记录包含答案必要事实/漏项、过期结论、原文支持、主 agent 往返、主与 worker 总耗时，以及首建、增量、失败修复和恢复投入。实际可得的模型、tokens、费用另记，取不到则留缺；字符数与工具次数分别报告。先确认质量和维护负担，再判断是否值得继续扩展；本小项目不足以证明广泛召回、大语料或并发性能。

## 后续维护方式

| 触发 | 最小维护动作与交接 |
| --- | --- |
| 每次开始或接续任务 | 读取现有入口并 brief；直接保留当前 mandatory，待核内容回原文。只维护与任务相关的小批，剩余范围交接。 |
| 修改原件或发现错误 | 对明确范围 changes/prepare，同次完成边界、摘要和关系复核，再 apply/embed；只更新受影响表示，失败保留 pending 与原错。 |
| 阶段收尾、升级或搬迁前 | 确定 source_scope 中应保留的稳定材料，核必保信息和覆盖缺口，按需要原生导出并带齐原件/assets/配置；恢复要求与保留位置由该业务项目维护。 |
| 复现故障或依赖变化 | 把真实故障缩成回归，检查受影响合同；一般文档/普通使用不重跑全部设施矩阵。定期深维护按实际变化和漏项需要安排。 |

小任务由一个订阅 agent 完成；ID 修复与接入文档可分工，主 agent 统一检查、提交和整合。M3 依赖前两项，M4 的安装验收依赖 M3；效果对照的题目和冻结快照可提前准备。每完成一项更新 [进度](progress.md) 并提交相关实现、文档和变更记录。当前下一步是 M1 的隔离复现与根因修复。
