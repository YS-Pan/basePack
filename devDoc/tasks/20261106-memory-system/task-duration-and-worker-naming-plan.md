# 自动维护时长判断与 worker 命名计划

2026-11-12（北京时间）。状态：方案待选择，仅交付计划，尚未修改入口、程序、提示词或安装包。现行基线仍为 0.10.0.dev1 的默认异步维护；历史交付见[实施结果](maintenance-implementation-result.md)。

## 用户要求与当前差距

用户要求主 agent 在任务启动时凭直觉估计业务耗时：约十分钟以内不启动自动记忆维护，超过十分钟才启动，不要求准确预测。自动维护的专职协调者和执行者采用统一命名规则，不再由每个调用者自由起名。

当前 [AGENTS 模板](../../../experiments/20261106-basepack/src/basepack/project/templates/agents-enabled.md)及[本机入口模板](../../../experiments/20261106-basepack/src/basepack/project/templates/memory-enabled.md)默认直接启动 maintain，没有时长判断。[prompt_dispatch](../../../experiments/20261106-basepack/src/basepack/memory/prompts.py)返回角色、模型、推理强度和命令，没有 worker 名称。[协调者模板](../../../experiments/20261106-basepack/src/basepack/memory/prompts/coordinator.md)已有最多四名 reader、协调者唯一发布者及持续接批的约定，名称尚未统一。

## 共同约束

- 时长指本项业务从开始到完成的预计经过时间，包括必要阅读、实施、验证及正常收尾；不加上自动维护耗时，不累加并行 agent 工时，也不把等待用户答复当成必然超过门槛的依据。
- 约十分钟及以内归短任务；接近边界时由 agent 凭直觉选择，不另作精确估算、计时、评分或工具调查。判断可嵌入原有启动说明，用“预计短任务，跳过自动维护”或“预计较长，将并行维护”表达。
- 短任务跳过整个自动 maintain，包括聊天采集、机械预检、取得 owner 和语义派工；不是先运行 maintain 再只省掉 reader。brief 及业务需要的 search/read/neighbors 继续按原合同使用。
- 用户明确要求维护时按显式维护处理，覆盖自动门槛；明确要求不维护时照办。已有他人 owner 时继续业务，不建立第二支维护团队。
- 判断只属于业务任务入口；维护协调者、reader 和普通检索 worker 不为自己的子任务再开维护。接续同一目标或压缩上下文不重复启动。
- 长任务仍使用全项目范围、固定回执和现有模型档位，结束时 stop 自有 control、取消子树、确认发布结果后 release。一次估计变化不反复启停；名称不承担权限或所有权识别。

## 一、时长判断方案

| 方案 | 行为 | 取舍 |
| --- | --- | --- |
| T1：仅启动时判断 | 开始时直觉分为约十分钟以内或以上；本任务保持该决定 | 最简单，最贴近一次判断；起初很小、后来扩大时可能错过维护 |
| T2：启动判断，范围明显变化时重估（推荐） | 初判同 T1；新增需求、发现排错或验证范围明显扩大时，随正常业务思考重新判断本项完整业务时长，必要时首次启动维护 | 能适应真实任务变化；不新增周期检查或计时器 |
| T3：允许必要查阅后再定 | 启动时确实信息不足，先做业务本来需要的最短查阅，在已有线索上完成判断 | 适合陌生项目，但维护启动较晚，也更容易拖延决定 |

T2 不以“已经过了十分钟”自动触发，也不把纯粹的估计误差当缺陷；没有新范围信息时无需追认一次补维护。若业务实际上已进入最终答复或提交收尾，不再为补开维护延长任务。已经启动的维护继续按原任务生命周期运行；中途不因重新估成短任务而频繁停止、重开。

推荐先把十分钟作为随包入口里的默认约定，不新增 TOML 配置。若未来确有项目要求不同阈值，再提供单一配置来源；这不是本次需求的实施前提。

拟议入口顺序为：主 agent 理解任务并粗判时长 → 按现有要求 brief → 短任务直接业务；长任务独立异步 maintain。brief 失败与维护启动是两项动作的各自失败，不能因同一段命令里前者 throw，就在未报告的情况下漏掉后者。

## 二、统一名称方案

| 方案 | 示例 | 取舍 |
| --- | --- | --- |
| N1：短角色与固定槽位 | `mem_coord`、`mem_read_01` 至 `mem_read_04` | 名称短；在混合业务团队中专职身份不如完整前缀醒目 |
| N2：产品前缀、固定角色与槽位（推荐） | `basepack_memory_coordinator`、`basepack_memory_reader_01` 至 `basepack_memory_reader_04` | 每轮名称一致、用途清楚；同父同名的复用需要宿主支持 |
| N3：角色加运行标识 | `basepack_memory_coordinator_<已有run标识>`；reader 按同一规则带标识 | 容易区分每轮实例，但实际名称逐轮变化，仅规则一致，不完全满足固定名称偏好 |

N2 默认结构：

```text
业务主 agent
└─ basepack_memory_coordinator
   ├─ basepack_memory_reader_01
   ├─ basepack_memory_reader_02
   ├─ basepack_memory_reader_03
   └─ basepack_memory_reader_04
```

槽位号表示同一父 agent 下的执行者位置，不表示文件、批次、模型或日期。同一 reader 完成一批后沿已取得的宿主句柄继续下一批，不为每一批换名新建。并发和组织仍按现有规则选择，不因列出四个槽位就必须创建四名 reader。

### 名称由谁提供

名称常量与槽位生成规则集中在现有 prompts 派工维护源，模板只引用渲染值，不分别手抄一份命名表。建议：

- maintain 的 `worker` 增加 `task_name`，主 agent 将其原样传给宿主创建参数；模型与 reasoning_effort 继续使用同一 worker 结果。
- 协调者渲染结果提供固定 `reader_task_names` 列表，英文协调者 prompt 指明用空闲槽位的给定名称派工、按句柄复用。名称覆盖现有单协调者与最多四名 reader 的派工合同。
- reader 的角色说明保持既有有界阅读和不自行 apply 的职责。名称不随 tier 切换而变化，不另设命名登记表、全局调度器或持久计数器。
- 使用句柄、control 和 owner 确认实例及权限，不能仅凭同名复用别人的 agent。新维护轮次使用全新 control；可复用的自有协调者须已满足选定命名规则，并先确认上一轮已结束且发布已解决。旧的任意名称不因复用而视作符合新规则。

### 宿主能力与同名冲突

当前 Codex 工具允许显式传 `task_name`，并提供 `followup_task` 复用已有 agent。可明确约束的是这个参数及其父子路径；随机昵称、头像名等独立展示字段是否随之固定，当前接口不能保证。

实施前做一次小规模宿主验证：同一父 agent 的同名创建是否被拒绝、已完成及已取消的自有句柄能否接续、用户实际界面能看到哪个名称字段。遇到同名冲突，优先使用已知且生命周期允许复用的自有句柄；没有可用句柄时保留错误并报告，不让 agent 自由添加日期或语义后缀。若宿主无法实现严格固定名称，先报告限制，再选择 N3 或宿主提供的固定展示字段；不得自行把“名称一致”降为“只有前缀一致”。

## 推荐组合与实施顺序

建议选择 **T2 + N2**。T1 + N2 是更小的第一步；只有宿主的同名约束无法解决且用户接受逐轮不同名称时，才改选 N3。

选择后再实施：

1. 验证宿主名称和句柄复用边界，确认可交付的名称效果。
2. 在 AGENTS 与详细入口模板加入时长判断，随包 memory skill 承接详情；直接 maintain 命令不增加程序“猜时长”或强制计时拦截，显式维护仍可直接使用。
3. 扩展既有派工元数据和英文协调者模板，使名称由同一来源生成、在实际创建时使用。保留默认 tier2 协调、tier1 阅读和统一发布职责。
4. 更新当前行为文档，复用既有入口刷新与 prompt 测试；通过下列实际场景后构建普通 wheel，按原 UUID、凭据和知识保留合同升级目标项目。刷新前先收尾旧版本维护；其它项目是否升级单独记录。

当前部署没有应用这些步骤。本轮仅形成计划与进度入口，项目纲领保持原文。

## 验收与边界

| 场景 | 要看到的行为 |
| --- | --- |
| 简短问答、查询 PID 等直觉短任务 | brief 保留，整个 maintain 未启动，没有该轮 owner 或维护 worker |
| 明显超过十分钟的改动 | 启动时只开一轮全项目维护，业务与维护并行 |
| 短任务后来新增较多排错或验证工作 | T2 在自然范围变化时重新判断，可首次启动；不等待计时达到门槛 |
| 用户直接要求维护记忆 | 不因估计很短而跳过，仍按授权范围交付 |
| 普通维护创建与多批接续 | 实际 task_name 使用产品给定值，reader 沿槽位句柄接批，模型配置与唯一发布者保持 |
| 同一父 agent 的下一轮维护 | 验证同名复用，control 更新，不复用他人实例、旧任意名称或旧发布状态 |
| 业务结束与启动失败 | 只停止自有维护，确认发布后释放；真实失败在业务答复中说明 |

验证聚焦行为与已有 prompt 的无副作用合同，不以文案包含某字符串代替宿主实际派工，不要求真实等待十分钟，也不建立新的统计或计时框架。

短任务连续出现时，记忆可能积压到下一次长任务或显式维护；这是减少启动成本的直接取舍。本轮不另加定时维护、累计任务计数或自动审计来抵消它，也不宣称十分钟阈值已由性能对照证明最优。
