# 记忆维护入口、并发与 worker 派工计划

2026-11-12（北京时间）。状态：用户已选定 **T2 + N2 + S2**，待实施。S2 为安装保存宿主并发上限、运行时由纯函数计算组织并生成 prompt；本文件是后续实施合同的单一维护源，[评估](research/capacity-driven-prompts-20261112.md)保留选型依据。本轮只更新计划，尚未修改实际配置、入口、程序、提示词或安装包。现行安装基线仍为 0.10.0.dev1；历史交付见[实施结果](maintenance-implementation-result.md)。

## 用户要求与当前差距

用户要求主 agent 在任务启动时凭直觉估计业务耗时：约十分钟以内不启动自动记忆维护，超过十分钟才启动，不要求准确预测。自动维护的专职协调者和执行者采用统一命名规则，不再由每个调用者自由起名。

用户已选择 T2（启动判断，范围明显变化时重估）和 N2（固定角色与槽位），并指定短名称 `bp_mem_coord_0`、`bp_mem_read_00`。coord 后的数字是队号，read 后两位依次为队号、队内序号。自动维护只用第 0 队；手动维护可以按系统配置的 subagent 最大并发数组织更多队。

用户进一步提出低并发时只保留一个 coord 并兼做 reader。本计划采用这一最小组织：整轮维护可用预算较少时，默认只启动 `bp_mem_coord_0`，由它自己阅读、生成和发布；独立 reader 和额外队伍按工作收益与实际余量增加。

当前 [AGENTS 模板](../../../experiments/20261106-basepack/src/basepack/project/templates/agents-enabled.md)及[本机入口模板](../../../experiments/20261106-basepack/src/basepack/project/templates/memory-enabled.md)默认直接启动 maintain，没有时长判断。[prompt_dispatch](../../../experiments/20261106-basepack/src/basepack/memory/prompts.py)返回角色、模型、推理强度和命令，没有 worker 名称。[协调者模板](../../../experiments/20261106-basepack/src/basepack/memory/prompts/coordinator.md)已有最多四名 reader、协调者唯一发布者及持续接批的约定，尚需统一名称，并为手动多队区分发布协调与阅读协调职责。

用户另要求把记忆检索 worker 纳入统一命名。当前[检索流程](../../../experiments/20261106-basepack/src/basepack/memory/SKILL.md#retrieve-in-one-delegation)只规定一次委托、默认 tier1、多轮检索／原文阅读／评分／rank，没有规定 task_name；`config ai --purpose retrieval` 仅返回 tier、model 和 reasoning_effort。以下新增检索命名与派工约定同样待实施。

## 共同约束

- 时长指本项业务从开始到完成的预计经过时间，包括必要阅读、实施、验证及正常收尾；不加上自动维护耗时，不累加并行 agent 工时，也不把等待用户答复当成必然超过门槛的依据。
- 约十分钟及以内归短任务；接近边界时由 agent 凭直觉选择，不另作精确估算、计时、评分或工具调查。判断可嵌入原有启动说明，用“预计短任务，跳过自动维护”或“预计较长，将并行维护”表达。
- 短任务跳过整个自动 maintain，包括聊天采集、机械预检、取得 owner 和语义派工；不是先运行 maintain 再只省掉 reader。brief 及业务需要的 search/read/neighbors 继续按原合同使用。
- 用户明确要求维护时按显式维护处理，覆盖自动门槛；明确要求不维护时照办。已有他人 owner 时继续业务，不建立第二支维护团队。
- 判断只属于业务任务入口；维护协调者、reader 和普通检索 worker 不为自己的子任务再开维护。接续同一目标或压缩上下文不重复启动。
- 长任务仍使用全项目范围、固定回执和现有模型档位，结束时 stop 自有 control、取消子树、确认发布结果后 release。一次估计变化不反复启停；名称不承担权限或所有权识别。

## 一、已选 T2：启动判断，范围明显变化时重估

开始时凭直觉判断本项业务约十分钟以内还是以上；新增需求、发现排错或验证范围明显扩大时，随正常业务思考重新判断本项完整业务时长，必要时首次启动维护。不新增周期检查或计时器。

T2 不以“已经过了十分钟”自动触发，也不把纯粹的估计误差当缺陷；没有新范围信息时无需追认一次补维护。若业务实际上已进入最终答复或提交收尾，不再为补开维护延长任务。已经启动的维护继续按原任务生命周期运行；中途不因重新估成短任务而频繁停止、重开。

十分钟作为随包入口里的默认约定，不新增 TOML 配置。若未来确有项目要求不同阈值，再提供单一配置来源；这不是本次需求的实施前提。

拟议入口顺序为：主 agent 理解任务并粗判时长 → 按现有要求 brief → 短任务直接业务；长任务独立异步 maintain。brief 失败与维护启动是两项动作的各自失败，不能因同一段命令里前者 throw，就在未报告的情况下漏掉后者。

## 二、已选 N2：短名称、队号与队内槽位

| 角色 | 固定格式 | 示例 |
| --- | --- | --- |
| 第 t 队协调者 | `bp_mem_coord_<t>` | `bp_mem_coord_0`、`bp_mem_coord_1` |
| 第 t 队第 r 名 reader | `bp_mem_read_<t><r>` | `bp_mem_read_00`、`bp_mem_read_03`、`bp_mem_read_10` |

t、r 都从 0 开始。read 后严格两位数字：第一位 t 对应 coord 的队号，第二位 r 是队内槽位。沿用每队最多四名 reader，因此 r 为 0 至 3；队号 t 为 0 至 9，这套格式覆盖最多十队。名称不包含日期、文件、批次、模型或运行标识。

自动维护只创建第 0 队：`bp_mem_coord_0` 和按工作需要创建的零至四名 `bp_mem_read_00` 至 `bp_mem_read_03`，即使还有空闲席位也不自动扩队。手动维护同样支持只用第 0 队的 coord；有并行收益与余量时，才依次增加 reader 和第 1、2 等队。例如，下图仅示充裕预算时的多队结构：

```text
业务主 agent（持有项目 owner）
└─ bp_mem_coord_0（统筹、唯一发布者）
   ├─ bp_mem_read_00 ... bp_mem_read_03
   ├─ bp_mem_coord_1（阅读协调）
   │  └─ bp_mem_read_10 ... bp_mem_read_13
   └─ bp_mem_coord_2（阅读协调）
      └─ bp_mem_read_20
```

同一 reader 完成一批后沿已取得的宿主句柄继续下一批，不为每一批换名新建；不因列出四个槽位就必须创建四名 reader。手动维护的各队仍共用一次 maintain 取得的一个 owner、一份固定回执和一个 control，不为每队重新采集或取得所有权。

### 手动维护的并发预算

按已选 S2，在安装／项目接入时由 agent 取得宿主有效 subagent 上限，归一化后写入 basePack 配置，后续由程序读取并计算组织；配置与刷新合同见下文 S2 一节。先核清计数口径：若包含业务主 agent，采集时扣除；若仅统计 subagent，不重复扣除。本轮预算 M 还须受其它占用及业务预留约束，不能把安装快照当作当前空闲数。所有队的协调者和 reader 都计入该预算：

2026-11-12 查阅的[官方 Codex 配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)将 `agents.max_concurrent_threads_per_session` 定义为不含主线程的并发子线程上限，`agents.max_threads` 为旧别名；未设置时由 Codex 选择默认值，文档没有承诺固定为 3。本计划不把 3 写成 Codex 默认常量；占用以宿主实际计额为准，不能仅用进程活动或 running 标签推断。

`各队 (1 名 coord + 本队 reader 数) 之和 ≤ M`，每队 reader 至多 4 名。

程序先为第 0 队给出额度；尚有独立材料且至少剩余一名 coord 加一名 reader 的席位时，手动维护才增下一队。末队允许不足四名 reader，不要求用满上限。队号和团队额度由脚本统一计算，宿主提供可取得的原始额度并按结果派工；各队不得分别把整个系统上限当作自己的额度。

例如，宿主若总共允许 13 席、其中主 agent 占 1 席且无其它占用，则维护可用 12 席；上图为 3 名 coord 加 9 名 reader，共 12 个 subagent。13 只是本例的宿主上限，不写成产品常量。

### 低并发：coord 兼做 reader

| 整轮维护可用预算 M | 默认组织 |
| --- | --- |
| 0 | 不创建维护 worker，保留待处理工作并说明容量限制 |
| 1 至 3 | 仅启动 `bp_mem_coord_0`，不创建独立 reader 或其它队 |
| 4 及以上 | 按并行收益增加 reader；手动维护可以扩队，也可以继续只用一个 coord |

单 coord 沿固定回执逐批完成 prepare、原文阅读、分块、摘要、关系、已阅处置与反馈处理，再由 apply 执行程序校验、编码和原子发布；不等待不存在的 reader，也不另派 reader 或 reviewer 来补齐组织形式。仍使用协调者的配置档位（默认 tier2），名称保持 `bp_mem_coord_0`，不把同一个实例再登记为 `bp_mem_read_00`。

例如，若系统上限是 3 个 subagent 且没有其它占用，维护只使用其中 1 席，其余 2 席可供业务；若某宿主的 3 席包含主 agent，则主 agent 与维护 coord 合计使用 2 席，剩余 1 席。两种口径都能运行，前提是主 agent 先按实际口径核算预算。

表中的 M 指整轮维护预算，不递归套用到手动多队的每个末队。高预算多队中末队仍可只有一至三名 reader；只余一席时可留空，由已有 coord 自行阅读，不必为用满名额另开一队。容量不足或未派工不能当作显式维护完成。

### 多队职责与发布

`bp_mem_coord_0` 分配不重叠的来源范围、统筹各队、合并最终稿，并作为唯一发布者执行 apply 和反馈结案。`bp_mem_coord_1` 等其它队协调者负责本队 reader、必要的共读和组稿，只向第 0 队交付完成稿路径、hash、覆盖范围和余项；可以 prepare/read/neighbors，但不自行 maintain、apply 或解决反馈。reader 仍不 apply。跨队关系由第 0 队取得必要原文共读后生成。

其它队协调者放在第 0 队协调者子树内，主 agent 沿现有 stop、取消自有子树、确认发布、release 的合同收尾。实施前核宿主可用层级；不能将现有含“sole publisher”和 apply 的协调者 prompt 原样派给每一队，也不新增持久队列或独立调度服务。

### 名称由谁提供

名称、队号和槽位生成规则集中在现有 prompts 派工维护源，模板只引用渲染值，不分别手抄一份命名表：

- maintain 的 `worker` 增加 `task_name`，主 agent 将其原样传给宿主创建参数；模型与 reasoning_effort 继续使用同一 worker 结果。
- 拟扩展现有派工／渲染入口，读取已配置的宿主上限，接收自动／手动模式及可取得的本轮原始额度，由纯函数生成并固定本轮布局。自动模式只给第 0 队元数据；手动模式给预算内的队伍。协调者取得本队固定 `reader_task_names` 和额度，使用给定名称派工、按句柄复用；总协调者同时取得其它队协调者的名称、额度和成果返回目标。
- reader 的角色说明保持既有有界阅读和不自行 apply 的职责。名称不随 tier 切换而变化，不另设命名登记表、全局调度器或持久计数器。
- 使用句柄、control 和 owner 确认实例及权限，不能仅凭同名复用别人的 agent。新维护轮次使用全新 control；可复用的自有协调者须已满足选定命名规则，并先确认上一轮已结束且发布已解决。旧的任意名称不因复用而视作符合新规则。

### 宿主能力与同名冲突

当前 Codex 工具允许显式传 `task_name`，并提供 `followup_task` 复用已有 agent。可明确约束的是这个参数及其父子路径；随机昵称、头像名等独立展示字段是否随之固定，当前接口不能保证。

实施前做一次小规模宿主验证：配置并发上限的计数口径和可用层级、同一父 agent 的同名创建是否被拒绝、已完成及已取消的自有句柄能否接续、用户实际界面能看到哪个名称字段。遇到同名冲突，优先使用已知且生命周期允许复用的自有句柄；没有可用句柄时保留错误并报告，不让 agent 自由添加日期或语义后缀。若宿主无法实现严格固定名称，先报告限制，由用户决定是否调整方案；不得自行改成带运行标识或只有前缀一致。

## 三、检索 worker 的固定命名与脚本派工

检索 worker 拟定名称为 `bp_mem_search_0`。同一父 agent 确需同时处理多个独立检索任务时，使用脚本给定的 `bp_mem_search_1`、`bp_mem_search_2` 等槽位；序号表示检索槽位，不是维护队号。它与 `bp_mem_coord_t`／`bp_mem_read_tr` 使用不同角色名。

- 一次检索委托默认一名 worker，负责全部必要 search、read、neighbors、评分和 rank，再交付内容、依据与缺口；查询改写、补读与重排不创建新名字，也不按系统上限自动拆成多个检索 worker。
- 名称与维护命名共用程序维护源，增加独立的检索派工／prompt 渲染入口，统一返回 `task_name`、`model`、`reasoning_effort` 和 `render_command`。问题、项目范围及内容预算作为结构化输入，不拼进名称；调用者原样设置宿主参数，不自由起名。
- 模型继续按 `config ai --purpose retrieval` 解析，默认 tier1，可按现有合同显式改档。模型配置解析不兼任检索实例／槽位分配，后者属于派工元数据生成。
- 检索渲染不要求维护 receipt、control 或 owner，不复用当前维护入口的强制参数合同。检索不因命名而触发 maintain 或维护协调者，T2 的短任务门槛只限制自动维护，业务需要的检索照常进行；轻量反馈继续沿既有接口提交。
- 检索 worker 计入同一宿主 subagent 配额，作为业务占用传入维护预算计算，不另复制一份系统上限。没有可用席位时，由主 agent 直接执行同一检索流程并报告实际执行者，不能记成已派出 tier1 worker。
- 同一检索任务的后续轮次复用已知自有句柄；独立任务按原约定使用干净历史，不能仅为复用固定名字而混入无关查询上下文。槽位和同名冲突沿统一宿主能力验证处理，不新增持久计数器或自由语义后缀。

实施须同时更新随包 memory skill、项目 AI／资源入口说明及检索派工模板，保持一次委托交付完整检索结果的流程。

## 四、已选 S2：安装保存上限，运行脚本计算组织与 prompt

### 配置采集与刷新

安装／项目接入 agent 从宿主有效配置或明确报告中取得容量 C，统一为“不含主 agent、包含全部后代”的 subagent 上限，写入项目 `.basepack/config.toml` 的 `[ai].max_concurrent_subagents`。这是待实施的新字段，例如：

```toml
[ai]
max_concurrent_subagents = 12
```

容量与使用该项目的宿主绑定，不假设一次 Python 安装只有一种宿主配置。`ProjectConfig` 是唯一解析入口，`config show` 展示解析后的值及简短采集依据；各队和检索模板不复制容量。宿主未显式配置且无法取得实际值时，在接入阶段一次性取得明确值，不猜 3、13 等默认数。

C 是安装／接入快照。系统上限、profile 或宿主改变后，在升级／接入刷新时重新采集；S2 不自动监视系统配置。已有项目只补配置并刷新入口，保留 UUID、原凭据和知识。当前不建设宿主 profile 目录或运行时有效配置适配器，S1／S3 不列入本轮实施。

为使后续修改宿主上限的用户能找到同步动作，本轮增加下文“项目配置维护要点文档”交付：并发字段须明确标为采集快照，说明何时重新取值和同步受影响项目，不能只在首次安装步骤中提及。

### 脚本计算本轮预算与布局

输入为配置 C、自动／手动模式，以及宿主已有的可用额度 A（若可取得）。A 已扣除其它占用、尚未扣本轮额外业务预留，且不含主 agent。检索 worker 等业务 agent 也属于其它占用。首版工程默认集中定义为：自动维护预留 R=1、手动维护预留 R=0，不让 AI 每次临时选择预留值。

取得 A 时，程序计算 `M = max(0, min(C, A) - R)`；未取得 A 时，仅按 `max(0, C - R)` 生成配置允许的组织上限，并明确标为实时额度未核，不能称为当前空闲预算。已扣过预留的输入不得再次扣 R。实际创建始终受宿主准入约束，不为算组织额外增加一轮 AI 调查。

组队采用确定性规则：

1. M 为 0 时不派 worker；M 为 1 至 3 时仅 `bp_mem_coord_0` 兼做 reader。
2. 自动维护仅第 0 队；M 至少为 4 时，独立 reader 数为 `min(4, M - 1)`。
3. 手动维护每个完整队为 1 coord + 4 reader。对 M 除以 5 取整及余数：余 1 席留空，余 2 至 4 席再生成不满队；先执行低并发规则。队号顺序为 0 至 9，不为用满更大上限改变命名格式。
4. 脚本给出队伍数、reader 配额、固定名称、父子关系、模型、推理强度和发布权限。没有可分配材料的槽位可以不创建，AI 不再重新设计组织或自由命名。

以下 M 已扣占用和预留；c/r 为协调者／reader 数：

| M | 自动维护 c/r | 手动维护 c/r |
| ---: | ---: | ---: |
| 3 | 1 / 0 | 1 / 0 |
| 4 | 1 / 3 | 1 / 3 |
| 5 | 1 / 4 | 1 / 4 |
| 6 | 1 / 4 | 1 / 4 |
| 13 | 1 / 4 | 3 / 10 |
| 30 | 1 / 4 | 6 / 24 |

例如 C=4、A=4 时，自动维护 M=3，仅 coord；手动维护 M=4，为 coord 加三名 reader。不能把系统上限 C 直接代入上表当作本轮 M。

### 接入、固定本轮结果与失败处理

在现有 `prompts.py` 扩展纯组织函数，接入 `prompt_dispatch()`、`render_prompt()` 和检索独立派工入口。`maintain` 沿既有写回执流程保存本轮维护布局，随后渲染命令继承同一模式、预算和队号；子队不重新领取系统总额，配置中途变化不改写已开始的一轮。

`prompt_dispatch()` 保持无数据库访问，`render_prompt()` 保持纯读配置／回执／模板；布局计算不调用 LLM，也不新建队列、常驻调度器或重复缓存。宿主 AI 只机械提供已有额度、按返回清单设置参数及派工；T2 时长判断和材料语义分批仍由 AI 完成。

名额不足时停止新增派工，保留原错和未派槽位。取得可核的新额度后，脚本只缩减尚未启动的派工清单，不重命名已启动实例、不重新分配其授权，也不开第二轮 maintain 或 owner；实际未处理工作保持待办。维护和检索继续共享同一宿主容量来源，检索入口不带维护 receipt/control/owner。

## 五、项目配置维护要点文档与入口

实施时新增面向使用者及协助维护的 agent 的 `experiments/20261106-basepack/docs/project-config-maintenance.md`，记录维护 basePack 项目配置时的要点。具体盘点与当前机制见[配置维护依据](research/project-config-maintenance-20261112.md)，本轮先完成盘点和计划，不提前发布包含未实现 S2 字段的操作说明。

文档按变更事件组织，逐项交代配置来源／读取时机、会过时或不同步的原因、要联动的文件／服务／状态及最小确认：

- 并发上限快照为首要条目；修改宿主上限、切 profile／宿主及升级接入时重新采集，按实际影响范围同步项目配置。模型档位与宿主可用性变化也要核对，但明确模型映射每次读项目配置，并非安装时冻结。
- 覆盖 Python／机器配置／项目路径、生成入口、Codex 绑定及注册根、source_scope／Git ignore、独立 skills 副本或联接，以及数据库、凭据、共享 embedding／GPU预算、Condor和作业路径的联动。
- 明确三类机制：安装采集快照、每次直接读配置、生成副本或启动时加载／持久状态；不能把每项都当作快照。已有 Codex 注册清单每次维护刷新，不新增一套配置扫描来替代它。
- 既有 `memory init` 只刷新托管块，instructions 块外的旧首段路径仍需核对；保持块外正文保护。改 data_dir 不自动迁库，改密码文件不轮换账户，服务设置要按其实际加载时机生效；向量是否补建依据实际 identity，详情链接各自现有说明。
- 只核对受影响项目与功能，不新增每对话全量配置核查、定时监视或自动审计。新字段按实际交付版本说明，模板仍是字段默认值维护源。

从 `setup-project.md` 的安装、版本升级与配置修改位置链接新文档；在生成的 instructions 中增加“维护本项目 basePack 配置时先读该说明”的条件入口，并为相关资源／管理员说明增加适当回链。生成入口使用已交付文档地址，不硬编码本机开发路径或假设使用者有源码检出。AGENTS 不复制整份清单，普通业务无需为此多读文档。新文档链接只在实际交付文件时加入产品入口。

## 已定方案与实施顺序

用户已定 **T2 + N2 + S2** 及上述命名，实施授权尚未给出。后续实施顺序：

1. 验证宿主并发配置、层级、名称和句柄复用边界；扩展安装／接入以采集容量，ProjectConfig 统一解析并展示快照，补齐已有项目配置。
2. 在现有 prompt 路径加入纯组织函数，按 S2 生成和固定本轮布局；在 AGENTS 与详细入口模板加入 T2 时长判断，随包 memory skill 承接详情。直接 maintain 命令不增加程序“猜时长”或强制计时拦截，显式维护仍可直接使用。
3. 扩展既有派工元数据，区分自动单队与手动多队、总协调与阅读协调的英文提示词及发布权限，使名称由同一来源生成、在实际创建时使用。明确零 reader 时 coord 亲自执行完整阅读与发布流程，低并发不强制派满 reader；保留默认 tier2 协调、独立 reader 默认 tier1 和第 0 队统一发布职责。增加检索 worker 独立派工／渲染入口，采用 `bp_mem_search_s` 固定槽位名与检索档位，不带维护所有权合同。
4. 交付项目配置维护要点文档及条件阅读入口，补齐并发快照与本次盘点的联动事项；更新实际行为说明并复用既有入口刷新与 prompt 测试。通过下列场景后构建普通 wheel，按原 UUID、凭据和知识保留合同升级目标项目；刷新前先收尾旧版本维护，其它项目是否升级单独记录。

当前部署没有应用这些步骤。本轮仅形成计划与进度入口，项目纲领保持原文。

## 验收与边界

| 场景 | 要看到的行为 |
| --- | --- |
| 简短问答、查询 PID 等直觉短任务 | brief 保留，整个 maintain 未启动，没有该轮 owner 或维护 worker |
| 明显超过十分钟的改动 | 启动时只开一轮全项目维护，业务与维护并行 |
| 短任务后来新增较多排错或验证工作 | T2 在自然范围变化时重新判断，可首次启动；不等待计时达到门槛 |
| 用户直接要求维护记忆 | 不因估计很短而跳过，仍按授权范围交付 |
| 自动维护创建与多批接续 | 仅有第 0 队，名称为 coord_0 及 read_00 至 read_03 的完整 bp_mem 名称；reader 沿句柄接批，不因空闲席位增加第 1 队 |
| 手动维护多队 | 依实际配置和空闲预算增加队，read 第一位与 coord 队号一致；coord、reader 和其它占用均计入上限，末队可不足四名 reader |
| 低并发单 coord | 自动与手动维护分别验证 M 为 1、2、3；只创建 coord_0，无 reader，实际完成阅读、生成与发布，名称和 tier2 档位保持 |
| S2 安装、刷新与纯计算 | 容量口径正确，未知值不猜；新旧项目配置可补齐，换宿主／profile 后显式刷新，保留 UUID／凭据／知识；生成 prompt 不连库、不读凭据或调用 LLM |
| S2 预算与配置上限 | 验证 0、1 至 6、10、13、20、30 及 C=4/A=4 的自动／手动差异；A 缺失明确标为组织上限，检索等占用不被重复使用 |
| S2 运行中容量不足 | 停止新增派工，只缩减未启动清单；已启动名称和授权保持，未接受材料继续待办，无盲重试或第二个 owner |
| 配置维护说明与阅读入口 | 安装／升级／维护配置时能找到新文档；普通业务不加载全清单；未交付字段不会被写成现有功能 |
| 修改宿主并发上限 | 按说明重新取值、归一化并同步受影响项目，config show 显示新快照；不为核数字启动完整维护，新一轮规划使用新值，已启动布局不被改写 |
| 其它配置联动边界 | 用路径迁移、模型映射与服务参数代表性场景核说明；保留 instructions 块外内容，明确实际读取／刷新时机，不把配置编辑等同迁库／轮换／重编码 |
| 多队提交与容量不足 | 共用一个 owner/control/receipt，仅第 0 队发布；验证 M 为 0、剩余一席及末队不满的行为，不超额派工、不伪称完成 |
| 同一父 agent 的下一轮维护 | 验证同名复用，control 更新，不复用他人实例、旧任意名称或旧发布状态 |
| 检索命名与完整委托 | 实际使用 bp_mem_search_0，模型／推理强度来自检索配置；同一问题多轮 search/read/评分/rank 保持同一 worker，不自由改名 |
| 并发与连续独立检索 | 并发独立任务使用脚本给定的不同检索槽位，计入共同容量；同名复用与干净历史符合宿主实际能力，无无关上下文串入 |
| 短任务与零空闲席位检索 | T2 跳过维护仍可检索；零席位由主 agent 执行且如实报告，正常／受限路径都不取得维护 owner、不启动维护协调者 |
| 业务结束与启动失败 | 只停止自有维护，确认发布后释放；真实失败在业务答复中说明 |

验证聚焦行为与已有 prompt 的无副作用合同，不以文案包含某字符串代替宿主实际派工，不要求真实等待十分钟，也不建立新的统计或计时框架。

短任务连续出现时，记忆可能积压到下一次长任务或显式维护；这是减少启动成本的直接取舍。本轮不另加定时维护、累计任务计数或自动审计来抵消它，也不宣称十分钟阈值已由性能对照证明最优。
