## SQL 413 的事实与解释

1. 这次 413 证明一份发给 SurrealDB 的 HTTP /sql 请求体被长度限制拒绝；**不证明 SQL 语法、知识内容或版本条件错误，也不证明它们全部正确**。请求体在 SQL 处理前受容量限制，不能由一次 413 推断“错误内容被拦截”。
2. SurrealDB [官方 HTTP 文档](https://surrealdb.com/docs/reference/rest-api/http-protocol#request-size-limits)列出 /sql 默认 1 MiB，即 1,048,576 字节，自托管可用服务进程环境变量 SURREAL_HTTP_MAX_SQL_BODY_SIZE 调整。实测请求为 1,292,144 字节。这个默认值属于上游数据库服务端的容量配置；本项目启动脚本 .basepack/memory/serve.ps1 与[部署示例](../../../experiments/20261106-basepack/docs/administrator.md)没有显式设置它。正在运行进程的继承环境尚未核实，不能把官方默认值当作已读到的实例有效配置。
3. 官方当前 main 的[配置代码](https://github.com/surrealdb/surrealdb/blob/main/surrealdb/server/src/cnf/mod.rs#L38-L40)给出默认值；[/sql 路由](https://github.com/surrealdb/surrealdb/blob/main/surrealdb/server/src/ntw/sql.rs#L24-L55)挂载请求体长度限制，之后才转换正文并执行查询。这是机制佐证，不是对本机 4.0.0 标签源码的逐字核验。
4. 即使正文完全正确，大请求仍需要接收、缓存、解析和执行资源。为这些成本设置上界，是请求体限额的合理工程解释；官方文档说明不同接口按工作类型采用不同限额，但本次没有找到“恰好选 1 MiB”的原始设计讨论，不能代上游维护者编造该数字的特定理由。通用服务默认值也不自动等于本项目合适的容量。
5. **可以考虑调高容量。** 本轮没有决定维持 1 MiB、取消限制或调到某个新数值；也没有决定必须让 AI 手工拆批。应核实际部署与合法批次，再选择合适方案。
6. SQL 构造、发送与 413 拒绝均由程序处理，没有 AI agent 在该 HTTP 环节判断“放行还是拦截”。本次机械维护直接由预检程序构造；语义维护的内容可能先由 agent 阅读产出，之后也走同一发布函数。embedding 是另一个服务：待编码输入分批，兼容向量可复用，但最后 SQL 仍可能一次携带整批向量。

## AGENTS 块的实施设计

复用现有 basepack:start / basepack:end 标记，只更新这一托管块，保留块外业务指令。本仓库当前块有自身 README/接入/恢复指针，迁移前核对并保留仍必要的项目入口。

拟直接显露以下动作；这是依据已定方向编写的文案草案，详细措辞在实施时与唯一详规同步：

| 触发条件 | AGENTS 中的简明指令 | 详细链接的职责 |
| --- | --- | --- |
| 开始或接续项目任务 | 先读取本机 Python/配置；记忆已启用时运行 brief，保留 mandatory，待核内容回源确认 | 本机入口与启动说明 |
| 记忆已启用且宿主具备可取消子任务能力 | 预先分配唯一 control，业务开始即默认异步运行全项目 maintain，业务不等预检 | 自动维护的执行、范围与 Codex 采集 |
| needs_semantic=true | 按 worker 返回的模型/推理强度实际派协调者，持续接批；一次 reader 或一批完成只表示进展 | 派工、英文模板及发布验证 |
| 普通业务任务结束 | 先 stop 同一 control，再取消维护协调者及全部后代 | 停止与提交仲裁 |
| 用户显式要求维护 | 将维护本身纳入交付，按授权范围处置候选或报告实际阻塞，不自行以剩余数量或优先小批结案 | 显式维护与完成条件 |
| 检索、AI 派工或资源工具被需要 | 按项目配置解析相应档位，进入对应检索/资源工作流 | 按需的模型映射、检索和资源说明 |

每条指令直接附详细链接。链接首先使用项目内稳定的 .basepack/instructions.md 及相应章节，再由本机入口定位随包 skill/角色提示及产品文档；实施时同步生成目标章节并验证锚点。新检出尚无本机入口时，AGENTS 块须提供可达的安装/接入文档链接。具体 prepare/apply 字段、凭据读取、Codex 归属、并发版本检查和错误原文保留在详细流程，AGENTS 不展开这些字段。

普通 init 尚未启用记忆时只呈现适用指令或明确启用条件，不能要求未建库项目直接连接数据库；启用记忆后再刷新相应指令。

## 生成、升级与维护源

当前[project/init.py](../../../experiments/20261106-basepack/src/basepack/project/init.py)的 _write_project_entry 同时改 AGENTS、整份 instructions 和忽略规则；普通 init 遇既有配置/入口会拒绝重跑。[memory/cli.py](../../../experiments/20261106-basepack/src/basepack/memory/cli.py)的 _activate 目前只刷新 instructions 的 memory 块，**不会刷新已有项目的 AGENTS**。因此不能只改模板，也不能调用现有整份写入函数覆盖用户本机说明。

实施安排：

1. 将 AGENTS 托管块的生成/更新收敛为一个可复用的维护入口，普通 init 与记忆启用/入口刷新共同使用。只处理本任务需要的托管块，不扩成安装编排平台。
2. 在[agents-snippet 模板](../../../experiments/20261106-basepack/src/basepack/project/templates/agents-snippet.md)维护通用短指令；[instructions 模板](../../../experiments/20261106-basepack/src/basepack/project/templates/instructions.md)和记忆激活生成段提供真实本机参数及直接详情链接。
3. 让已有启用项目能用明确的入口刷新步骤取得新块；选择最小现有命令接入点，并在安装/升级说明中写清。刷新不得重置配置、凭据、项目 UUID、数据库或用户在托管块外的内容。
4. 同步[memory skill](../../../experiments/20261106-basepack/src/basepack/memory/SKILL.md)、[协调者模板](../../../experiments/20261106-basepack/src/basepack/memory/prompts/coordinator.md)及[用户记忆文档](../../../experiments/20261106-basepack/docs/memory.md)的背景/显式维护完成边界，清理本次涉及的重复与矛盾规则；reader 的详细内容仍由其角色模板维护。
5. 最后迁移本项目 AGENTS 托管块，并更新部署、接入和维护文档中的旧“仅短指针”描述。系统说明只在实现落地后改成已实现状态。

## SQL 容量问题：待选方案

2026-11-11 补充[限额调查与隔离实测](research/sql-request-size-limit.md)：建议本机显式采用有限 32 MiB（33,554,432 字节），不取消上限；这是待用户采纳的建议，不是已经实施的决定。显式 32 MiB 配置下 31.9376 MiB 合成向量事务成功，2.671 秒、服务器私有内存采样峰值约 979 MiB。2×约 16 MiB 并发出现独立事务写冲突，因此未通过并发稳定性验收；真实磁盘、大型历史库及长期运行未测。0 代表拒绝非空 body，不代表无限。完整依据、失败和建议条件见调查。

用户已提出**由程序自动分包、调用 AI agent 无感**的要求；具体事务连接实现与容量数值尚未选定，该选择不阻碍先实施已确定的 AGENTS 入口调整。后续应：

- 核实目标 SurrealDB 发行版、启动环境和有效容量设置，保存不含凭据的依据。
- 用已确认内容与依赖的隔离样例复现大请求，记录正文/向量/快照等体积；原 1,292,144 字节请求未完整捕获，事后 environment.md 30-chunk 探针不能当作原始 SQL。
- 比较满足当前需求的最小方案：适当调高服务端上限；或在保持每批版本/依据一致和原子性的前提下调整发布分组；必要时再评估数据库已有的更大消息接口。不预先叠加所有方案或新增独立客户端小上限。
- 方案确定后按所选服务端配置或程序发布方式实施，不要求 AI 在每次 SQL 写入前审核请求大小、猜测正文正确性或承担例行拆批。可恢复错误由具备相应处理办法的一层处理，其他错误继续保留原错。
- 明确预检遇到采集或机械提交故障时的交接状态，区分已提交、失败和仍可安全接续的范围；不把失败当 needs_semantic=false，也不无条件吞错继续。

### 调用方无感的自动分包

调用方仍只执行一次 memory apply 或同一 Python 方法，提交同样的知识批次；客户端负责消息大小、分组、发送与最终结果，不增加 AI 调用轮次，不要求 agent 选择包大小或例行拆 SQL。最初的人工拆批只是故障恢复方式，不是目标产品流程。

- 保留一次逻辑 apply 的原子发布：先开启一笔事务，分多次发送，全部语句及版本检查通过后统一提交；中途失败取消整笔事务，保留原错。不能把一笔原子批次默默改成多笔各自提交，否则会出现部分成功、部分失败。
- 目前 basePack 使用 HTTP /sql。SurrealDB 4.0.0 的普通 /sql 事务不跨 HTTP 请求；[HTTP RPC 实现](https://github.com/surrealdb/surrealdb/blob/v4.0.0/surrealdb/server/src/rpc/http.rs#L947-L975)也不支持交互式 begin/commit/cancel，attach 不能替代事务句柄。不能直接截开现有 SQL 后逐包 HTTP 发送。
- 优先评估数据库原生 WebSocket RPC 事务或相应 SDK：[Python 事务文档](https://surrealdb.com/docs/reference/python/api/core/surreal-transaction)要求 WebSocket；[4.0.0 WebSocket 实现](https://github.com/surrealdb/surrealdb/blob/v4.0.0/surrealdb/server/src/rpc/websocket.rs#L1522-L1720)支持同一事务 ID 下多次 query 后 commit/cancel。先做隔离验证再确定依赖与发布路径，不增加自建数据库或多后端平台。
- 分包按序列化后的实际消息字节数与完整语句/参数边界处理，保留顺序、依据及版本检查；不是简单按字符、成员个数或网络帧切割。同一个 HTTP 请求的流式分段仍受整份 body 上限约束。
- 单条 source_version 写入可能包含整个原文快照，若单条操作本身超出消息上限，仅分组仍不够；后续需验证数据库原生的分片赋值/数据写入方式，或明确容量错误，不擅自改变 chunk 语义与原文。分包也不消除整笔事务的总内存成本。
- 沿用同一任务 control 和停止/提交仲裁；断连或提交响应丢失时核实结果，不能盲目重放可能已提交的批次。正常成功路径对 agent 透明，真正无法处理的错误仍明确返回。

验收增加：调用方一次调用实际发送多个消息；中间包故障、版本冲突或 stop 时不留下半批可见知识；成功时内容和向量共同可见；单条超限、断连与提交结果不确定分别有明确处理。此前 32 MiB 仅是服务端候选容量，不替代自动分包目标，也不证明上述事务方案已实现。

数据库配置调整、服务重启、接口改变及自动分包均未在本轮实施；原生事务连接与细节仍待验证，不把候选写成已完成修复。

## 验收与交付

入口修改实施后，使用现有项目/CLI 回归而非另建测试框架，覆盖：

- 新项目未启用记忆、启用记忆、已有项目升级刷新；重复刷新幂等，托管块外字节保留，损坏标记明确报错。
- AGENTS 每条关键指令有可达的详情链接；路径含空格/中文和重定位后仍按本项目实际参数执行，分发模板没有作者机器绝对路径。
- 真实普通新任务未收到“请维护”的额外提醒，也实际启动预检并按需派出维护分支，业务并行推进；结束时按 control 停止并取消后代。验实际行为，不只检查生成文字。
- 显式维护对固定候选与授权范围逐项验收，或给出具体阻塞及余项；未核完不能靠“先做一批”或“剩到某数”结案，不追赶当前聊天无限追加。
- SQL 方案确定后另验合法大批实际写入、版本冲突和失败原子性；embedding 分批不当作 SQL 容量验收。服务端配置变化及部署步骤据实记录。
