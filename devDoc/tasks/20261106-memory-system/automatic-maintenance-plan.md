## SQL 413 的事实与解释

1. 这次 413 证明一份发给 SurrealDB 的 HTTP /sql 请求体被长度限制拒绝；**不证明 SQL 语法、知识内容或版本条件错误，也不证明它们全部正确**。请求体在 SQL 处理前受容量限制，不能由一次 413 推断“错误内容被拦截”。
2. SurrealDB [官方 HTTP 文档](https://surrealdb.com/docs/reference/rest-api/http-protocol#request-size-limits)列出 /sql 默认 1 MiB，即 1,048,576 字节，自托管可用服务进程环境变量 SURREAL_HTTP_MAX_SQL_BODY_SIZE 调整。实测请求为 1,292,144 字节。这个默认值属于上游数据库服务端的容量配置；本项目启动脚本 .basepack/memory/serve.ps1 与[部署示例](../../../experiments/20261106-basepack/docs/administrator.md)没有显式设置它。正在运行进程的继承环境尚未核实，不能把官方默认值当作已读到的实例有效配置。
3. 后续[限额调查](research/sql-request-size-limit.md)已核官方 v4.0.0 的[配置代码](https://github.com/surrealdb/surrealdb/blob/v4.0.0/surrealdb/server/src/cnf/mod.rs#L28-L30)和[/sql 路由](https://github.com/surrealdb/surrealdb/blob/v4.0.0/surrealdb/server/src/ntw/sql.rs#L30-L81)：路由挂载请求体长度限制后才执行 SQL。标签源码已核，不再列为待重新调查；运行进程的有效配置和本机二进制构建身份与上游源码仍应区分。
4. 即使正文完全正确，大请求仍需要接收、缓存、解析和执行资源。为这些成本设置上界，是请求体限额的合理工程解释；官方文档说明不同接口按工作类型采用不同限额，但本次没有找到“恰好选 1 MiB”的原始设计讨论，不能代上游维护者编造该数字的特定理由。通用服务默认值也不自动等于本项目合适的容量。
5. **可以考虑调高容量。** 本轮没有决定维持 1 MiB、取消限制或调到某个新数值；也没有决定必须让 AI 手工拆批。应核实际部署与合法批次，再选择合适方案。
6. SQL 构造、发送与 413 拒绝均由程序处理，没有 AI agent 在该 HTTP 环节判断“放行还是拦截”。本次机械维护直接由预检程序构造；语义维护的内容可能先由 agent 阅读产出，之后也走同一发布函数。embedding 是另一个服务：待编码输入分批，兼容向量可复用，但最后 SQL 仍可能一次携带整批向量。

## AGENTS 块的实施设计

复用现有 basepack:start / basepack:end 标记，只更新这一托管块，保留块外业务指令。本仓库当前块有自身 README/接入/恢复指针，迁移前核对并保留仍必要的项目入口。

拟直接显露以下动作；这是依据已定方向编写的文案草案，详细措辞在实施时与唯一详规同步：

| 触发条件 | AGENTS 中的简明指令 | 详细链接的职责 |
| --- | --- | --- |
| 开始或接续项目任务 | 先读取本机 Python/配置；记忆已启用时运行 brief，保留 mandatory，待核内容回源确认 | 本机入口与启动说明 |
| 记忆已启用，宿主有任务开始/完成事件及可取消子任务能力 | 先取得项目维护所有权，分配唯一 control，异步运行全项目 maintain；未取得者继续业务 | 自动维护、项目锁与 Codex 采集 |
| 本 thread 持有维护且 needs_semantic=true | 按 worker 返回的模型/推理强度实际派协调者，持续接批；有效 B/F 处置也纳入完成口径 | 派工、英文模板及发布验证 |
| 持有维护的普通业务任务结束 | stop 自有 control，再取消自有协调者及后代；确认发布状态后按 G 释放所有权 | 停止、结果核实与项目锁释放 |
| 用户显式要求维护 | 将维护本身纳入交付，按授权范围处置候选或报告实际阻塞，不自行以剩余数量或优先小批结案 | 显式维护与完成条件 |
| 检索worker或调用agent在使用中发现问题 | 轻量记录疑点与观察版本，交未来维护；不要求当场完成审计，不直接改知识 | 问题报告与修复闭环 |
| 用户明确要求记忆系统审计 | 按该次意图和范围启动手动审计；讨论“审计”或普通维护不触发 | 手动审计入口 |
| 检索、AI 派工或资源工具被需要 | 按项目配置解析相应档位，进入对应检索/资源工作流 | 按需的模型映射、检索和资源说明 |

每条指令直接附详细链接。链接首先使用项目内稳定的 .basepack/instructions.md 及相应章节，再由本机入口定位随包 skill/角色提示及产品文档；实施时同步生成目标章节并验证锚点。新检出尚无本机入口时，AGENTS 块须提供可达的安装/接入文档链接。具体 prepare/apply 字段、凭据读取、Codex 归属、并发版本检查和错误原文保留在详细流程，AGENTS 不展开这些字段。

普通 init 尚未启用记忆时只呈现适用指令或明确启用条件，不能要求未建库项目直接连接数据库；启用记忆后再刷新相应指令。

## 生成、升级与维护源

当前[project/init.py](../../../experiments/20261106-basepack/src/basepack/project/init.py)的 _write_project_entry 同时改 AGENTS、整份 instructions 和忽略规则；普通 init 遇既有配置/入口会拒绝重跑。[memory/cli.py](../../../experiments/20261106-basepack/src/basepack/memory/cli.py)的 _activate 目前只刷新 instructions 的 memory 块，**不会刷新已有项目的 AGENTS**。因此不能只改模板，也不能调用现有整份写入函数覆盖用户本机说明。

本节旧路线链接用于定位基线机制；本轮代码、模板、依赖和回归的实际改动落在新 experiment 的对应文件。候选入口建立后，先准备可独立复现的试验包，再执行以下修改。

实施安排：

1. 在新实验固定导入所需基线代码、依赖声明及测试，建立独立环境与运行入口；检查实际导入路径，避免测试误用旧路线或正式安装。
2. 提取复用 _write_project_entry 已有的 AGENTS 托管块替换逻辑，使普通 init 和已有 memory init 刷新路径共用；不从零重建块替换，也不复用会覆盖整份 instructions 的写入。成功刷新时保留块外原字节仍需补验证，不能将既有文本级测试当成证明。
3. 在候选的 agents-snippet 模板维护通用短指令；instructions 模板和记忆激活生成段提供真实本机参数及直接详情链接，基线对应模板见[agents-snippet](../../../experiments/20261106-basepack/src/basepack/project/templates/agents-snippet.md)和[instructions](../../../experiments/20261106-basepack/src/basepack/project/templates/instructions.md)。
4. 将 AGENTS 刷新接到现有升级步骤 memory init：它已核 schema/项目 UUID 后执行 _activate，目前只刷新 instructions 的 memory 块。保留这个已部署入口及其数据库可用条件，不另造 force-init 或称为离线刷新；同步说明不得重置配置、凭据、UUID、已有知识或块外内容。
5. 同步memory skill、coordinator/reader及检索流程：删除普通批次事后语义复核、例行search/read/neighbors验收门槛和自动独立审计；保留作者理解/生成、问题记录、显式维护范围及单独的手动审计说明。

## 程序写入检查：优先保留已有、补齐缺口

以下按0.9.1实际代码区分。机械保护应由CLI/Python共用的写入路径在发布前或事务中执行；AI提供内容选择与依据ID，不手工计算哈希、比对版本或逐项重验这些等式。

| 类别 | 已有程序检查 | 本轮处理 |
| --- | --- | --- |
| 来源 | 批次原件revision、删除条件及source版本，编码后提交前再核原件 | 沿用；文件系统不与数据库组成同一原子域，不承诺冻结所有原件 |
| 版本 | 事务内检查实际写入/退役/更正目标、所用依据和边端点的expected | 沿用；不锁无关全库。父引用的相关依赖保护在下述补缺中落实 |
| 原文范围 | 范围有效、chunk从原文提取、显式文字严格一致，部分file范围要求标缺口 | 沿用；程序不判断分块含义、摘要概括是否合理 |
| 依据与结构 | node/edge有依据，旧依据核stale/affected与来源或原范围散列，basis保存版本/定位，边端点有原生约束 | 高优先补非空parent能解析为预期member及相关并发/批内引用检查；不把引用存在当成语义支持 |
| 向量 | 输入版本和模型identity匹配才复用，否则编码；核返回identity/数量并与知识同事务发布 | 沿用；不要求AI逐条验证向量或保证任意查询命中 |
| 事务、错误与停止 | 原子提交，SQL非OK/HTTP错误抛出；control仲裁stop和提交入场 | 沿用并覆盖SQL分包新路径；已获准不等于已完成，结果不明不得盲重放 |

父引用是已核的实现边界：当前apply主要保存ID，尚未证明会产生线上坏数据。候选用对应回归覆盖缺父项、本批新父项、既有父项及并发变化、失败不半发布；保留合法chunk直接挂file，不额外强加同源、固定三级、范围包含或全图无环等未定规则。

退役/错误知识的正常路径已通过stale、受影响依据和既有退役流程处理；不要把它写成完全没有程序保护。若最小真实回归证明确有直接apply状态准入缺口，再补相应条件，不因假想损坏增加层层防御。摘要/关系是否受原文支持属于作者生成时的理解，错误可进入使用反馈，不新增独立AI检查来冒充机械保证。

本节是重要实施项，但不是重写六类已有机制。源码/既有回归依据见[审阅调查](research/review-overhead-20261111.md)，本轮核对记录选留在artifacts；候选只为实际补缺保留必要回归，不新增校验平台或每批发布后的机械审计阶段。

## 成本策略 A、B、F

### A：普通增量、历史首建与专项审计分开

现有协调者已按固定回执中的来源/依赖分批，也未要求每次全库独立审计。A 的增量是把既有知识变化、历史首建、迁移和专项审计在回执/交付中分清，并约束实际执行不擅自扩展审计；沿用全项目发现与接批，不新建调度机制。

复用已有固定候选集和聊天采集截点；这不是所有项目文件同时冻结的版本快照。prepare 仍读当时原件，每批以该次 prepare 的版本核提交。回执之外的新增材料和当前聊天追加留后续运行；收尾不再启动新一轮采集来追赶自己。已选文件在途中变化按现有冲突处理，结果记录实际接受版本及余项，不声称统一接受了任务开始时的全项目版本。本轮不增加全项目原子版本截点。

**已采用的新方向：建立与普通维护在作者完成必要原文理解、生成批次并由程序提交后结束，不追加逐项语义复核、发布后例行回读/检索抽查、批量事后审计或独立审计。** 协调者不因职位重审reader已做的同一判断；协调者若自己生成跨reader新关系，仍须共读所需原件，这是首次生成。

检索也只做业务需要的检索、筛选、评分和原文阅读，不要求额外遍历所有命中及证据链来完成质量审计。检索worker或调用agent发现问题就报告，未来维护定位修复；不为问题自动再派审计者，也不审计每次修复。普通“维护记忆”不等于“审计记忆”。

显式维护仍按授权范围如实报告已处理/未解决事项，不自行以剩余数量结案；程序提交失败、冲突或结果不明不得声称已完成。该结果说明不是额外语义审计。代码修改、安装、恢复与迁移本身的必要开发测试仍执行，不把它变成日常每批知识的验收门槛。

[审阅调查](research/review-overhead-20261111.md)和[使用反馈评价](research/use-feedback-evaluation-20261111.md)保留历史证据；前一轮建议中的事后批量对账、例行访问验例和自动针对性独立复审，已由本节取代。当前安装模板仍是旧合同，候选实现和收敛后再切换。

### B：为已阅来源版本保留处置

零正文且无活动知识已能登记，无须重做。新增非空材料的“已阅，无新增知识”或“与已有知识重复”处置，记录版本、实际阅读范围、理由和已有表示定位（若有）。这是作者读过并处理，不表示另做审计；未变且处置仍适用时不重复首建，相关变化或明确手动审计可重访。

优先在现有来源/版本数据做最小扩展；“已阅处置”与表示深度分开，单一权威记录不等于一个互斥状态。部分阅读不得声明整源处理。同步候选判定、角色完成口径及写入；若扩展source_version，覆盖当前UPSERT CONTENT不丢字段。子聊天可判重复但保留原件和独有事实，不按角色整类排除。

### F：全项目粗层入口，精细知识渐进建设

已有file/section/chunk、全文快照及范围回读，当前不要求逐句分块/向量化。F复用这些能力，优先独有决定、约束、结论和问题线索，细化随真实变化、使用反馈或明确深维护推进。随机跨材料共读用于发现新关系，不变成默认核查旧知识的审计。

摘要仍由作者实际阅读的精选原文chunks支持，不必逐段拆块。fresh全范围file已计覆盖，coverage_gaps仍会重复入队；候选区分未读缺口、粗层已完成但待细化和B的有效已阅处置，调整入队/完成口径。不能抹去gaps伪造完整阅读，也不让待细化每轮重做；粗层不代表所有原文/关系已覆盖。

用户已选择这种深度取舍。优先复用现有成员/摘要/依据，必要的最小合同调整据实记录；不为粗层策略丢弃既有精细知识。重写已有 mandatory 成员时显式保留标记及原文信息，不能依赖 omitted 字段的默认 false。当前 prepare/reader 仍交付并共读新旧全文；F 可减少精细表示、建图及输出，但不预先承诺减少全文输入或整体耗时，效果通过对照判断。

### C：现有局部维护的边界

0.9.1 已用原始字节 revision 发现变化，以行差异/唯一锚点判断未变块，结合 parent、evidence/basis 和已有语义边处理已知依赖；符合条件的块和向量可复用。已有图和证据依赖解决“哪些已记录知识可能受影响”，不保证发现尚未建出的关系。prepare 仍可能交付整份新旧原文供 AI 判断摘要和关联。

因此不把“开始使用图判断相关性”列成新任务，也不承诺只读变化行即可完成语义维护。相关源码和反例见[局部维护核实](research/local-maintenance-20261111.md)。本轮不扩成新的语义影响分析或通用依赖调度平台。

## 使用反馈与手动审计

新增轻量持久问题入口，检索worker和调用检索的agent走同一接口；多个报告者可并发入队，不等于另开维护thread。程序尽量自动带上时间/报告者与观察版本，AI只需写疑点和可用依据，不必先写审计报告或完整修复方案。

- 有目标时保留member/node/edge ID及观察时知识版本或内容指纹、原文定位；search现不返回knowledge_revision，不能事后read到新版再假称是当时版本。
- 无命中ID的漏检也可报告查询和预期信息/来源线索；区分知识错误与检索/排序问题，不能一律改知识来迎合报告。
- 在项目记忆库保存最小待办及结果，不用tmp、不另造知识库/审计服务。当前rank不持久反馈，corrections会立即影响知识，不能直接拿来存未经判断的疑点。
- 未决报告必须进入下次回执、needs_semantic及实际派工，即使原件未变、pending为零；业务使用不等待修复，当前回答按需要避开已识别错误或说明缺口。
- 单维护owner按当前版本和原件判断并修复，复用已有apply/corrections留痕；旧报告不覆盖新版。修复、不成立、重复或不再适用写清结果；失败、未决和提交不明保持可见，不先派另一个worker审计报告/修复。
- 报告属于运行状态，随导出恢复保留，且不作为新业务原件自摄入。扩表或记录类型须验证旧七表备份与新增未决记录的恢复边界，避免清理丢失。

只有用户明确表达记忆系统审计意图时启动手动审计，例如“进行一次记忆系统审计”；按意图而非精确字符串触发，讨论该词或普通维护不触发。范围按该次要求确定，不无限追赶新增聊天；审计可产生同种问题记录，是否立即修复按用户要求，写入修复仍遵守维护所有权。没有自动“风险高就审计”的旁路。

## G：同项目单一维护 thread

现有 control 文件的短时锁只仲裁该任务 stop 与提交入场，不是项目全生命周期所有权。新增 G 在 maintain 预检前原子取得项目所有权；每个 thread 仍可 brief。最小记录包含项目身份、持有 thread、control 与运行标识，锁位置由本机入口定位，不能仅“读到不存在”后都启动维护。

- 取得锁的 thread 负责预检、协调者、reader 和停止收尾；锁覆盖机械维护和语义阶段。
- 其他 thread 看到真实持有者即跳过自身维护，继续业务并报告已有维护；不再派第二队团队，也不终止或接管别人正在做的维护。
- 其他thread仍可提交问题报告；只有处理报告并修改知识属于维护。手动审计若仅阅读/记录问题不占第二份维护所有权，需要写入修复时再取得owner。
- 用户显式要求维护但已有 owner 占用时，报告该持有者及阻塞/已知范围；不能把跳过自身维护当成显式任务完成。
- 结束时 stop 自有 control、取消自有协调者和后代。现有 stop 不撤销已获准提交，但“已获准”不等于已完成，取消宿主任务后 CLI/连接是否存活也不能先假定。候选须以可观察的执行/事务结果确认发布阶段已结束再释放所有权；无法核实则明确保留未决状态，不假报释放或盲目重放。业务答复不为此无限等待，最小退出/恢复办法先隔离验证，不新增永久后台服务。
- 非持有者不得解锁；异常遗留须核实持有者已结束后显式恢复，不以文件年龄或一次读取结果盲目抢占。错误保持可见。

当前没有实现此锁。前期不做多维护 thread 的细粒度分工、跨聊天共享草稿、引用计数调度或永久后台；未来确有需要再扩展。

## H：目录约定与计划清理

采用[项目本机数据目录约定](../../system/project-data-layout.md)：生产状态及恢复必要原件留 `.basepack`，一次性准备/批次/验证材料放根 tmp，选留原证放根 artifacts/runs；保留现有 store、assets、codex 等实际路径，避免为整理而迁库。候选生成器、角色提示及使用文档随后按同一规范调整。

反馈记录是持久运行状态，数据库内保存并纳入恢复集合；不可作为临时工作包清除，也不把报告再摄入成业务知识形成循环。

本机清理已做只读分类，实施步骤如下；本轮不执行这些删除或移动：

1. 复核配置实际 memory_dir/jobs_dir/password_file、source_scope 显式纳入、Git 清单、已登记/历史来源、活动维护及 launcher 引用。tmp/artifacts 可被显式纳入，候选源码/文档也是 Git 受管材料；不能仅按目录名判可删，也不能将未接受来源等同可重建垃圾。
2. 按用户决定清除 `.basepack/backups`、`.basepack/memory/backups` 和散落的历史备份导出；不将整套旧备份搬到另一个目录冒充清理，也不在清理前再复制一整套来抵消目标。未来仅按明确恢复需求生成与保留备份，不默认长期叠加多套。
3. 已结束的阅读包、batch、验证输出和杂乱试验目录按真实可重建性清理；coverage/onboarding 的独有原证先选留并修正引用。控制文件可能早于回执创建，apply/stop 共用，提交未明时不能清；采集收据可能承载附件身份。候选只有工作包可转 tmp，控制、仍在使用的回执和恢复必要出处须稳定保存，不能跟随每日临时清理丢失。
4. 保留配置、入口、原凭据、活动库含 WAL/vlog、launcher、实际运行日志/状态、受管聊天、附件及图片快照、必要来源身份；jobs 先按其运行与记录合同核实。不根据当前 source.path 清掉旧 source_version 或历史 basis 所需材料。
5. 核对清理前后大小与文件清单、配置/UUID/凭据未改、库仍可用、mandatory/检索及旧依据可读；分别报告空间减少与保留例外，不把空间减少当作 AI 提速。

本轮只建立规范、候选分类和计划引用，不移动生产目录，不删除旧恢复点，不重启正式服务。

## SQL 透明分包与配套容量

2026-11-11 补充[限额调查与隔离实测](research/sql-request-size-limit.md)：建议本机显式采用有限 32 MiB（33,554,432 字节），不取消上限；这是待用户采纳的建议，不是已经实施的决定。显式 32 MiB 配置下 31.9376 MiB 合成向量事务成功，2.671 秒、服务器私有内存采样峰值约 979 MiB。2×约 16 MiB 并发出现独立事务写冲突，因此未通过并发稳定性验收；真实磁盘、大型历史库及长期运行未测。0 代表拒绝非空 body，不代表无限。完整依据、失败和建议条件见调查。

用户已提出**由程序自动分包、调用 AI agent 无感**的要求；具体事务连接实现与容量数值尚未选定，该选择不阻碍先实施已确定的 AGENTS 入口调整。后续应：

- 核实目标 SurrealDB 发行版、启动环境和有效容量设置，保存不含凭据的依据。
- 用已确认内容与依赖的隔离样例复现大请求，记录正文/向量/快照等体积；原 1,292,144 字节请求未完整捕获，事后 environment.md 30-chunk 探针不能当作原始 SQL。
- 比较满足无感自动分包和整体原子发布的最小实现：数据库原生事务连接/SDK、完整操作的消息分组方式及相应服务端容量。单纯调高上限不能替代自动分包；此前 32 MiB 针对 HTTP /sql，仅为配套候选，不强制沿用到不同传输的消息配置。
- 方案确定后在候选程序中实现分包与事务发布，按所选传输核验或配置配套容量；不要求 AI 在每次写入前审核大小、猜测正文正确性或承担例行拆批。可恢复错误由具备相应处理办法的一层处理，其他错误继续保留原错。
- 明确预检遇到采集或机械提交故障时的交接状态，区分已提交、失败和仍可安全接续的范围；不把失败当 needs_semantic=false，也不无条件吞错继续。

### 调用方无感的自动分包

调用方仍只执行一次 memory apply 或同一 Python 方法，提交同样的知识批次；客户端负责消息大小、分组、发送与最终结果，不增加 AI 调用轮次，不要求 agent 选择包大小或例行拆 SQL。最初的人工拆批只是故障恢复方式，不是目标产品流程。

- 保留一次逻辑 apply 的原子发布：先开启一笔事务，分多次发送，全部语句及版本检查通过后统一提交；中途失败取消整笔事务，保留原错。不能把一笔原子批次默默改成多笔各自提交，否则会出现部分成功、部分失败。
- 目前 basePack 使用 HTTP /sql。SurrealDB 4.0.0 的普通 /sql 事务不跨 HTTP 请求；[HTTP RPC 实现](https://github.com/surrealdb/surrealdb/blob/v4.0.0/surrealdb/server/src/rpc/http.rs#L947-L975)也不支持交互式 begin/commit/cancel，attach 不能替代事务句柄。不能直接截开现有 SQL 后逐包 HTTP 发送。
- 优先评估数据库原生 WebSocket RPC 事务或相应 SDK：[Python 事务文档](https://surrealdb.com/docs/reference/python/api/core/surreal-transaction)要求 WebSocket；[4.0.0 WebSocket 实现](https://github.com/surrealdb/surrealdb/blob/v4.0.0/surrealdb/server/src/rpc/websocket.rs#L1522-L1720)支持同一事务 ID 下多次 query 后 commit/cancel。先做隔离验证再确定依赖与发布路径，不增加自建数据库或多后端平台。
- 分包按序列化后的实际消息字节数与完整语句/参数边界处理，保留顺序、依据及版本检查；不是简单按字符、成员个数或网络帧切割。同一个 HTTP 请求的流式分段仍受整份 body 上限约束。
- 单条 source_version 写入可能包含整个原文快照，若单条操作本身超出消息上限，仅分组仍不够；后续需验证数据库原生的分片赋值/数据写入方式，或明确容量错误，不擅自改变 chunk 语义与原文。分包也不消除整笔事务的总内存成本。
- 沿用同一任务 control 和停止/提交仲裁；断连或提交响应丢失时核实结果，不能盲目重放可能已提交的批次。正常成功路径对 agent 透明，真正无法处理的错误仍明确返回。

验收增加：调用方一次调用实际发送多个消息；中间包故障、版本冲突或 stop 时不留下半批可见知识；成功时内容和向量共同可见；单条超限、断连与提交结果不确定分别有明确处理。此前 32 MiB 仅是服务端候选容量，不替代自动分包目标，也不证明上述事务方案已实现。

数据库配置调整、服务重启、接口改变及自动分包均未在本轮实施；原生事务连接与细节仍待验证，不把候选写成已完成修复。

## 验收与交付

以下为候选实现的开发验收，不是日常每批知识的审计门槛。覆盖机械补缺、入口、SQL分包、默认无审计、反馈/手动审计、B/F、项目互斥与目录治理。D/E不纳入，C不重复实现；不为批准新策略先全库审计，也不在测量前宣称已解决长耗时。

入口修改实施后，在候选独立环境及隔离项目中复用基线项目/CLI 回归，覆盖：

- 新项目未启用记忆、启用记忆、已有项目升级刷新；重复刷新幂等，托管块外字节保留，损坏标记明确报错。
- 保留已有来源/expected/范围/依据/向量/事务相关回归；为真实父引用补缺增加最小失败与成功用例，确认由共用程序入口拒绝错误而不要求AI另审，失败不半发布。
- AGENTS 每条关键指令有可达的详情链接；路径含空格/中文和重定位后仍按本项目实际参数执行，分发模板没有作者机器绝对路径。
- 无 owner 的真实普通新任务未收到额外提醒也实际取得所有权、启动预检及按需派工；已有 owner 时不重复启动，业务继续。持有者结束按 control 停止和取消后代，验实际行为而非只查生成文字。
- 在开发样例中确认显式维护能如实报告授权范围内的处置、阻塞和余项，不凭剩余数量结案；普通批次不以另做逐项语义复核/审计才能结束。
- SQL 方案确定后另验合法大批实际写入、版本冲突和失败原子性；embedding 分批不当作 SQL 容量验收。服务端配置变化及部署步骤据实记录。
- A：建立、自动/普通维护及修复没有追加独立语义复核、例行回读/抽查或事后逐项对账门槛；作者生成和机械保护继续，实际问题不自动升级审计。沿用固定候选/聊天截点和每批prepare版本，不误称全项目冻结。
- 反馈：检索worker与调用agent均能并发报告，有目标/无ID漏检均可；原件未变且无其他候选时仍能触发维护。旧报告不覆盖新版，未解决/冲突不被假关闭，修复留痕且导出恢复后未决记录仍在，不会自摄入。
- 手动审计：明确的自然语言审计意图能启动所需范围；引用/讨论该词、普通维护与实际问题报告都不会误触发。审计需要写入修复时仍取维护owner。
- B：同一已阅版本再次维护不重复首建，部分范围不冒充全源处理；内容或必要依赖变化会重评，子聊天独有事实能保留。
- F：用现有摘要+精选原文依据完成粗层闭环，未读缺口与待细化区分，未变材料不因可延期细化反复入队；已有 mandatory 标记/原文保持。比较独有事实、跨源/主动发现质量与实际 AI 输入、输出及轮次，不只统计层级数。
- G：两个 thread 同时尝试只有一个取得锁，未取得者继续业务；正常 stop/释放仅由 owner 执行，异常恢复须另核旧 owner 与发布状态。覆盖预检故障、宿主取消和已准提交未返回，不把 control 的 S 标记当事务完成。
- H：新候选不再向生产目录散写一次性工作文件；清理只按清单执行，旧依据与必要原件保持，释放字节据实报告。
