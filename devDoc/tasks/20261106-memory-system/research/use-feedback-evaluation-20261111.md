# 默认不审计、使用反馈修复的设想评价

2026-11-11（北京时间）。本文保留用户提出“建立/自动维护不审计、使用反馈修复、仅显式手动审计”时的评价依据。后续用户已要求据此更新[维护计划](../automatic-maintenance-plan.md)，方向已正式纳入候选；0.9.1产品与模板仍未切换。评价阶段只读核查、运行brief，没有启动维护/审计或修改知识。

## 判断与正常流程

支持作为新实验可选的默认方向。它符合[项目纲领](../../../project-charter.md)中审核可以默认省略、图检索可作为审阅过程，以及低建库/维护成本的目标。用户已明确接受较低可靠性，不应以自动增设独立复审作为采用条件。

建议将默认流程明确为：作者正常理解材料并产出知识 → 程序按数据合同提交 → 本批结束；不再追加逐项AI语义复核、发布后例行回读/检索抽查、独立审计或多轮语义验收。生成关系者仍需理解两端和依据，版本、原文范围、向量匹配、原子事务、错误和停止边界继续作为写入合同；不能把原来整套事后审计改名后偷偷保留。软件实现、安装/迁移本身的必要开发验证与日常知识批次审计分开。

使用过程中：

1. 检索worker按实际问题检索、筛选和阅读，发现疑似错误、矛盾、过期、依据缺口或漏检时顺手记录。没有发现问题时不要求逐项验全部命中、整条依据链或加派审计者。
2. 调用检索的agent若发现worker漏掉的问题，也走同一报告入口；不要求调用者重复worker的全部检索工作。
3. 当前答复避免依赖已经识别的错误，可按任务需要找原文、其他命中或说明缺口；报告不阻塞业务去等完整修复。
4. 未来唯一维护owner读取未决报告，结合当前版本和原文作修复或说明为何不成立/已过期；证据不足继续待处理。回源判断是修复本身，不再追加“审计这次修复”的另一组AI。
5. 只有用户明确表达记忆系统审计意图时，启动按其目标定范围的手动审计；自然语言无需精确匹配某一句，讨论或引用“审计”一词不触发。普通“维护记忆”不自动升级审计。手动审计可产生同种问题记录，是否立即修复按该次要求执行。

## 已有能力与实际缺口

| 项目 | 当前0.9.1与需要的增量 |
| --- | --- |
| 定位与回源 | 已有member/关系身份、来源版本、范围/图片定位及保存依据；能支持有目标的修复 |
| 修复及变更历史 | apply/corrections已有，但corrections会实际替换或标stale、影响依赖，是已决操作，不能拿它直接存未经核实的疑点 |
| 两级问题报告 | 没有统一持久待办入口；rank评分理由不持久化，也不是问题队列。需要让worker和调用agent均可轻量报告 |
| 精确定位当时结果 | search省略knowledge_revision；后来再read可能已是新版。候选应随结果保留观察版本或表示指纹，不凭同source_version认定摘要未变 |
| 触发未来维护 | needs_semantic只看来源/知识候选和待核关系，不读取报告。必须让未决报告进入下次回执/派工，即使原件未变、pending为零也能处理 |
| 默认审核行为 | coordinator/skill当前仍要求发布后查询核验，检索skill也要求较强的逐语义主张回源。采纳后须同步修改这些合同，避免把审计成本转嫁到每次检索 |
| 手动审计 | 宿主已有阅读/订阅agent与原件工具，可形成明确手动流程；不需要先建LLM API或为一句自然语言添加专门关键词解析器 |

最小闭环可在项目现有记忆库中保存问题记录，采用独立ID/原子写入；允许多个使用者报告，只有单个维护owner处理。报告行为不直接改写已发布知识，也不等于开第二个维护thread。原件未变而报告存在时应能派工，不能依赖“以后刚好有别的文件变化”。

报告由程序自动保存时间、报告者和可得版本信息；AI主要提供疑点和依据线索。若有目标，保存ID与观察时版本/内容指纹；没有命中ID的漏检也允许只给查询、预期信息/来源线索。不要强迫报告者先完成一份审计报告、寻找完所有证据或写修复方案。

处理结果保持简单：未决，或有理由的修复/不成立/重复/不再适用；失败、冲突和材料缺失不能直接记成已修复。旧报告遇到新版本时重新判断适用性，不照旧文本覆盖新版。弱worker的怀疑只作为线索，不立即删除知识或宣布新事实。复用既有变更留痕关联真正的修复，不另造一套知识库/常驻审计服务。

这些记录是持久项目状态，不能放可每日清除的tmp，不能作为新业务原件被自动摄入形成反馈循环。扩展现有表或增加最小记录类型时，需核未决报告的导出恢复；不能假定既有七表手工备份自动包含新增数据。

## 与当前计划的取舍

- **A要进一步改写。** 当前已排除默认全库独立审计，但仍建议按问题复核、发布后批量对照和代表性访问验例。新设想取消普通建立/维护的额外语义审计，不让问题自动触发独立审计；正常提交仍返回成功/失败并如实保留未决报告和变更留痕，不再以另做发布后逐项对账或抽查作为每批门槛。此前[审阅调查](review-overhead-20261111.md)是建议和证据，不是不可变要求。
- **B/F可继续。** B的“已审”应解释为作者实际读过并处置，宜用“已阅/已处理”避免误当独立审计。F的粗层/精细策略可由使用反馈驱动；随机跨材料共读用于首次发现新关系仍是建图工作，若转为检查旧知识正确性则属于审计，不默认另行追加。
- **G/H仍适用。** 问题记录可并发，维护修复遵守单owner。记录及必要出处持久保留，可重建工作包才清理；不为反馈再建杂乱文件目录。
- D草稿接续和E通用性能优化不因此恢复；来源发现、首建及知识更新也不被问题队列替代。

## 成本收益与接受的代价

它能直接删除额外语义判断、阅读与协调步骤，反馈又集中于真实使用中的问题，值得在候选中试验；但首次理解、分块、摘要、建边和真正修复仍有成本，不能推定两小时会缩成某个数字。

历史独立复核确实发现过超范围摘要与mock/实际混淆，因此尚无数据证明“生成过程已经足够可靠”。这不妨碍采用用户明确接受的低成本取舍；含义是同类错误可能先被使用，再被发现修复。

使用反馈的盲区也明确：弱worker和调用者可能同向误判；未召回的知识、冷材料和漏建关系可能没有被使用的机会；错误mandatory可在被发现前反复影响上下文。被发现的问题可以形成闭环，未被发现的问题没有自动修复保证。这些是该选择的代价，不据此再加一个默认后台审计。

候选最小验证聚焦闭环是否真实可用：两类报告者、漏检无ID、旧报告遇新版本、仅报告触发维护、未解决保留、明确手动审计与普通维护不混用。无需为批准“无例行审计”先跑全库审计，不建立额外可靠性平台。尚未执行候选流程或测定节省比例。
