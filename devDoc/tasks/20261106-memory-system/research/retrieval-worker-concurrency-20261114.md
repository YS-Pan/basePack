# 检索 worker 并发规则与近期使用调查

2026-11-14（北京时间）。检查基线为 main `b2267eb`、本项目客户端 0.14.0；近期案例保留各自当时的实现条件。本次只调查和记录，不修改派工策略、模型档位或产品代码。

## 规则与实现

现行规则明确默认“一次检索委托一名 worker”，同一问题由它完成多轮搜索、回源、评分和 rank；独立问题允许不同 slot 并行。前者约束委托的完整性，后者允许主 agent 拆分整个业务任务。依据是[派工计划第三节](../task-duration-and-worker-naming-plan.md#三检索-worker-的固定命名与脚本派工)、[随包检索合同](../../../../experiments/20261106-basepack/src/basepack/memory/SKILL.md#retrieve-in-one-delegation)。

[retrieval_dispatch](../../../../experiments/20261106-basepack/src/basepack/memory/prompts.py) 每次接收一个 request、返回一个 assignment；`slot=0` 为默认，容量不足时才改由主 agent 执行。它不分析业务问题并自动扩成多个 worker，容量上限也不意味着自动用满。检查时，源码与普通安装的 prompts.py、retrieval.md 分别哈希相同。因此常见的单 worker 既有明确默认的影响，也有主 agent 把业务问题合成一份委托的组织选择；不是全任务只能并发一名检索 worker。

历史讨论中，用户要求 brief 不包含检索、有检索需求时交检索 worker；把项目概况与任务检索合并到同一 worker，是助手为避免重复派发提出的建议，并非用户规定全业务只许一人，见[制定 basePack 使用整改计划](codex://threads/01a1ce4e-982e-7e21-9255-bc1449fe3ced)。后续[任务入口整改](../../../archive/20261112-usage-rectification/plan.md#b按任务启动按业务问题委托)要求跨历史发现实际交付原证和排名，减少重复启动、半成品交付与主 agent 接手；这不是检索人数最优的性能结论。

## 组织建议与证据限度

多个检索 worker 的价值来自互补问题和材料覆盖，而非人数本身。宽的项目状态任务可以让一路查未完成的用户要求及变更，另一路追实际交付与后续发布；主 agent 核当前代码、配置和远端，并综合冲突。每路保留完整检索闭环，避免按 search/read/rank 切碎一条证据链。若主 agent 或已有广读分支已经承担其中一部分，优先复用该分工。

本样本没有找到可以明确断言“应多派而未派，导致遗漏”的案例；上述宽任务拆成两路是值得采用的组织选择，不是已证明的因果修复。已观察到的更直接问题是窄问扩展过多、命令/身份转写错误、rank 后迟迟未 final、过早中断，以及后续历史决策漏触发检索。仅增加同题 worker 不能自动修复这些问题。

当前提示显著强调完整的一次委托，如何把宽任务拆成独立问题主要留给主 agent 判断。若后续调整，应在同一组织入口说明这一步，并保持单问题完整交付；本次没有把建议写成新强制规则。没有多 worker 与单 worker 的同题对照，也没有完整团队 token/费用，不能承诺更好召回或固定加速比。

本次主 agent 核实现及 file-structure 聊天，并补看相关记忆系统比较的最初一轮作为组织对照；两个并行审查 agent 分别回读另外三、四个核心聊天及子聊天，另有一个记忆检索 worker 回查规则历史。后台维护返回 acquired=false，已有私密隔离聊天持有 owner，未取得或释放他人所有权。分页定位及工具 ID 的一次性工作稿位于项目 tmp/retrieval-concurrency-20261114/；核心事实和可回读的聊天入口保留于本文。
