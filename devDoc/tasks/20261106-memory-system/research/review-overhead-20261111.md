# 发布后回读与审计：必要保证和重复边界

2026-11-11（北京时间）。按用户要求核查两小时维护中的发布后回读、逐项语义复核、独立审计。依据现行0.9.1代码/角色合同及既有审计账本；仅只读调查和文档记录，不执行新维护、全库审计或产品修改。本文细化[维护计划A](../automatic-maintenance-plan.md#a普通增量历史首建与专项审计分开)的建议，未改变现行模板的执行要求。

## 三层检查实际做了什么

| 层次 | 检查的问题 | 实际机制 |
| --- | --- | --- |
| 作者阅读与提交保护 | 内容应怎样表示，输入/版本/原文/依据是否符合发布合同 | reader共读新旧原文及必要关系两端；apply检查相关expected、来源revision、文本范围/原文、依据、向量输入与身份、原子事务和control入场 |
| 发布后回读与处置核对 | 实际写入的内容、处置、依据与访问路径是否符合预期 | coordinator提示要求每批后用search/read/neighbors，并核受影响ID及未覆盖范围；不是每个ID各跑三条命令。apply本身不执行这些查询，返回数量和失效ID也不等同完整验收 |
| 此次额外独立审计 | 摘要/关系是否受原文支持，历史与当前是否混淆，迁移及旧依据是否正确 | 17个主题的语义判定，另用脚本串起对象、依据、来源、状态、向量与迁移守卫；范围扩至717个不同ID。独立全量审计不是客户端每轮强制的步骤 |

阅读保存的原文能证明历史依据；它不自动证明当前接口行为。search验证实际检索路径，read验证依据访问，neighbors检查展开结果；某ID没进入自然语言top-k并不等于未写入或知识错误，三种工具也不是每条记录都要各调用一次。

## 哪些检查确实发现了问题

- 15:56，部署验证摘要无依据声称包括“隔离数据库原生写入”，实际来源支持的范围更窄，审阅后收窄了摘要。
- 15:57–15:59，jobs关系把mock PID查询写成实际取消和receipt文件行为，第一次修订仍超出证据，随后再次收窄。这不是哈希/版本匹配能够判断的错误。
- 16:23，接入摘要修正“何时读凭据”和设施检查的适用范围；相邻块的read/stale-neighbor合同被误放进另一块标题，也被修正。
- progress变化后，旧范围13–32改成15–35，并重读受影响的五个依据块；旧判定确实失效时的局部复审有必要。

最终PASS是修复后的结论，不能据此说独立复核没有发现错误；这些个案也不证明每个普通批次都值得完整独立重审。具体对象、时间和文件位置在选留的actual-reviews.md。

## 账本证实的复用与尚不能量化的重复

- 最终前681条有效判定与最终同ID判定逐条相同，新增36条；最后两次guard使用的717条判定也完全相同。这里已有有效复用，重复的是机器有效性检查，不是两轮新的717项AI审查。
- 4条旧判定因目标知识版本/保存依据变化失效，其中3条也有progress物理源变化，均有替代判定。这不能当成无变化记录被无故重审。
- 1,215是按member与读取参数去重后的请求数；996条basis按目标、知识版本、依据及位置组成的键也无重复。因此不能将二者直接称为重复或人工阅读次数。
- 1,215个返回中有442条与同集合其他返回完全相同，但调用键或服务的目标主张可以不同；相同原文可以支持不同主张。这只提示有合并读取的空间，不能直接减去442次语义判断。
- 账本不足以把作者、协调者、独立审计跨阶段的同一主张/同一依据精确对齐，未能量化重复语义复核的次数或墙时占比。两小时也不能按“命令累计时间相减”推导AI审阅时间。

## 必须保留什么，怎样简化

以下保留的是需要成立的保证，不要求继续使用昂贵的逐项AI方式。调整属于候选建议，现行实现未改。

| 保证或检查 | 建议处理 |
| --- | --- |
| 生成/改变主张前阅读原文，关系判断者同读两端及依据 | 保留；由实际判断责任人做一次。原reader已完整判断且主张/依据未变时，协调者不因职位再从头审一遍；跨reader合并新增的关系仍须共读 |
| 来源/相关知识版本、有效范围、原文与依据、匹配向量、事务和停止入场 | 保留程序的相关契约检查；不让AI重复逐字段算hash或手工验证程序已证明的等式，程序也不能代替语义支持判断 |
| 实际发布结果与授权处置 | 保留闭环；候选用程序批量对照全部本批相关ID、保留/更新/退役/未解决处置及范围差集。抽样语义复核不能替代完整处置对账，但完整对账不等于每ID再由AI判一次 |
| 父引用完整性 | 当前apply只保存parent，未验证非空父引用可解析；这个机械保证不能直接删。候选先补或保留有合同依据的核验。未证明线上已出现坏parent，也不额外强制固定三级、同源、包含范围或无环等未定合同 |
| 发布后的实际read/search/neighbors | 保留与本次变化有关的访问路径验例及差异处理；可批量和代表性执行，不为每个ID拼齐工具调用。迁移/快照/检索实现变化时有针对性加强，不能用几个命中证明全库召回或每项语义正确 |
| 同一有效主张及依据的复审 | 复用已发布知识、本轮阅读批次或已有判定覆盖的范围；不另建审查数据库。目标主张、条件、端点、依据版本/范围/locator或必要上下文变化时只重判受影响部分；机械等价可用已有证明，不因随机知识revision改变自动整批重审 |
| 独立AI全量逐项复审 | 不作为普通增量默认步骤，也不要求tier2重读全部tier1结果；具体歧义/矛盾、实际检索错误、历史/模拟/当前混淆、已知缺陷或明确专项审计目标才触发有界复审 |
| 最终全表前后快照、全库引用/向量守卫、重写判词及反复结案 | 整库迁移、恢复或实现修复按任务需要保留；普通知识批次聚焦本批变化与依赖。状态稳定后复用判定并做必要的一次收尾确认，不为每次guard重跑重写语义判词或增加另一层审计 |

复用不能只看ID或“某文件曾经读过”。需确认实际主张及已审范围、保存依据与适用条件仍成立；历史事实绑定旧快照，不因工作树后来更新就一刀切全审，声称当前行为的主张则需核当前适用性。对没有可靠旧判断或等价证明的内容，不能假设它已被审过。

这既不是用户排除的D未发布草稿续用，也不是E通用程序性能优化；它调整的是已选A的审核职责和完成口径。B/F的有效处置、粗层与待细化也要进入对账，不能仍要求每个非空来源都以精细表示覆盖才算处理。

## 最小普通流程与验证边界

建议流程：实际变化/必要依赖的一次作者共读 → 程序发布保护 → 本批实际结果与完整处置对照 → 必要的真实检索/回源验例；具体矛盾或明确审计目标再增加独立语义复审。协调者只对合并产生的新判断或错误补读，不串成所有角色逐级重复审同一结论。

实现前对照同版本资料，用已发现的超范围摘要、mock/实际混淆、遗漏旧ID、历史来源迁移和并发修改作为例子，比较错误检出、实际阅读/工具轮次和墙时。程序差异必须处理，不能被抽样通过覆盖。现有研究未运行此简化流程，不能保证零漏判或宣称已节省某个比例；独立审查不是无价值，默认重复全量审查也缺少成本收益依据。

代码依据为active store.py、maintenance.py、schema.surql、candidate_vectors.py及角色提示；程序能力不包括对摘要、关系、条件正确性的普遍证明。三个分支报告、原证路径与复算方法选留在本机 `artifacts/runs/20261111-review-overhead/`；原始账本仍在 `artifacts/runs/20261111-task-archive-memory/audit/`。本轮未新开维护写入、全库审计、embedding或功能测试，仅运行brief和既有文件读取。
