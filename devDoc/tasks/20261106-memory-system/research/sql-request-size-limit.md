# SQL 请求尺寸上限的目的、效果与本机建议

2026-11-11（北京时间）。本轮核查上游机制并在隔离实例测量请求体积的影响，没有修改或重启正式项目数据库。前因见[自动维护调查](automatic-maintenance-20261111.md)，实施选择沿[入口与容量计划](../automatic-maintenance-plan.md)。

## 结论

**建议把本项目 SurrealDB 的 SQL HTTP 请求体上限显式设为 32 MiB（33,554,432 字节），保留有限上限。** 这是本机试用建议，尚未获得用户采纳或应用到正式服务，也不是任意 SQL/并发/持久化场景的稳定保证。当前 1,292,144 字节的已知失败请求约 1.23 MiB，32 MiB 提供约 26 倍余量；调高限额不会强制生成更大批次。

依据是本机隔离 4.0.0 实例在显式 32 MiB 配置下成功提交 31.9376 MiB 的合成向量事务，耗时 2.671 秒、服务端采样私有内存峰值约 979 MiB。主机可见物理内存 47.216 GiB，调查时可用约 26.565 GiB，16 逻辑处理器。8–16 MiB 也是更紧的可选容量；没有必要仅为目前约 1.23 MiB 的需求直接放到 GB 级或近似无限。

单请求结果足以支持容量可行性，**并发稳定性尚未通过**：两个约 16 MiB 的独立 ID 事务并发时，只有一个提交，另一个 COMMIT 返回 Write conflict。此观察发生于内存测试实例，不能等同正式 SurrealKV 的结论，亦不能归因于 HTTP 大小上限。

## 上限的目的与实际效果

上游 v4.0.0 的 /sql 路由先关闭 Axum 的默认 body 限制，再安装自己的 RequestBodyLimitLayer；处理器以 Bytes 聚合整个正文，然后转换 UTF-8 并执行 SQL。它对单次 HTTP 请求体设置字节上界，而不是判定知识质量或 SQL 内容是否正确。

直接效果是：已知 Content-Length 超限时可立即拒绝，未知长度时在读取过程中累计约束，减少继续接收、缓存和解析大输入的成本。Axum 的[官方说明](https://docs.rs/axum/0.8.9/axum/extract/struct.DefaultBodyLimit.html)明确将默认 body 限制与安全关联。对本项目的本机回环、认证连接，网络恶意流量不是主要使用场景；仍需考虑误生成的大批、多个请求叠加以及解析/事务中的内存放大。后者是本次实测观察，不只是对未知攻击的假设。

它不能限制小查询产生的大扫描、大返回结果、计算时间或整个服务的总内存，也不是并发限流器；调高值不是预留等量内存。实际包变大才增加相应接收与处理开销，执行成本还取决于语句内容。此前默认请求体上限拒绝合法尺寸需求，与其保护资源的效果可以同时存在。

历史与用途证据：

- [2021-05-24 提交](https://github.com/surrealdb/surrealdb/commit/469de77609)把当时 SQL 上限从 1 KiB 提高到 1 MiB，但未解释精确数值的选择。
- [2024 年 PR #4670](https://github.com/surrealdb/surrealdb/pull/4670)将各接口限额配置化，允许部署方调整；没有宣称 1 MiB 是不可更改的安全边界。
- [官方 HTTP 文档](https://surrealdb.com/docs/reference/rest-api/http-protocol#request-size-limits)按查询、导入等端点用途区分限额。
- 没有找到上游对“恰好 1 MiB”的原始数值论证，也没有官方的机器无关稳定最大值。

## 能否取消限制

上游 [v4.0.0 路由](https://github.com/surrealdb/surrealdb/blob/v4.0.0/surrealdb/server/src/ntw/sql.rs#L30-L81)始终挂载数值限制层。环境变量是 SURREAL_HTTP_MAX_SQL_BODY_SIZE，默认值见[配置声明](https://github.com/surrealdb/surrealdb/blob/v4.0.0/surrealdb/server/src/cnf/mod.rs#L28-L30)。

- **0 不是无限，而是拒绝非空正文。** 它可被字节解析器解析为零，限制层仍照常执行。
- unlimited、disable 等不是合法数值。[字节解析器](https://github.com/surrealdb/surrealdb/blob/v4.0.0/surrealdb/common/src/str/bytes.rs#L1-L39)与[环境宏](https://github.com/surrealdb/surrealdb/blob/v4.0.0/surrealdb/common/src/mac.rs)在这类解析失败时回退默认值，不能用这些字符串关闭。
- 该变量没有发现受支持的“关闭限制”模式。技术上可设置极大的有效 usize 数值，近似取消本层约束；也可修改服务端路由，但这会引入自维护数据库构建。二者都不会取消内存、执行时间或其它协议约束。
- 设置较大上限仍需作用于新启动服务进程。本轮没有重启共享实例，原进程实际继承环境尚未读取。

本轮不建议近似无限：实测数值向量 SQL 的新增服务私有内存约为请求体的 24–28 倍，32 MiB 已接近 1 GiB 峰值。该倍率只适用于本合成样例；若粗略外推到 128 MiB，新增私有内存可能在 3 GiB 以上，但未实测，不能当容量保证。32 MiB 在请求体大小方面覆盖已知约 1.23 MiB 请求，并为偶发异常大包保留明确边界；不据此保证原 SQL 的实际执行结果。

## 本机隔离实验

每例使用本机 surreal.exe 报告的 4.0.0 for windows on x86_64、新端口、仅内存库和独立随机凭据；正式 18080 实例及磁盘 store 未用于测试。请求为 BEGIN/COMMIT 中的 change CREATE、member UPSERT、短原文及 2048 维数值数组；不调用 embedding 服务，也不是原 1,292,144 字节请求或完整 basePack apply。每个成功样例均核 HTTP、全部语句状态、成员/变更计数及一个存储向量的长度。

表中私有内存为服务器进程 baseline→20 ms 采样峰值，不含客户端；可能遗漏更短峰值。MiB=1,048,576 字节。主机其它工作仍在运行。

| SQL body 配置 | 实际 body 字节 / MiB | 请求中的成员数 | 耗时 | 私有内存 MiB | 结果 |
| --- | ---: | ---: | ---: | ---: | --- |
| 默认 | 537,045 / 0.5122 | 14 | 0.069 s | 93.56→105.02 | 提交成功 |
| 默认 | 1,380,943 / 1.3170 | 36 | 0.011 s | 90.39→90.39 | HTTP 413，未接受此请求 |
| 64 MiB | 1,380,943 / 1.3170 | 36 | 0.130 s | 92.16→124.28 | 提交成功 |
| 64 MiB | 8,400,878 / 8.0117 | 219 | 0.691 s | 90.80→310.42 | 提交成功 |
| 64 MiB | 16,763,576 / 15.9870 | 437 | 1.375 s | 104.99→538.15 | 提交成功 |
| 64 MiB | 33,565,694 / 32.0107 | 875 | 2.723 s | 104.86→996.93 | 提交成功 |

64 MiB 设置仅为首轮测试保留空间，并没有测试 64 MiB 大小请求；不能把它说成“64 MiB 请求已验稳定”。实际 8.0117/32.0107 MiB 样例略大于 8/32 MiB，上限恰为相应数值时不能假定通过。32 MiB 的独立配置样例严格低于上限。本轮均在当前客户端 30 秒 HTTP 等待以内，但未验证更复杂查询、真实磁盘提交、长时间运行或大型正式历史库。

### 并发与未解决观察

同一个内存库、并发前已建立 namespace/database，使用不重叠的 member/change ID：

- 2×8.0121 MiB：两个 HTTP 200，只有一个事务提交，持久计数为 219 而非 438。首版脚本只保留前 3 条 NotExecuted，未保存真正根错误，原因未定。
- 2×15.9878 MiB：配置 32 MiB，两个 HTTP 200，只有一个事务提交；另一个 COMMIT 明确报告 Transaction conflict: Write conflict。墙时 1.408 秒、服务器私有内存采样峰值 957.16 MiB。完整 ERR 留存，不能当吞吐成功，也不是 413。
- 原因尚未定位，不据此断言底座有缺陷或要求默认串行化。后续如评估并发写稳定性，须单独复现并核正式存储引擎、写集合及 basePack 的版本合同；升高或取消 body 上限本身不会解决事务冲突。

实验初次漏建 namespace 导致取消事务，未计成功；一次结果保存后的控制台编码错误也保留。全部 16 个临时服务 PID 已结束并复查不存在。没有失败组被改记为成功，没有修改正式服务或引入自动重试。

## 建议、采纳边界与原证

建议先采用有限的 32 MiB 作为**本机待采纳配置**；资源较小部署可选择 8/16 MiB，出现明确更大需求后再测高值。若用户采纳，部署步骤可在本项目 launcher 启动前设置 SURREAL_HTTP_MAX_SQL_BODY_SIZE=33554432，然后按共享实例的维护窗口重启并实际回读；此处仅描述实施方式，尚未执行。

这能处理已有 1.23 MiB 级容量拒绝，不能解决主 agent 漏启动、显式维护过早收尾、预检失败交接或并发冲突。有限上限也不等于要求 AI 每次人工拆 SQL；容量配置、SQL 构造和发送由程序/部署负责。

选留原证在项目忽略的 artifacts/runs/20261111-sql-limit/：probe.py、concurrency.py、results.jsonl、probe-report.md、upstream.md、host-memory.json、selected-summary.json。上游源码基于 v4.0.0 tag 提交 284fe93afc851c3baec2c262c01289602021a70d；本机二进制报告版本一致，但未证明源码与二进制构建逐字一致。原证只保留不含随机凭据的输入生成逻辑和输出。
