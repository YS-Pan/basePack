## 实际职责与开销

当前[publisher prompt](../../../../experiments/20261106-basepack/src/basepack/memory/prompts/coordinator.md)要求分派、亲读必要批次、跨reader scope整合、共读关系依据、freeze/hash/apply、处理反馈和版本冲突；[reader](../../../../experiments/20261106-basepack/src/basepack/memory/prompts/reader.md)主要交有界来源的草稿、范围和错误。协调者实际兼任作者、集成发布者与恢复执行者，职责比纯调度更重。

核读了[主协调者](codex://threads/01a1da06-7fb7-7680-a50b-22dc2085475e)、[第二协调者](codex://threads/01a1da06-f6d0-7d62-8789-97559554e3af)及两个reader。完整运行中主协调者有638次命令、173次wait；第二协调者69次命令、220次wait。操作计数不是模型请求数，不能逐一分摊token。可定位的负担包括：

- 必需整合：曾因 `Conflicting expected revisions` 拒绝合并，需要共读证据并重新准备；不能把所有回读视作重复浪费。
- 机械步骤碎片化：22:01的一批将freeze、hash、apply、写ledger分为四次独立调用。成功路径可由程序接续并返回紧凑回执，异常再交模型判断。
- 重复取入：第二协调者20:28:27读过含原文的reading.json，7秒后又读九份原文件。主协调者还读入整份回执和全目录清单；记录输出字符不保证全量进入上下文，但重复取入本身可定位。
- 草稿及运行返工：缺关系/节点ID、引用形状错误、embedding实际3628 token超过2048，以及源版本变化，均引入修稿和发布接续。语义、范围、分块修订可回原reader，机械格式问题应在已有程序边界尽早暴露。
- 等待粒度：有一分钟内连续5次wait的区间。等待有必要，但持续接批不要求每几十秒重新检查状态；可沿宿主完成事件接结果，尚未量化可避免部分的token。

一处并发返工由本聊天引起：`c03e730`于11月14日22:29:54写入检索并发调查进度，22:29:59的apply拒绝旧来源版本。提交前后progress正文SHA256分别精确匹配失败稿及两个repair稿；下一稿又遇依据需重读/接受，之后补接受成功。不能把它归为维护无故重复；业务变更与低优先级维护应并行，恢复应局限于受影响批次。

## 后续与证据

优先减少机械操作的模型往返、重复正文和短轮询，让程序交紧凑批次回执，把语义修稿交回原作者，协调者集中处理跨来源判断、冲突与关键验收。不是靠增加reader用量实现某个比例，也未证明更换模型可消除这些开销。本次未修改派工、发布合同或模型配置，节省幅度留实际改进后的同口径对照。
