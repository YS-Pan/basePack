## 与耗时是什么关系

**不能建立“目录 1.5 GB，所以每次维护要读 1.5 GB”的关系。** 默认发现排除 `.basepack`，已登记来源另行纳入；本次实际已登记的 `.basepack` 路径只见 memory/codex，无备份。维护另行枚举保留的聊天，读取活动库、受管原件和本轮收据；旧备份和旧维护目录不会仅因存在就参与默认全项目扫描。依据为 active 源码 discovery.py、maintenance.py、content.py 和实际来源清单。

关系分三层：

1. **直接关系尚未量化。** 活动库、实际源读取、序列化及磁盘写入会影响程序阶段；HDD 上重复读取和小文件往返值得关注。本轮没有分组件维护计时，不能把 189 MB 数据库或 WAL 大小解释为两小时主因。
2. **共同放大因素已找到。** 反复全量准备/核查、完整记录多格式保存、维护过程产生新材料，会同时增加时间和空间。以前调查的主证据仍指向工作范围、语义判断、审计与协调扩大；磁盘文件增长也包含这些工作的结果，不能倒置因果。
3. **不同治理目标。** 整理冷备份和历史产物可明显降低空间；减少 agent 重读、重判和反复协调才更直接针对长墙时。清理冷备份不应承诺语义维护明显提速；增加磁盘或提高 SQL 上限也不消除这些重复工作。

19:06 的只读聚合计数为 source 258、source_version 392、member 1,914、node 26、semantic 212、change 4,118；七表计数请求约 0.046 秒，仅能说明该次聚合未出现长等待，不能作为 maintain/prepare/apply 性能基准。

## 可选方案

以下可组合；复杂度为当前工程判断，未通过候选实现或同条件测速验证。保留全项目发现、聊天原件、历史依据、版本保护和知识/向量原子发布，不用任意数量截点宣称维护完成。

| 方案 | 具体改变 | 能减少的工作 | 代价与边界 |
| --- | --- | --- | --- |
| A 普通增量与专项审计分开 | 回执分列既有知识变化、历史首建、迁移、审计；普通维护不默认追加全库逐 ID 复审。按固定捕获/版本截点收尾，后续变化留下一轮 | 范围自扩、追赶自己的收尾文档、无必要的多轮独立审阅 | 低；不减少真正历史首建，未处理范围仍须显示；保留程序检查，语义支持不能由 hash 代替 |
| B 允许“此版本已审，无新增知识” | 读过的来源或范围可保留明确处置及版本；未变时不反复作为首建候选，内容或必要上下文变化后重评。维护子聊天先判断是否有父报告未涵盖的新事实 | 无价值或重复材料反复入队、对同一工作过程重复提炼 | 中；需要小而明确的状态与失效规则。保留原件，不能按“子聊天”一刀切，也不能把首次未读材料标成已处理 |
| C 局部变化只传播到必要依赖 | 用变化范围和已有引用定位受影响块、祖先摘要、关系；未变兄弟表示复用，语义关系仍由共读 agent 判断 | 一处修改引起整份文件和大范围关系重新理解 | 中至高；依赖不完整会漏更新，需覆盖改名、移动、拆合及跨源依据；不另建通用调度平台 |
| D 短任务可续用未发布草稿 | 保存非权威草稿及引用版本；下次先核版本和依赖，变化部分重读，最后仍按原合同 apply | stop 后丢失已完成阅读、下一轮同源重写 | 中；先证明同源重读真实发生；草稿不可当已发布知识，stop 后不提交，不等于模型可以从任意中断点恢复 |
| E 收紧程序读取与向量传输 | prepare/apply 按目标及依赖查询，单次操作内复用原件读取；匹配向量在数据库内保留，少回传及重写 | 全表响应、重复原文读取、向量序列化/传输 | 中；完整依赖与事务并发条件必须保持。单独 embed 不一定推进 knowledge_revision，需事务内检查向量身份、输入版本和存在性；不替代 SQL 自动分包 |
| F 全项目粗层覆盖，精细表示渐进 | 所有原件保留可检索入口和粗层线索；精细章节、摘要及关系随真实变化、使用和随机共读逐步完善 | 为全部历史过程材料立即生成同等深度表示的成本 | 架构选择，中至高；少建的细关系可能降低主动发现能力。若允许长期只保留粗层，会改变当前完整首建/验收合同，需用户选择 |
| G 活跃业务期间合并项目维护作业 | 多聊天避免重复领取同一来源版本，在有业务任务承载时接续可验证作业；各业务任务仍有停止边界 | 多个维护团队争同一版本、重复启动与冲突 | 中至高；宿主须有实际可用的跨聊天任务协调能力，不能假设目前已具备。没有活跃业务承载时暂停，不建立永久 LLM 后台或无期限执行 |
| H 治理备份和过程文件 | 恢复以经验证的权威备份为准；仅为比对而存的全量 JSON 可考虑改为 digest/必要元数据，旧恢复点与可重建中间文件按明确保留规则处理，必要时验证压缩收益 | 重复导出与校验材料的空间、备份时间，部分过程写入 | 低至中；主要解决空间，不能承诺语义提速。先验恢复集合与附件/旧快照，不直接删 WAL/vlog，不自动删除已有备份 |

另有两项按测量再选的局部优化：聊天采集仅在宿主能证明历史未变时增量重用，不能只看最后消息 ID；对真正字节重复的 source_version 内容做去重，保留不同版本、路径与历史定位，迁移/恢复成本通常高于冷备份治理。当前未证明它们值得优先实施。

## 建议怎么试，而非一次全部修改

优先比较 **A+B**：先减少反复决定“要做哪些昂贵工作”，同时保留积压可见与真正变化的处理。A 可以先从工作约定与回执尝试，B 的新状态需要候选代码和失效验证。H 作为独立空间治理，不把释放容量计作维护提速。

随后按阶段计时选择 E；若重复冷启动确实突出，再选 D，跨聊天争用突出再考虑 G。C 是更深入的增量机制，F 是质量与成本的不同产品取舍；都适合作为对照候选，不默认替换现行合同。不承诺倍数，不用更多并行 agent 直接替代工作量治理：并发可能缩短墙时，也可能增加重复与版本冲突。

最小对照使用相同隔离库起点、真实材料和 agent 档位，分别测试：无变化再维护、修改一段、移动一份文件、短任务中断后继续、父/子聊天重复且子聊天含独有信息。一次改变一个因素；记录首次/重复候选、读写字节、prepare/apply 次数、语义重读与协调轮次、阶段墙时、冲突及实际可得用量，并保留原文更正、历史回读和检索任务的质量检查。数据库备份恢复另验。HDD、冷/热缓存和并行负载据实标注；本轮没有执行这些性能对照。
