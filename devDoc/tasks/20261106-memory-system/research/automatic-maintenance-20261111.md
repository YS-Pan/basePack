## 实现与故障链路

[brief](../../../../experiments/20261106-basepack/src/basepack/memory/store.py)分别查询所有未退役 stale member、node 和 semantic，pending_count 为三者长度之和；默认仅前 20 条进入明细。采集分页的 100 及检索的 0–100 评分均不是维护门槛。

[CLI](../../../../experiments/20261106-basepack/src/basepack/memory/cli.py)的 maintain 顺序为发现来源、采集 Codex、机械维护、补充 receipt、生成 worker 元数据。[维护实现](../../../../experiments/20261106-basepack/src/basepack/memory/maintenance.py)先完成机械组 apply，末尾才写新的语义 receipt。[prompt_dispatch](../../../../experiments/20261106-basepack/src/basepack/memory/prompts.py)只返回角色、模型和渲染命令，不调用宿主 spawn。缺少绑定是明确 gap，不能与采集过程抛错混为一谈。

本调查使用本项目独立 control，亲自复现：

1. 沙箱下 Codex App Server 无法打开 state_5.sqlite（OS error 5 / SQLite code 14）。
2. 正常用户上下文下，已进入 memory.maintain 的机械 apply，HTTP 413；错误附注 SQL request body 为 **1,292,144 bytes**。

机械维护按跨来源 evidence 连通组一次发布；SQL 包含来源快照、成员、向量及版本约束，没有组内按请求大小分页。413 在最终 receipt 写出前抛出，所以这次调用没有产生可按正常流程派发的新 worker。已成功的前序机械事务和已采集聊天可能保留，不能把整个失败预检当作全量回滚，也不能解读为 needs_semantic=false。

SurrealDB [HTTP 协议文档](https://surrealdb.com/docs/reference/rest-api/http-protocol)列出 /sql 默认上限 1 MiB，超限返回 413，自托管可配置 SURREAL_HTTP_MAX_SQL_BODY_SIZE。本次请求大于该默认值；当前进程的有效上限未核实。**超限组的具体来源、各部分大小占比及归档是否导致其膨胀尚未定位**，不把静态机制当作实际组分析。

## 原因分析

**启动遗漏、范围收缩与预检失败是三条不同的因果链，不能互相代替解释。** 任务开始漏执行先于 413；主 agent 后来的主动 stop 也有独立决策证据。没有证据表明 100 是阈值、安装版本不一致或宿主不能创建并行子任务。

1. **启动依赖主 agent 执行文本协议，尚未形成可靠的任务生命周期动作。** 项目入口已经明确要求开始时异步维护，本调查也读到了该规则，却先推进资料读取和调查派工，约 1 分 49 秒后才调用预检。CLI 只提供命令和派工元数据，没有代替主 agent 完成开始事件、句柄管理和业务结束事件的执行层。直接原因是主 agent 未按已有规则调度；结构上的薄弱处是同一 agent 既规划业务，又必须额外记住并执行维护步骤，没有独立执行或可核的启动结果来暴露漏项。这是从执行路径得出的设计分析，不推测模型内部注意力或动机。
2. **完整预检成功是正常语义交接的唯一出口，局部失败因此阻断全部新派工。** CLI 先采集聊天，再提交机械组，最后才写语义 receipt 和 worker。采集所启动的 Codex App Server 需要访问宿主全局状态，沙箱下权限不足；换到正常用户上下文后，故障推进到 SQL 请求过大。失败批次应停止并保留原错，但安全可接续的历史语义工作也拿不到本轮交接，说明预检和后续维护的恢复责任没有贯通。旧 receipt 可以重新渲染并在新 control 下接续，依靠 prepare/apply 重新核版本；它只覆盖旧截点，不是失败轮自动产生的恢复回执。
3. **依赖闭合的机械组没有同时受传输大小约束。** 为保持 evidence、expected 及新接受版本一致，机械候选按来源与依赖连通组一次原子提交；SQL 又内联来源快照、成员和向量。embedding 请求分批或复用已有向量，不能缩小最终仍写入向量的这一份 SQL。实测 1,292,144 bytes 被拒绝，说明当前成组方式与接口容量之间存在未处理的冲突。进一步找到 15:34 的事后探针：将 apply 替换为保存候选并抛 DiagnosticStop 后，首个拟发布组为 environment.md 的 30 个 chunk；随后按每批 5 项处理，默认预检成功。这支持该组是超限候选的推断，说明单一来源也可能形成大请求；探针晚于原错误约 8 分钟，并非原始 SQL 捕获，不能无条件认定就是原 1,292,144 字节请求。各部分占比及归档是否触发仍未知。
4. **主 agent 混用了后台停止权和显式维护的完成判定。** 当前 coordinator 模板始终表述为后台低优先级、宿主停止即停，渲染接口没有区别显式维护交付的完成合同。模板同时要求持续处理固定 receipt，所以它并未要求提前停止；已证实的是主 agent 自行把优先的 38 来源等检查点当成收尾线。共同模板可能增加完成边界不清的风险，但没有证据证明它就是那次决策的心理原因。剩余数不为零本身不等于后台任务失败，关键是显式交付仍有可做工作却被自行收窄。

既有验收证明了 CLI、英文渲染、实际多批派工、依据回读与 stop 能工作，见[交付验收](../../../archive/20261111-memory-worker-prompts/result.md)。这些证据不直接证明普通新任务会自行启动维护，也不覆盖主 agent 面对显式维护和预检故障时的实际行为。验收结论需要区分“按流程启动后可工作”与“默认会被可靠启动并接续”。

后续修复应先明确并落实启动责任及显式维护的完成边界，再解决机械组大小和失败交接。新增重复提示文字、增加 reader 或放宽数据库上限都不能独自覆盖上述三条因果链；需要针对每条链取得实际行为证据。

## 后续修复与验收

- 宿主执行：明确业务开始的异步预检及句柄归属，以真实命令、派工和退出事件确认执行。当前模板已有持续接批要求；再次增加相同文字本身不能证明遗漏已消除。
- 完成条件：普通业务后台维护随业务停止；用户显式要求的维护按授权范围逐项处置或报告真实阻塞。主 agent 不能自行把优先范围升级成全任务的收尾线。
- 预检故障：先查超限组及依赖，修复机械批次大小与证据闭合的冲突；在保留原错、已提交状态及原子性的前提下，让可安全接续的语义工作取得明确交接。旧 receipt 可用于已核范围的恢复，不能冒充新全项目预检。
- 对应验收应覆盖实际宿主开始/完成流程、显式维护的范围、真实超限组及失败后仍可安全执行的候选。调高上限、生成 worker 元数据、派出一个 agent 或 pending 下降均不能单独证明这些问题已解决。
