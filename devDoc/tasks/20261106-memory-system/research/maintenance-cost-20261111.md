# 两小时记忆维护的成本与深层原因

2026-11-11（北京时间）。调查对象是[评估并修复项目不一致](codex://threads/01a1c8be-c120-7d32-b0c0-0bf457181823)最后一轮归档与记忆维护。依据完整相关聊天/真实子线程、正式维护回执、独立验收账本、现行 0.9.1 源码及历史交付；本轮没有修改产品实现或重跑性能实验。既有入口/413问题见[原调查](automatic-maintenance-20261111.md)，后续实施安排见[计划](../automatic-maintenance-plan.md)。

## 结论

这次整轮确实约两小时：**15:21:58–17:29:39，共 127 分 41 秒**，包含归档、维护和收尾。**原100项待核在16:02:25已归零，约40分钟；之后还持续约87分钟。** 因此不是单独处理100项一直花了两小时，而是范围扩大、独立语义验收、共享文档变化及收尾工作继续发生。

当前证据更支持“工作组织、范围和验收放大”为主要解释，不能把两小时解释为 SQL 或 embedding 持续运行。原文/关系确有错误被修正，不能把额外工作全视为浪费；但也没有证据证明每一项都值得以这次强度处理，或证明这次维护的检索收益覆盖了成本。

更深层的判断是：**增量维护、历史资料首建和专项知识审计混在同一流程；完整性/正确性有强而明确的完成步骤，而全周期成本与收益缺少同等强度的验收。** 文件/摘要/关系的依赖又使一次业务变化扩为多层知识复核。过去的优化改善了局部能力，却没有证明昂贵语义工作随真实变化及必要依赖相称地增长。

## 为什么还有638个原件没接受

最终固定回执有695个候选路径：48有当前覆盖及独立接受，9个删除路径已迁移处置，638无当前source/member接受证据。**638是原件候选，不是638条尚未修复的旧知识，也不证明每份都应该生成新的知识表示。**

独立复算该回执：650个标added、9个deleted；578个added位于受管Codex聊天，34个added位于archive。关联采集回执中，这578个聊天有534个带parent_thread_id，557个标记本次捕获字节未变、只有21个变化。这说明候选大头是**此前已捕获、尚未语义接纳的历史材料**，其中大量为子聊天；不能把它们全说成本轮维护新产生的内容。

清原有待核、更新已接受来源与给大量历史聊天做首建，是不同工作。它们被放进同一队列，容易造成“花很久，剩余仍很大”的体验，也让pending数难以解释实际完成边界。默认全项目发现本身不要求每个候选以同样强度精加工；保留所有项目聊天的目标不应靠删来源来规避。

## 直接成本为何放大

1. **范围持续扩展。** 发现原stale之外的来源漂移、遗漏旧片段和关系时，需要补处置；但从待核修复扩至固定回执既有知识独立审计，是额外组织选择，不能只用“全项目维护”四字代替工作量说明。
2. **语义决策与验收被分成许多轮。** 同一阅读批次要共读新旧整文件、成员邻域和关系两端，再草拟、合并、发布、回读、独立审核。六个reader反复复用，协调者有23次followup、258次wait；等待期间读者可以工作，不能当空转，但大量短步骤仍需agent上下文和协调往返。
3. **收尾追赶正在变化的资料。** progress本身是受管来源；17点前后持续改它、维护它、重核其摘要与历史关系。已有reader因版本冲突暂停或重准备。主agent在本调查chat的16:53和17:09也提交了同一progress文件，参与了共享资料的变化；底层事件context为空，不能把具体7条知识并发更新全部归给某个chat。
4. **错误造成额外路径。** 权限、413人工拆批、摘要超出依据、旧版本草稿被拒均有实际记录。版本保护防止错误覆盖是必要的，不能靠忽略冲突提速；但需减少冲突和重复准备的发生条件。
5. **批次还有固定机器开销。** prepare/apply读多张全表、返回较大邻域；机械组每次提交后再读表；复用向量仍可能重新序列化并发送。源码存在规模放大路径，但目前没有证据说明它们主导了本轮墙时。

## 更深层：原因的原因

以下为依据现行机制与本次证据形成的设计判断，不是已量化的唯一根因。

**第一，昂贵工作的单位和“增量”不一致。** 原件按文件版本，知识按块/章节/文件摘要，依据又跨来源；一个局部改动可能使摘要和关系需要重判。prepare提供整份新旧文本及邻域，独立审计再追完整依据。已有安全机械复用，所以不是所有变化都全量重做；问题是尚未证明昂贵的agent工作能稳定收敛到变化本身及必要依赖。

**第二，材料进入系统与值得持续精加工没有清晰的成本界面。** 非空未登记来源、没有活动知识的来源和未覆盖范围会继续作为候选。当前没有找到针对“已经审过、无需知识表示”的独立持久处置，也没有自动续用上轮未发布草稿的流程。只要历史候选仍在，pending=0时needs_semantic仍可能为true。捕获原件、语义接受、覆盖齐全和对任务有用必须分别判断，不能互相替代。

**第三，业务任务与维护工作单元的生命周期可能不匹配。** 本chat多轮简单追问均由主agent选择新control、启动团队、回答结束后stop。发布过的成果可复用；未发布的阅读/草稿不自动接续，下一轮仍会prepare。若短业务窗口常短于一个来源的阅读至发布周期，可能产生重复启动和重读。是否每轮问答都应视为新业务任务是宿主组织选择，不是程序自动创建模型团队。当前只有机制和本chat生命周期证据，尚未核同源重读及其时间占比，不能反推这是目标两小时的主要原因。

**第四，维护具有产生后续材料的反馈条件。** 维护agent产生子聊天、进度、变更记录；这些又在默认发现范围内。多个任务同时维护同一项目时，还可能争同一版本。同一chat用固定UUID路径，重复采集不会每次生成一个新路径；历史候选大多数本次未变。故只能说存在反馈放大条件，不能声称已证明无限自激、语义重复或净积压增长率。

**第五，改进验收偏重局部能力，缺少成本反馈。** 漏项后增加发现/覆盖，证据错误后增加共读/逐ID核验，生命周期问题后增加持续派工，都有正当局部理由；但没有同样明确的“同工作量完成更快、重读更少、业务效果不退化”的验收。于是更完整、更一致的实现，仍可能无法实现项目纲领的低维护成本目标。这是工程验收需要补齐的部分，不应解释为用户要低成本与正确性有错。

## 应优先改变什么（建议，未实施）

后续用户已重新要求比较具体方案与本机空间，详见[备选方案与1.497 GB盘点](maintenance-options-20261111.md)；以下保留本次原因调查的建议背景。

- 在入口/回执和交付中分清既有知识增量、历史首建、迁移和专项审计，各自说明完成范围；保持全项目发现，不用任意数量截点或删聊天伪造完成。
- 固定一个可交付的版本截点。收尾报告的新内容在截点后留待下一轮；不要让“把正在写的收尾再次完整入库”成为无止境的完成门槛。
- 按版本复用程序可证明的哈希、范围、端点和原文核查结果，把agent注意力用于真正有变化/有歧义的语义；独立审计强度与实际风险、验收目标匹配。不是删除证据保护或让错误自动通过。
- 用最小真实增量做同条件全周期对照：改一段、移动一文件、无变化再维护，分别记录读取字节、prepare/apply次数、语义重判、模型/协调墙时和业务收益。先确认哪项工作被消除，再优化批量查询、消息分包或并发安排。
- 若短任务中确有未发布工作反复重做，再决定怎样核版本后复用成果或调整组织；不先建立新调度平台，也不把额外状态和无限后台执行当默认答案。

这些建议尚未变为新的来源筛选、默认审核或运行策略。SQL分包的中小规模估计仍只针对传输改造，不能推广为“几百行代码即可解决本轮全部两小时成本”。
