# Terra 用量与真实维护观察

2026-11-17，北京时间。**原图对应的早期窗口中，多数 Terra 用量来自实现分支；随后完整第二轮维护中，Luna total 高于 Terra。维护内仍确有旧 C1 同类的短等待、全树查询和交付返工。** 不能仅凭一个模型比例判定异常，也不能用缓存占比把已观察的浪费解释掉。本稿已补第二轮54来源终态，新模板无提醒验证另列后续。

## 图表与当前角色

用户提供的近七日小时图是本机保留 Codex 日志的统计，包含多个任务及不同版本；原数据截止19:04:55，图片约19:05生成。统计优先使用 `token_count.last_token_usage`，缺失时才取相邻累计差，并非把累计快照直接相加。缓存输入属于输入，推理输出属于输出；这些本地 token 不代表服务端账户额度、费用或计算量。

本主任务截至19:04:55的 Terra 统计中，四条实现分支（含其子任务）合计81.967M，占70.6%；首轮维护为34.179M，占29.4%。已对这四条分支的10份选定日志按唯一响应身份复核，数值一致。因此这一窗口的橙色不能全部归为维护协调者。调查、集成和文档等其他角色也应按真实职责记账。

## 旧整改实际交付了什么

[11月15日调查](../../20261106-memory-system/research/coordinator-token-overhead-20261115.md)提出机械步骤合并、减少重复取入和短轮询；[11月16日通信调查](coordinator-communication-20261116.md)进一步确认长期协调上下文承担大量小组交接、等待和全树状态查询。旧案例中发布组合工具已经使用，不能把它再算作新增收益。

[0.16.0整改](../result.md)已交付 C1 的有限相关来源组、固定稿引用、同稿一次完成、自有分支观察和有界事件等待，以及 C2 的精确阶段交接与真实新身份接续。[随后完整维护](../maintenance-20261116-result.md)确认 C2 的上下文重置生效，但 C1 仍只有部分成立，存在全树查询、短等待、改交稿和协议修复，后期还加入了宿主督导。旧节省区间是情景估算，没有通过同材料对照证明，不能称为已经完成的收益验收。

本轮首维护发布协调者仍有16次10秒等待，已核至少12次超时；7次状态列表中6次没有自有子树范围。这与旧 C1 属同类未稳定执行的行为。本轮该协调者日志中，6次成功列表输出的嵌套完成状态实际带入7,447字符正文，其中其他业务2,986、本队4,461；另1次无范围调用未形成JSON列表。全树成功输出示例约1.7—2.1K字符，未重现旧长轮70K字符的规模，但仍有无关正文取入，不能外推整个宿主API或换算节省比例。

## 本轮返工分别归因

| 观察 | 归属与处理 |
| --- | --- |
| N1把合法历史 basis／parent pin 错与当前头比较，阻止原作者合法稿编译，并引出不必要重写 | 0.17 新增产品缺陷。0.17.1已保留精确历史依赖并分开当前头检查，以同一作者草稿验证，无需语义重写；新轮已观察段尚未复现 |
| 作者交付 hash 后原地修改5条 evidence，联合发布在 freeze 前报 SHA 不符 | C1固定交付合同未稳定执行。程序拒绝发生在写库前，属于正确拦截；原作者已另存新文件并确认新交付，不能简单替换期望 hash 后推进 |
| architecture 的 file 摘要漏计末行 | 作者范围合同错误，与历史 pin 缺陷分开。原作者已按正确范围另交新稿 |
| 一次历史 read 缺少行界 | 调用合同错误，单列保留；不是历史 pin 缺陷或已确认原证丢失 |
| 摘要、关系等作者修改使既有依赖失效 | 可能需要正常的证据更新与作者修复，不能仅凭失效数量归为无效重复 |

上述分类不把所有回读或失败都视作浪费，也不因程序成功提交而增加例行语义复审。具体接受版本与本轮剩余范围沿[实施结果](../implementation-result.md)维护。

## 统计工具的独立缺陷已修复

调查另发现：相同 `last_token_usage` 和未推进的累计状态，会以不同时间再次出现在日志中。旧统计指纹包含时间，因此首轮把五条 Luna 事件重复计入：Luna从正确的196条／19,145,840，变为201条／19,784,968，多计639,128。Terra在此样本中没有这项差额。该缺陷不能解释为 Terra 真实消耗，也不能外推全七日误差。

`codex-usage-plot 0.2.1`保持 last 优先和累计差分，只有同回合、实际用量及两侧累计均匹配时才关联响应身份；缺少证据的等大事件继续保留。响应身份与原完全重复指纹共同去重，兼顾混合分叉副本、迟到连接及最早事件的时间／模型等元数据；旧缓存版本失效重建。

修复已在统计工具独立仓库提交为 `dcf6669a06cf9b88a639f5c373f92280f623c688`，分支保持原状且无推送。124项相关检查通过；实际仓库20个身份回归通过。普通 pip 安装落在原 Python 的 user-site，版本0.2.1；原 Python 和原 `Scripts/codex-usage.exe` 都从源码外目录查询去内容夹具成功，结果为471事件／53,324,937、剔除5条重复，且18个包源码与 wheel／安装一致。原全局0.2.0和原wheel保留，PATH未改。

**原图、CSV和全机缓存尚未按新规则全量重建。** 现有图片仍是旧数据快照；本次用有界去内容复现完成修复验收，没有为了补全机比例扫描所有聊天正文。

live 指导后的两个协调者共157次等待，参数全部为60秒；已核85次超时中84次的下一工具直接仍为等待。71次等待在更新到达后提前返回，另1次未有可解析JSON结果，未补推。发布协调者两次列表均限定自有子树；辅助协调者只有初期的一次无范围列表，指导后没有新增全树查询。另一个作者有9次30秒等待及一次无范围列表，未据此把整个团队写成全部遵从，也未在缺少任务语义时把这些等待都判为浪费。

发布协调者单次输入仍从21,620增长到239,047，辅助协调者从22,081增长到144,530。事件等待减少短超时醒来，并不自动解决阶段内所有交接与上下文积累。这一轮仍是宿主督导后的观察。随后0.17.2已普通安装：两协调者的60秒／自有子树规则及reader固定稿／字段规则已落盘，65个文件源码、wheel、安装副本一致；pip check及已安装三角色渲染的23项检查通过。渲染检查未实际派工或写数据库，新身份在没有 live 提醒时的行为仍待验证。本轮净费用、耗时和质量收益均未知。

新增一项知识反馈留给下一轮：startup 节点两个依据的 `source_version` 元数据有差异，但两个依据原文 read 均成功，精确知识版本也可读，原因尚未确定。它不是已确认的原证丢失；本轮闭合与该未定反馈分别报告。

`prepare`全节点目录及相同版本的 previous 正文是另一个候选线索：首轮包包含166个节点、约28.8万JSON字符，而直接关联节点远少于此。包字节不等于模型实际读入量；仍需核实际打印字段及全域发现用途，当前不据此宣布 token 节省或另开整改范围。

本机选留原证（可选，不随公共 Git 分发）位于 `artifacts/runs/20261117-terra-usage/`：去内容计数夹具、角色聚合、工具调用元数据、复算脚本、回归及安装回执。原 rollout 和真实 CSV 未放入公开稿；公开结论不依赖这些本机文件才能理解。
