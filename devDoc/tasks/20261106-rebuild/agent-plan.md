# AI agent 执行计划

2026 年 11 月 6 日制定。本文是重建实施方案，战略依据为 [项目纲领](../../project-charter.md)，推进情况见 [工作进度](progress.md)。本计划中的数字预算和接口名是可调整的工程建议，不冒充用户指定值；开发文档按 [文档维护规则](../../documentation.md) 组织。

## 目标与取舍

本项目建设记忆、资源协调、分层协作与独立的文件结构建议工具。2026 年 11 月 7 日用户指定先实施资源协调，按 [资源协调专项计划](resource-coordination-plan.md) 推进 P6，记忆建设继续保留 P0–P5 的依赖顺序；文件结构 skill 按 [专项计划](file-organization-plan.md) 独立交付。旧项目只取明确需求、事故样例和经确认的小接口，不整体迁入旧数据库、任务台账、授权或审计树。

记忆工具的首个可用版本包含短项目说明、文字检索、原文定位、一个廉价检索 worker、最小增量维护；紧接着补齐本地向量、图片和实际语义图。不能把这些后续能力从完整交付范围中删掉。

代码和 skill 各保留一份维护源，项目实例保存配置与数据。各工具可独立使用；记忆的一次查询不以完整资源平台或三层组织已建成为前提，文件结构 skill 也不以记忆闭环为前提。

## 最小结构与责任

建议采用一个源码仓库和三个模块，不为每轮尝试另建长期产品副本。

```text
basePack/
  AGENTS.md                 开发入口与阅读导航
  README.md                 发布前编写的安装与使用入口
  devDoc/                   长期依据、系统说明、任务材料与变更记录
  src/basepack/
    memory/                 来源、检索、图与增量处理
    resources/              现有资源设施的薄适配
    agents/                 宿主衔接及任务包处理
  skills/                   短技能、角色 prompt
  tests/                    小样例和真实事故回归
  examples/                 可随包分发的小型公开资料
  pyproject.toml            依赖与安装入口
```

产品源码与安装目录按上述建议建设，现行实现见 [实现概览](../../system/overview.md)。按 [安装与路径布局计划](deployment-layout-plan.md)，运行代码安装到系统 Python，项目以 `basepack.toml` 引用机器共享配置，数据放项目局部 `.basepack/memory/` 与 `.basepack/jobs/`；模型和 HTCondor 保持外置。源码与生成后的 skill 不分别手工维护。实验的临时输入和输出放仓库外或被忽略的 `artifacts/`；长期只保留能解释结论的小报告与必要样例。

| 对象 | 唯一职责与保存位置 |
| --- | --- |
| 项目纲领 | 用户意图和战略；本文不重复维护其正文 |
| AI 执行计划 | 步骤、依赖、验收；当前阶段、完成事项、阻碍和下一步统一记在 [工作进度](progress.md) |
| 项目原件 | 继续位于业务项目；记忆保存定位、版本及必要派生内容，不默认复制全库 |
| 来源、片段、节点、边、变化记录 | 项目局部数据存储；优先少量数据库/索引文件，避免每节点一文件 |
| 通用代码与依赖 | 源码由本仓库维护，安装到选定系统 Python 的 package 中；业务项目不复制 app 源码 |
| 权重、共享服务与机器调度 | AgentTools 共享模型/运行状态及独立安装的 Condor；路径和预算由机器配置维护，不存项目知识 |

底座先比较现有 Basic Memory 路线与一个更薄的数据库路线，最多做两个小型适配样例。选择能满足全文、向量、图、原文定位、增量与机械盘 I/O 要求的一种。若现有底座要求大量镜像文件或与新接口强耦合，采用更薄路线；若其原生能力已够用，停止自建。选择前核对实际安装版本及官方接口，不在本轮预设必须保留 Basic Memory，也不另设图数据库服务。

## 调用方式与最小数据约定

本地程序负责材料准备、查询、持久化、数值排序、变化检测和资源适配。理解、建图、图片识读、筛选和评分由宿主实际派发的订阅 agent 执行。宿主不支持的能力直接报告，不用不存在的 LLM API，不把准备好的任务包称为已执行。

对外先提供四种记忆动作，命令拼写在首版实现时固定：

| 动作 | 输入 | 紧凑输出 |
| --- | --- | --- |
| `brief` | 项目根、可选任务说明 | 核心目的、少量当前线索、值得注意的变化或缺口、原文入口 |
| `search` | 问题、来源范围、结果预算 | 文字/向量/图候选，正文摘录、来源定位及可读图路径 |
| `read` | 来源 ID、版本、范围 | 指定原文/图片及定位；不存在或已变化则给具体结果 |
| `maintain` | 变更范围、候选批次、自动/手动模式 | 应用结果、错误或未完成位置，供宿主继续 |

用户层的一次检索委托流程：工作 agent 发目标与预算 → 一个廉价 worker 检索并按需扩展/读原文 → 对实际读到的候选打分 → 脚本排序截取 → 返回直接相关的内容、来源和缺口。默认同一 worker 完成检索与评分，不强制独立评分员；工作 agent 仍能自行深入检索。候选多时分批，但先在共享候选范围或有共同锚点的批次内评分，避免把不同批的主观分数直接当作统一标尺。

最小数据字段：来源有稳定 ID、路径/聊天定位、内容版本和类型；片段有来源及原文范围；节点有稳定 ID、简短内容和支持来源；边有独立 ID、两端、关系含义、必要条件和依据。修改保留时间、操作及宿主可取得的执行聊天/turn/根聊天信息；宿主不给的字段留空，不编造。每项当前状态只存一处，不再建一套完整的事件认证系统。

自动与手动维护共用一条流程：找变化 → 准备相关新旧材料 → agent 共同阅读并产出节点/边及必要分段 → 可选批量审核 → 一次提交 → 更新受影响索引。自动模式处理当前任务的小批变化，手动模式可以深读、重访旧图和随机共读。默认不加独立审核层，争议关系或专项评估可显式启用审核；错误能在使用中更正。

## devDoc 自用与读取轮数

2026 年 11 月 7 日补充：将本项目 `devDoc/` 作为记忆工具的自用场景，一并验证主 agent 逐层读索引、找文件和补读造成的往返。当前任务 的启动信息、一次检索委托与增量维护落地后，应缓解这一问题；效果以实际使用验收为准。

- **P1：** 已知少量相关文件或章节由主 agent 同批读取；需要寻找和交叉取证时，由主 agent 一次说明目标、范围和预算，worker 内部完成必要的多轮检索、阅读、筛选与评分，返回可直接使用的内容、依据和缺口。宿主指令与必须保留的前提直接保留；链接供追溯和主动深入。
- **P3：** 文档或进度改变后，启动线索与检索结果及时反映变化，避免用旧结论指导新工作。保留短入口和直接读原文的能力，方便首次接入、定位错误和人工核对。
- **P4：** 在已有评估任务中加入“继续重建”或“修改开发文档”的自用任务，对照直接文件工具与记忆辅助读取，核对必要指令、事实和来源是否完整、有效，记录主 agent 串行往返、底层工具操作、返回材料量、补读、耗时及主/worker 合计可得用量。区分轮数下降与总成本下降；未验证前保留为待验收目标。

此场景从 P1 的文字闭环开始，不以完整资源协调或三层组织交付为前提。把读取开销纳入同一 work，按实际缺口改进，避免重复建立另一套文档检索流程。

## 阶段与完成条件

### P0 收敛边界和运行入口

**输入：** 本轮计划、精选调研、AgentTools 现有说明与实际接口。

**动作：** 沿用已建 Git 仓库、忽略规则及资源 R0 的 basepack 包/公共配置入口，确定四种记忆动作；复用资源阶段的环境实测，变化部分再核对；用同一个小资料集完成底座比较并选定一种。共享路径通过配置定位，公共源码不硬编码 `D:\AgentTools`。

2026 年 11 月 6 日的 [基础设施调查](research/sources.md) 观察到：AgentTools 只有模型、空 `profile` 和锁状态；系统 Python/依赖位于目录外。不要重建用户已决定留空的 profile，也不建离线 packages 仓库。该次 HTCondor 25.4.0 能查询本机 slot，但 `condor_q -json` 认证失败；实施时核实查询/提交的认证条件，沿现有配置解决接入问题。现有项目 Qwen 文件锁只提供合作式 GPU 互斥，没有统一 CPU/RAM 队列，也没有已完成的 `agent-run`。

**交付：** 可安装骨架，复用资源阶段按 [路径布局计划](deployment-layout-plan.md) 形成的配置/初始化入口；一个小资料集、一份不超过一页的底座设计决定，列明未选路线的主要理由。首个资料集包含当前/旧决定、低字面相似度关联、两份跨材料关系、图片及待处理材料；人工写出少量预期结果，单独保存以便隔离测试。

**完成：** 新路径可安装和运行；配置能指定项目根；测试数据不含旧业务授权；底座选型结束后不长期维护两套实现。P0 不全量读取旧库、不重新下载已有权重；共享模型和机器配置沿资源阶段成果复用，不重建环境或复制资产。

### P1 文字记忆闭环

**动作：** 来源登记、文字检索、片段与原文定位先跑通。生成短项目地图，通过宿主可用的项目启动指令/skill 在正常任务开始时交付最简 `brief`，先用项目核心和少量人工确认线索实现主动提示。提供一个可用的检索 skill：工作 agent 一次派工，廉价 worker 自行检索、评分、整理结果。需要文件组织建议时按需引用独立的 [file-structure skill](../../../skills/file-structure/SKILL.md)，沿用其单一维护源；其它布局同样能使用记忆工具。先允许显式触发维护，失败保留简单错误和未完成范围。

**交付：** 文本可用版本；一次实际订阅 subagent 检索记录；简短使用说明。建议返回给主 agent 的普通结果默认不超过 6,000 个中文/英文字符，可由调用者调整。

**完成：** 新聊天的普通任务能收到短地图及一个有关线索，未主动检索也有发现信息的入口；同一真实问题能从资料找到依据；找不到时说明具体缺口；主 agent 不必手动调度每轮查询；内容和定位对应；两个项目的相同问题不混入彼此资料。这时即可供小范围日常使用。

### P2 本地向量、图片和语义图

**依赖：** P1 可用；大规模 embedding 前先解决模型服务的实例与预算。资源 R1 用合成建库型/查询型请求验收共享客户端，本阶段让真实记忆建库与查询统一接入它。embedding 不以 Condor 认证成功为运行前提；小样例可先验证模型调用，正式并行按资源专项预算执行。完整记忆工具不以完整资源平台建成为前提。

**动作：** 优先复用 AgentTools 已固定的多模态 embedding 权重和环境；本轮调研所见旧方案为 Qwen3-VL-Embedding-2B、统一 2048 维，正式实现时核 revision、预处理与输入合同。查询与资料必须进入兼容的向量空间。先支持图片文件和 PDF 必要页面，视觉 agent 实际看图，保存短描述、必要 OCR/表格与区域定位；识读文本是派生解释。

建图以真实实体、决定、条件和材料关系为主，不能只在有“新洞见”时才建节点。新增与变更时共同阅读相关片段、旧图邻域、检索近邻；手动维护增加小比例随机共读和旧内容重访。先批量合并跨 worker 候选，再应用关系，避免各 worker 只能连到自己的新节点。边独立增改，新增一条边不能覆盖既有其他边。

分段是同次阅读的副产物，不能替代语义任务。普通原件先用稳定的结构分段即可，需要智能边界时再利用同次阅读；不为追求全量智能分段延迟可用版本。

**完成：** 文字问题能召回图片；相关图像能定位原图/页；低字面相似度任务能沿至少一条有依据的跨材料关系找到关键资料；矛盾、更正、删除、节点合并和重复维护有正确结果。只报告有效关系的例子、错误和未测范围，不用边数阈值结案。

### P3 主动提示与增量维护

**动作：** 通过短入口 skill/项目指令在任务开始或接续时调用 `brief`；按任务触发小批变化处理，手动深维护调用同一处理入口。自动维护仅发生于任务过程中，不建设常驻后台 agent。

主动提示优先使用短项目地图、最近变化和相关决定/条件，再按有限预算轮换探索线索。启动不重新遍历全文；初建负责已声明范围的整体整理，后续按变化和重访扩充。已有项目允许分批建库并清楚说明剩余资料。

默认从文件清单、大小和时间等低成本信息发现变化，实际读取时绑定内容版本；不每查询都遍历/哈希全部权重、原件和历史快照。已知变更影响的知识标为待更新或历史，更新前不冒充当前结论。所有资料已登记、已经读过、已经形成语义和已经能检索是不同覆盖信息，直接从实际记录汇总，不另建四套工作流。

如采用「已知必读」执行建议：将少量已确认前提直接传给工作 agent，作为探索性候选的补充；预算不足时明确尚未交付的内容。先用简单显式列表，不复制旧 map 平台和通用依赖推理器。该建议尚未确认，不作为用户要求或其他阶段的前置条件。

**完成：** 在未指示检索的任务中，主 agent 通过启动线索发现一个原本未点名的相关前提；任务内修改资料后能完成一次真实增量维护；自动预算结束能说明下次位置，手动处理可以继续；全程没有被流程要求反复完整载入长合同。

### P4 小型独立评估与机械盘检查

**依赖：** P2/P3 核心行为形成。早期就用 P0 的小样例回归，不等本阶段才第一次试完整闭环。

用约 8–12 个固定任务覆盖主动未知提示、精准查找、跨材料关系、图片、更正/删除、范围隔离和失败。比较三组：普通文件工具；短常驻信息加文件工具；完整记忆。需要时做一次去掉图的消融，确认收益来自哪里。评测起点不用建设聊天 fork，不把答案和评分材料放入被测可见目录；固定模型配置、任务输入和资料范围，报告实际可观察的配置。

| 维度 | 记录方式 |
| --- | --- |
| 质量 | 预先列出的必要信息找回/漏项，错误和过期事实，原文是否支持答案 |
| 主动性 | 未提示检索的任务中发现了什么；不能据几个成功样例宣称解决所有未知未知 |
| 上下文 | 工作 agent 实际收到的字符数、检索委托次数；有宿主 token 数据时再记 token |
| 成本 | 初建、更新、worker 与主 agent 的总墙时/可得用量；无价格或计量则留空，不用字符冒充费用 |
| 维护 | 改动后的正确性、重复处理量、待处理范围、失败是否可定位 |
| I/O | 文件数、读写量与频率；在真实机械盘或明确标注的替代条件上观察，区分冷/热启动 |

**完成：** 核心行为样例通过，报告各任务的收益、无收益或未定条件及成本；即使未发现净收益也如实结束本阶段。质量无收益或维护成本明显过重时，先收敛导致问题的机制，不扩大语料掩盖问题。报告不足以决定时记录未定，不用无限扩测拖延交付。

### P5 独立目录安装试用

**动作：** 在一个与开发目录分离的试用项目安装，使用小型代表性公开/合成资料跑首建、检索、正常修改、任务内维护与手动深维护；再使用另一个独立目录核隔离。若用户已指定真实业务资料，按其范围替换其中一组；未指定时不擅自把旧业务项目变成新试验。

**完成：** 换路径后可用，不依赖旧项目的可变文件或数据库；发现实例问题只回改产品维护源再安装，不产生业务分叉；输出一个短试用报告。真实新业务项目的效果待指定资料后验证，公开/合成安装试用不替代该结论。至此可发布第一版完整记忆工具，不等待后两种工具全部完成。

### P6 资源协调工具

**当前优先实施：** 2026 年 11 月 7 日用户指定下一阶段先做本工具，详细步骤、共享 embedding 接法和验收按 [资源协调专项计划 R0–R5](resource-coordination-plan.md) 执行。本节保留总体边界；独立资源工具不以记忆底座选型、建库或评估为前置条件，所需环境确认纳入 R0。

R0 先交付系统 Python 包、公共配置和初始化入口，再按 embedding/Condor 各自探针分别放行 R1/R2；R3 汇合验收。共享服务生命周期独立于普通作业，具体启动、账户、请求隔离和预算发布合同以专项计划为准。

先以两个项目争用同一 GPU 为场景，统一 `submit/status/cancel` 等少量动作。任务明确 executable、参数、工作目录和 CPU/内存/GPU 请求；共享调度保存资源与任务元数据，项目资料和记忆留在项目内。共享代码与本机管理配置分开。

优先提取 [已核实的旧 runtime、服务与进程清理](research/resource-coordination.md)，复用已经安装的 HTCondor 及其 CLI。embedding 保持独立共享服务，建库与查询共用实例；其他重任务由 Condor 排队，通过固定预留 embedding 峰值和系统余量，使二者按显存预算并行。旧整卡锁和 13 GiB 启动门槛改造后再接入；外部直接启动的程序仍需使用者协调。Condor 的当前认证、实际提交、路径、结果与取消按本次验证，不以历史轻任务回执代替。

**完成：** 两项目共用同模型实例，embedding 与预算容许的普通 GPU 作业真实重叠执行；两种启动顺序、作业内请求 embedding、取消与异常回收均可用。普通 GPU 作业之间首版可串行；CPU/RAM 按声明额度预留排队，不把预留等同于 OS 硬限制；无法满足的请求说明原因，空闲无高频写盘。详细验收以专项计划为准。

### P7 分层 agent 组织

2026 年 11 月 7 日按用户要求先交付 [agent-team skill](../../../skills/agent-team/SKILL.md) 指令层初版；[参考与检查](research/agent-team.md) 记录高星项目筛选、公开实测和本机行为验证。以下真实广读对照仍是本阶段的完成条件，初版不代表 P7 已验收。

从 P1/P2 的实际派工提炼短角色 skill 和任务包。任务包只含目标、范围、必要材料入口、约束、输出和预算。返回包含结论、直接依据、已做动作、缺口/下一位置；有相关内容就返回内容，长证据给精确链接。链接只是入口，关键判断者仍要读必要依据。

主 agent 负责目标和高层取舍；协调 agent 定界、派工、管理依赖并汇总；执行者按任务难度选择模型，广读可采用低成本模型。人数和层级随任务及阶段调整，简单任务跳过协调层；记忆建图团队仍遵守纲领中的专项约定。新主题使用干净起点避免无关历史，同一任务需要续读时可沿同 worker 继续，不建设独立的上下文认证流程。

**完成：** 一个广读任务在单 agent 和分层方式下各跑一次，按 [性能定义](../../terminology.md) 比较能否完成、覆盖与遗漏、判断及成果质量；主 agent 能依据精选材料决策，执行者的重复劳动与遗漏可见。主上下文、总用量和耗时作为代价另行记录，允许增加用量换取性能提升，不以省额为验收条件。模型名称和推理强度放配置，角色不写死为某一代型号。

### P8 联合交付与轻量发布

联合场景：业务主 agent 提出资料问题 → 检索团队返回证据 → 项目有变更时增量维护 → embedding 等重任务经过资源协调 → 新结果保持项目局部。短文件读取和每次 agent 派工不进入重任务队列。

发布仅包含源码、skills、安装配置、依赖声明/必要锁、小样例和短文档。权重、虚拟环境、数据库、缓存、原始聊天、业务资料、大测试结果及多份升级备份不进 Git 或发行包。版本通过可用的远端/包索引恢复依赖，通过配置绑定本机共享资产；不把本机绝对路径当作安装要求。

建议第一版预算：被跟踪文件的逻辑总大小目标不超过 **20 MiB**、普通单文件不超过 **2 MiB**，发行压缩包目标不超过 **10 MiB**。这些是 agent 提出的起始预算，用户可调整；例外先说明具体必要性，优先外置。实施时直接基于待提交文件计算，并看仓库历史有没有误纳大对象，不仅量压缩包。初始源码从新仓库开始，不导入旧 Git 历史。

调研时 [basePack](https://github.com/YS-Pan/basePack) 连接器返回 public、默认分支 main、size=0；这不单独证明无提交，首次推送前读取实际远端引用。新路径安装、核心闭环和发布清单检查完成后再发布。

## 工作方式与停止条件

- 一个功能批次一个主 owner；不同人可并行研究/写独立模块，写同一数据存储和最终整合顺序执行。
- 先验证完整的最短实际流程，再补局部优化。修复真实事故保留一个对应回归，不照搬旧测试矩阵；文档小改只检查相关内容和链接。
- 避免静默 fallback、广泛 catch 和猜测成功。错误直接返回可操作原因；完成标准达到即结束该批，不再追加假想风险检查。
- 默认不做层层复审，运行数据优先批量写入，不每细修就完整打包安装。形成可用功能批次后统一发版；阻断用户的具体缺陷可单独修。开发变更记录按文档维护规则逐次保存。
- 控制常驻入口：建议项目启动说明约 1,500 字符内、单个通用 skill 约 3,000 字符内，细节按需链接。超出时删重与拆按需资料，不增加新的全量必读链。
- 原始材料和已知更正需可回查；索引可重建。首版使用数据库事务与必要内容版本即可，不建设全面快照、协议签名或审计平台。
- 阶段结束只记录结果、实际检查、余项及设计决定；不把长过程复制到战略计划。用户新指令改变范围时更新本执行计划和唯一进度来源，避免讨论中的要求丢失。
