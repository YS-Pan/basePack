## 三、暴露的问题及其新旧边界

| 问题 | 证据与影响 | 判断 |
| --- | --- | --- |
| 官方数据库示例Origin漏端口 | administrator.md的allow-origin只写127.0.0.1，默认WebSocket Origin含项目端口；HTTP init可用而publish握手403。本项目改为完整endpoint，同一冻结稿成功接续 | 新的明确部署文档缺陷；失败发生在事务前 |
| 私有标记与业务布局冲突 | 业务正文按用途保存，另复制到private/memory-sources以获得private标记；需要选择清单、映射及原件→镜像→accepted三层hash。镜像中的相对链接还须按原正文目录解释 | 本次显现的设计张力和持续同步成本，不直接等于程序缺陷 |
| 私有保存被扩大为脱敏工程 | 本地私有库没有公开分享要求，但执行者增加匿名化副本；规则误伤技术数字和书目信息，引入定向恢复、多轮材料修订与重新发布 | 额外流程与项目自写工具问题；不是basePack建库必需成本 |
| collector权限使文件维护一并中断 | SQLite code 14已知；新项目中整条maintain失败并已取得owner，执行者自写file-only包装才继续官方文件流程 | 权限是已知问题，新的实用影响是官方CLI缺少可直接使用的文件路径；不要静默忽略采集失败 |
| 误把chunks排除当作源快照清理 | 一行元数据未进chunk但仍进完整source snapshot；后改源并未清除旧快照 | 已有合同的真实误用，无外传证据；应在必要入口讲清存什么，不能加一般性审计来替代 |
| 协作状态误判 | 连续向已completed作者send_message，修正没有开始；root用followup_task后才实际恢复 | 本次可定位的调度执行问题，非basePack数据库缺陷 |
| 草稿／冻结稿、关系ID与rank输入错误 | 已冻结稿误走completed入口、关系缺id报裸KeyError；后续rank两次不合输入合同。纠正后继续，错误批次未开始事务 | 多为既有合同下的执行偏差；缺关系ID在旧调查已有，不能重复包装为全新发现。裸错误的定位信息仍可改善 |

当前仍可定位的Origin示例在[administrator.md](../../../../experiments/20261106-basepack/docs/administrator.md)；本轮只记录问题，没有顺手改产品。file-only包装、镜像映射和脱敏脚本属于项目自写补偿，不应被当作官方产品已经提供的能力。

多轮材料清理并不等于五次全量语义重摄入：实际存在少量变更的定点发布与未变来源复用。也没有证据证明无限自动循环。关系stale=false同时保留旧endpoint_versions属于既有历史版本合同，需要核实际端点，不能只凭字段名认定当前关系错误。

## 四、建议的后续顺序

1. 修正已证实的Origin示例，并保持接入验收包含一次真实publish／查询／回源；只看doctor、ready或init不能覆盖发布连接。
2. 提供明确、受支持的文件维护入口，保留聊天采集失败与覆盖缺口；文件工作不应要求每个项目复制维护布局和派工内部调用。owner失败收尾仍须明确，不能吞异常后宣称全量成功。
3. 先确定整项目私有与可公开分享的实际边界，再决定来源布局。评估如何减少canonical与私有镜像双维护；已有私有本地保存不默认追加匿名化。确需净化时，先稳定有界来源再摄入，实际变化只回到原作者和受影响版本。
4. 保留E，下一步优先处理协调者上下文、消息正文和等待粒度。按已完成的有界任务考虑交接或新上下文，已知步骤合并调用；从现有真实日志继续观察，不先扩建完整cycle或另一套状态台账，也不简单把工作转给root后宣称省费。
5. 沿后续真实业务核复用质量、漏检和完整本地分项。新项目已证明可用；低成本与质量净收益仍是未解决目标，不另起全量维护或合成评测来替代业务证据。

### 新增的明确问题是求解器并行与内存

首次多频点求解实际并行3个频点，占满内存，用户手动停止。此前接入、doctor及模型能打开均没有防止这次事故。用户纠正后，执行者禁用原多频扫描、每次只启用一个离散点、设置单任务并核实际配置及profile，两个后续单点先后正常结束，单进程峰值约20.5／20.1 GB。

这说明“能调起仿真”不等于“资源受控”：单个点的内存与原生频率并行会相乘，不能只看工具调用里任务数为1。现有证据显示的是项目内PyAEDT执行与事后约束修复，没有证明共享资源协调参与了该求解。后续应在原生求解器实际并行层核内存与并发，再运行完整工作；不自动将本项目的单频要求推广为所有项目固定政策。

这也限制了自主能力结论：低指导下组织材料、计算、成稿和打包已有实际成果，但资源事故仍依赖用户发现并干预。新的mandatory保存了经验；尚无再下一轮任务证明它能防止重犯。

内存压力有可能伴随分页和高磁盘活动，但缺少当时分页／进程磁盘计数，不能倒推此前D盘100%的原因或全部归于任一聊天。没有新的Origin／合法输入失败；collector权限仍复现，文件包装仍是项目自写补偿。私有镜像的同步负担也仍在，只是本轮精选增量成功，未出现重新摄入全部历史材料的证据。
