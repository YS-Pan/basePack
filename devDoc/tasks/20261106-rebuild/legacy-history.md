## 为什么越来越难推进

可以直接从记录确认的问题有四类：讨论中的要求在计划转写时遗漏；派工目标从建图偏成分段；完整宿主流程验证偏晚，逐环修补；微小修订也反复承担发包、升级、新空安装与一致性检查。真实试用还留下不同副本的接口和锁语义冲突。

据此可以推断，复杂度的主要放大方式是：为一次具体失败加上一层状态、留痕或恢复规则，随后该层又成为需要维护、交付和审阅的对象。大量长流程进入常驻指令，使普通任务也承担维护系统的固定开销。这个判断不等于这些机制全无用途，也不能证明某种模型、Basic Memory 或日期目录本身是唯一原因。

### “递归”的边界与反证

- 未发现无限吞入自身数据库/运行产物的证据。初期[14 源合同](<D:/project/20261024 doc system/docs/context/20261104-project-memory.md:126>)显式排除实例、数据库、任务/查询轨迹及本次交付记录；后期[聊天采集](<D:/project/20261024 doc system/.context-memory/app/src/context_memory/chat_sources.py:336>)固定原件长度，[采用记录](<D:/project/20261024 doc system/docs/context/20261104-project-memory.md:104>)明确截点后待下一次同步，不承诺实时追尾。新增文件也须显式登记，链接不自动扩大范围。
- 确有把自身回答再作为历史材料的通道。[安装代码](<D:/project/20261024 doc system/.context-memory/app/src/context_memory/chat_sources.py:440>)允许 assistant 消息入库，并保留 main/subagent、role、作者与 original_prompt 身份；工具正文不按普通聊天正文保存。旧回答被重新召回可能延续错误判断，但本次未追到具体错误沿此路径自我强化的实例，不能断言它是已发生的主要故障。

对当前项目的工程启示是把自用作为有边界的使用与验证：开发可直接读取原件；按必要的小批维护已登记知识；一组相关改动完成后统一做受影响交付检查。功能验收和净收益仍靠实际任务结果判断。以上是本次调查建议，不改变项目纲领，也未修改现行工具、配置或维护权限。

本次由主 agent 与两个只读调查 worker 分查原意及实际机制，主 agent 交叉读取关键原文和回执。完整翻页核对上述两条原始需求聊天，另查[版本迭代调查](codex://threads/01a1ae6f-ce9c-7e32-b8d8-7825aafa0655)及相关旧文件/安装代码；没有重跑旧维护、索引或业务测试，未穷尽全部历史聊天。主上下文与团队总用量不可核；已有工程数量不作为本次因果验收。

## 新项目继承与舍弃

| 保留价值 | 新项目的处理 |
| --- | --- |
| 主动未知提示、项目局部记忆、成熟检索组件 | 作为核心方向，先做小范围完整闭环 |
| 精确来源、更正、历史与当前的区别 | 保留简单版本和定位；已知失效资料不能冒充当前事实 |
| 廉价 agent 广读、评分和返回精选依据 | 默认一个 worker 完成，不强制双模型复审链 |
| 任务内增量维护、手动深维护、随机共读 | 共用入口，按任务设预算，不复制旧 checkpoint 状态机 |
| 已有权重、环境及 HTCondor | 核实接口后复用；统一资源包装尚需实现 |
| 真实事故和有限结果 | 留少量回归与报告，不搬全量运行树和旧评分器 |
| 三端手工同步、多级协议、全套审计与发布门槛 | 不作为新项目默认架构或验收要求 |

最重要的证据限制是：旧项目实现了不少可用工程能力，但现有小样本、合成检索分数和安装回执，没有证明完整系统在真实项目中普遍提高质量或降低全周期成本。新项目应把这个问题放到早期直接测量，而不是继续靠功能数量证明价值。
