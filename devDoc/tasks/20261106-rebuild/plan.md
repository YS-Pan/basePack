## 复用优先

- 用户明确：简洁以自己实现和维护的代码尽量少衡量；可另行安装现成库与软件，允许适度调整行为。运行计算与存储采用本地能力，理解、建图和评分使用 Codex 订阅，不新增联网模型 API。
- 通用模型适配、服务、进程管理、检索、事务和依赖安装优先交给现成实现；自己保留来源版本、项目隔离、主动线索及必要的接入代码。候选按净删代码、剩余配置与运维负担和真实功能共同选择，移动代码或另包一层不算精简。
- 先用最短样例验证首选；不适合时记录具体缺口，再试一个备选。选定一套实现后删除本次涉及的重复逻辑；行为差异写清调用与升级方式，不为完整复制旧工程细节增加兼容层。
- 资源 0.5.0 的现行行为由 [模块说明](../../system/modules/resources.md) 维护，取舍与验收保留在 [R9 结果](../../archive/20261107-resource-coordination/r9-result.md)；记忆底座由 P0 决定。历史验收保持原条件。

## 后续维护的简化

这些做法随相关功能交付或依赖升级落实，不另设通用平台或当前阶段的前置任务。

- 环境由声明、锁文件和原生包管理命令准备，服务由现成管理器配置；保存可重建的安装来源与升级/卸载方式，避免再写依赖锁校验器、环境安装器或进程平台。
- 优先上游公开 CLI/MCP、SDK 和扩展点，原生配置与输出可直接使用时沿用。适配代码只表达项目实际差异，不为统一命名再造协议、数据模型或多后端抽象。
- 升级依赖或修复适配故障时，核上游是否已覆盖自有补丁；覆盖后删除对应实现。确需临时补丁，在代码旁保留上游依据和删除条件即可，不另建补丁台账。
- 使用底座原生 ID、事务、备份和导入/导出能力，持久知识保留一个维护源；派生索引按需重建。选型时以小样例核可恢复、可导出，减少未来更换工具的专用迁移代码。
- 实际调用方切换、在途工作结束且恢复资料保留后，按支持范围退役旧接口、旧格式、一次性迁移及对应测试/说明；旧版本从 Git/发行包回查，仍在使用的兼容只覆盖已确认调用方。
- 小资料集与公开用户流程复用于库升级和实现替换，保留项目语义及真实故障回归，随内部实现退役失用测试。命令帮助和上游文档已有的细节直接链接，项目文档只维护本项目差异和必要操作入口。

## P7 分层 agent 组织

2026 年 11 月 7 日按用户要求先交付 [agent-team skill](../../../skills/agent-team/SKILL.md) 指令层初版；[参考与检查](research/agent-team.md) 记录高星项目筛选、公开实测和本机行为验证。以下真实广读对照仍是本阶段的完成条件，初版不代表 P7 已验收。

从记忆任务 P1/P2 的实际派工提炼短角色 skill 和任务包。任务包只含目标、范围、必要材料入口、约束、输出和预算。返回包含结论、直接依据、已做动作、缺口/下一位置；有相关内容就返回内容，长证据给精确链接。链接只是入口，关键判断者仍要读必要依据。

主 agent 负责目标和高层取舍；协调 agent 定界、派工、管理依赖并汇总；执行者按任务难度选择模型，广读可采用低成本模型。人数和层级随任务及阶段调整，简单任务跳过协调层；记忆建图团队仍遵守纲领中的专项约定。新主题使用干净起点避免无关历史，同一任务需要续读时可沿同 worker 继续，不建设独立的上下文认证流程。

**完成：** 一个广读任务在单 agent 和分层方式下各跑一次，按 [性能定义](../../terminology.md) 比较能否完成、覆盖与遗漏、判断及成果质量；主 agent 能依据精选材料决策，执行者的重复劳动与遗漏可见。主上下文、总用量和耗时作为代价另行记录，允许增加用量换取性能提升，不以省额为验收条件。模型名称和推理强度放配置，角色不写死为某一代型号。

## P8 联合交付与轻量发布

联合场景：业务主 agent 提出资料问题 → 检索团队返回证据 → 项目有变更时增量维护 → embedding 等重任务经过资源协调 → 新结果保持项目局部。短文件读取和每次 agent 派工不进入重任务队列。

发布仅包含源码、skills、安装配置、依赖声明/必要锁、小样例和短文档。权重、虚拟环境、数据库、缓存、原始聊天、业务资料、大测试结果及多份升级备份不进 Git 或发行包。版本通过可用的远端/包索引恢复依赖，通过配置绑定本机共享资产；不把本机绝对路径当作安装要求。

构建、安装和测试沿 active 工程 README 执行。源码回归核导入来自该路线 src，普通安装验收核来自本次安装的 site-packages，避免误用机器已有版本；同名候选包分环境验证。“源码外”以隔离源码导入为准，验收项目、临时环境和输出可在根 tmp，长期服务环境与交付物保持稳定位置；选留原证归根 artifacts/runs，详见 [材料维护约定](../../documentation.md)。

建议第一版预算：被跟踪文件的逻辑总大小目标不超过 **20 MiB**、普通单文件不超过 **2 MiB**，发行压缩包目标不超过 **10 MiB**。这些是 agent 提出的起始预算，用户可调整；例外先说明具体必要性，优先外置。实施时直接基于待提交文件计算，并看仓库历史有没有误纳大对象，不仅量压缩包。初始源码从新仓库开始，不导入旧 Git 历史。

目标仓库为 [YS-Pan/basePack](https://github.com/YS-Pan/basePack)，首次推送前核实际远端引用和待发布清单。新路径安装与对应工具核心闭环验收完成后，按用户指令发布；历史查询结果不作为当前远端状态。

## 工作方式与停止条件

- 一个功能批次一个主 owner；不同人可并行研究/写独立模块，写同一数据存储和最终整合顺序执行。
- 先验证完整的最短实际流程，再补局部优化。修复真实事故保留一个对应回归，不照搬旧测试矩阵；文档小改只检查相关内容和链接。
- 避免静默 fallback、广泛 catch 和猜测成功。错误直接返回可操作原因；完成标准达到即结束该批，不再追加假想风险检查。
- 默认不做层层复审，运行数据优先批量写入，不每细修就完整打包安装。形成可用功能批次后统一发版；阻断用户的具体缺陷可单独修。开发变更记录按文档维护规则逐次保存。
- 控制常驻入口：建议项目启动说明约 1,500 字符内、单个通用 skill 约 3,000 字符内，细节按需链接。超出时删重与拆按需资料，不增加新的全量必读链。
- 原始材料和已知更正需可回查；索引可重建。首版使用数据库事务与必要内容版本即可，不建设全面快照、协议签名或审计平台。
- 阶段结束只记录结果、实际检查、余项及设计决定；不把长过程复制到战略计划。用户新指令改变范围时更新对应任务的计划和进度，避免讨论中的要求丢失。
