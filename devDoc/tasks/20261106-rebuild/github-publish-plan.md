完成条件：待发布文件与历史范围明确，凭据及本机运行状态未被纳入，许可处理方式已确定。

### 2 补齐面向新用户的入口

调整根 README，说明四项能力、Windows 与 Python 3.13 的支持范围、当前成熟度，并提供从 clone 到安装轻量客户端的可执行命令。包位于 `experiments/20261106-basepack`，根目录不是 Python 包；从仓库根安装须显式指定该目录。

README 给出问题记录及 [GitHub Issues 反馈入口](https://github.com/YS-Pan/basePack/issues)，根 AGENTS 与生成到业务项目的 instructions 提醒 agent 在使用中发现问题时及时记录。在本仓库按所属任务进度留存，尚无所属任务的问题先登记到重建总进度；外部业务项目沿使用者已有的记录约定，无需复制本仓库 devDoc 结构。记录问题现象、版本与必要复现条件、处理状态，按需附去除凭据及私人资料的证据；修复后补验证结果。

外部问题同时形成可复制的 Issue 草稿，包含最小复现和当地记录位置，由用户提交或授权 agent 提交。反馈入口可达、草稿可用作为流程验收内容，使当地记录能够回传作者。

路线 README 与使用文档分别给出纯文字记忆、图文 embedding、HTCondor 作业及独立 skills 的入口，按所选能力说明需要的设施。新用户无需先安装全套模型服务才能尝试文字记忆或使用通用 skills。

将通用安装步骤中的本机路径替换为用户选择的路径；本机实测留在开发说明。检查公开文档指向被忽略的 `artifacts/`、`dist/`、`.basepack/` 的引用：用户所需步骤和结论在 Git 中可读，原证注明本地保留；选用的交付 wheel 转为 Release 附件。

### 3 完成新机器首次部署与项目接续

交付内容落在 active 工程的 [部署说明](../../../experiments/20261106-basepack/docs/administrator.md)、[项目接入](../../../experiments/20261106-basepack/docs/setup-project.md)、配置与 instructions 模板、随包 memory skill 及必要实现中；产品流程集中维护，根 README 只给简短入口。

按所用能力准备设施：纯文字记忆需要客户端与独立 SurrealDB；图文检索再准备 CUDA embedding；普通重任务再接入 HTCondor；两项通用 skills 可独立使用。给出 Python 3.13、所用 uv、SurrealDB、Shawl、HTCondor 的官方安装来源和实测版本；图文路径注明支持的 GPU、显存与驱动条件，先核 CUDA 可用性。各路径从空白环境按需执行。

#### 机器首次准备

1. **数据库：** 沿现有每项目独立目录、端口和 UUID 的流程，完整交付程序安装、密码来源、launcher、启动、独立调用 ready/init/brief 与知识读写步骤。
2. **模型：** 提供固定模型 revision 的官方下载命令，说明 `model_root/model/` 布局和 `model.lock.json` 公开格式；从实际下载文件生成相对路径、大小与 SHA256，记录模型名和 revision。准备时核文件完整性，并从这份本机权重启动共享服务、完成真实图文编码。采用原生下载工具和短命令或脚本，运行请求继续复用已准备文件。
3. **Condor 与预算：** 补 Windows 单机 pool 安装、提交/执行角色、服务启动，以及主配置加载 `60_resources.conf`、`70_job_transforms.conf` 的步骤。根据当前机器 CPU、RAM 和显存设置容量，首次为 embedding 设置可用的正预算，测量背景占用并划分普通作业池；将原机数字标为样例。实际核容量、队列、提交转换、业务结果及资源归还。

#### 持续使用所需配置

项目配置作为默认检索模式的唯一维护源：纯文字路径明确选择文字默认；CLI 显式 `--mode` 优先，未传时取项目默认。同步检索 skill 和生成入口，显式 hybrid/vector 的失败保留原错。首次诊断用 core，额外设施按已选能力检查；纯文字路径的正常诊断和检索无需 embedding 或 Condor。新增配置字段时同步说明现有 0.6.2 项目的补项与升级步骤。

生成 instructions 交付每个新进程所需的凭据来源及加载办法，从当前配置读取 `password_env` 和实际 memory 目录，凭据保存在项目忽略目录或使用者选定的秘密来源。后续调用仅凭生成入口即可加载所需变量，不依赖部署 shell 的变量、函数和工作目录。该入口也定位本项目实际数据库 launcher、cwd、日志及恢复操作说明。

完成条件：从公开安装来源可准备所选设施，模型锁和容量配置可在新机器生成；项目模式、凭据和服务入口随配置及生成指令交付给后续 agent，产品文档与实际行为一致。

### 4 验证安装与持续使用

使用待发布提交生成干净副本，在根 `tmp/` 的独立 Python 3.13 环境按路线 README 安装依赖、运行已有回归并构建 wheel。先核源码回归的实际导入位置，再从源码外普通安装本次 wheel，核版本、导入位置和包内模板、schema、memory skill。临时目录与端口独立于正式项目，保留正在服务其它聊天的数据库和共享服务。

先运行客户端回归，再完成以下两类使用验收。为本次新增或修复的实际行为保留对应的小型回归。

#### 空白环境首次部署

在空白 Windows 实机或虚拟机中，使用待发布源码和公开文档，从头准备所需工具及设施。作者机的独立 venv 只作为客户端回归；新机演练使用自己的机器配置、数据库、模型下载和新建服务，不挂载作者的现存模型目录或连接作者已有设施。图文与 GPU 作业路径须在支持 CUDA 的实机或等效隔离环境验证。

验证最短实际流程：

1. 新项目 `init` → 配置 → `memory init/brief` → 示例 `prepare/apply/search/read/neighbors`，完成纯文字记忆闭环。
2. 宿主订阅 agent 读取两份小材料，实际完成一次分块、关系写入与评分检索；修改一份材料后执行必要的小批维护，验证新知识和旧依据的状态。
3. 从头准备模型和锁文件，使用新建共享服务完成图文编码/检索；新建 Condor pool 完成一个小型 CPU 作业，再让 embedding 与一个申报显存的小型 GPU 作业并存，核业务输出、终态、进程退出和资源归还。模型服务可供该机器多个项目复用，各项目配置与数据独立。
4. 在新目录核对两项通用 skills 的可发现性和使用入口；分层协作尚未完成的质量对照按现状披露，不扩成首次上传前的新研究任务。

#### 新 shell 与新聊天接续

首次部署调用结束后，开启干净的新 shell 和新的 agent 聊天，按生成的 `AGENTS → instructions` 入口执行诊断、凭据加载、`brief` 和实际检索。新 agent 仅接收试用目标，依靠仓库与生成入口定位路径、加载办法和操作步骤。纯文字项目在无 embedding、无 Condor 的环境完成默认检索；图文项目按配置完成默认混合检索。核外部业务项目能找到问题记录提醒和反馈入口，并形成一份可提交的最小问题报告草稿。

完成条件：必要回归、空白环境的所选能力、新 shell 和新聊天接续均通过。记录提交、wheel SHA256、实际环境、独立部署的设施、结果与未测范围；缺硬件或安装条件的路径明确记为待验，不能以复用作者服务的结果替代。验证中发现的问题有记录和处理状态；已有质量和费用结论保持其原边界。

### 5 上传源码

完成上述准备后汇总待推送提交、变更摘要、按能力划分的验收结果及待验路径，公开支持范围与这些结果一致。后续收到上传指令再操作远端。

执行时重新核对目标仓库及远端引用，配置 `origin`，预览推送内容，再将本地 `main` 正常推送至目标 `main`。若远端期间有新增提交，先核对内容与历史关系再处理，保留双方有效修改。同步简短的仓库简介与能力说明。

完成条件：GitHub `main` 的 SHA 与验收提交一致，首页、相对链接及源码目录可正常浏览。

### 6 核验分发并按需发布附件

从 GitHub clone 到另一目录，按公开 README 重新安装轻量客户端并运行最小文字记忆流程；再从干净新 shell 核生成入口和默认检索，核独立 skills 的分发入口。这一步检验 Git 忽略和本机文件是否造成遗漏；新机器设施的从零验收仍以第 4 步为准。发布后的实际使用继续兼作测试样本，沿同一入口记录问题、形成反馈并跟进处理。

如需直接下载 wheel，在已验收提交打版本 tag 并建立对应 Release，附本次 wheel、SHA256、简短功能与支持范围说明；版本号以最终交付包为准。PyPI、跨平台支持与更广泛性能评测另按需求安排。

完成条件：远端 clone 的新用户流程通过；如提供 Release，tag、源码、包内版本及附件一致。
