# 开发文档组织与维护

`devDoc/` 服务于理解、修改和验证 basePack 的开发工作，读者包括开发者与 agent。根目录 AGENTS.md 是简短入口，按任务进入相关文档。未来使用者的操作流程与管理员维护流程按实际职责另行编写。

## 内容归属与读取条件

| 位置 | 内容与读取条件 | 更新时机 |
| --- | --- | --- |
| `project-charter.md` | 用户目标与长期要求；涉及目标和取舍时读 | 用户意图变化且同意修改正文时 |
| `terminology.md` | 项目特有概念的边界；遇到歧义时查 | 新概念或既有用词需要澄清时 |
| `current/overview.md`、`architecture.md` | 已有实现的总览、流程、职责、外部边界与不变量；了解现状或跨模块修改时读 | 实现、模块关系、数据所有权或边界变化时 |
| `current/environment.md` | 开发入口、环境实测及未核范围；准备运行或诊断环境时读 | 环境核验或开发入口变化时 |
| `current/modules/模块名.md` | 已实现模块的意图、行为、输入输出、数据责任和非显然设计；修改对应模块时读 | 模块职责、公共接口、关键约束或设计理由变化时 |
| `work/开始日期-主题/` | 活动工作的计划、调查、决定、进度与结果；执行对应工作时读 | 工作推进或范围、依据、决定变化时 |
| `archive/原工作目录名/` | 已结束工作的完整材料；追溯理由或证据时读 | 工作结束后整体迁入；历史结论保留原意 |
| `change_log/major/`、`minor/` | 已发生的重要变化；查找变化及影响时读 | 每次有意义的变更新建记录 |

现行说明描述实际实现，待实施方案留在工作目录。源码、配置和命令帮助中易查的细节优先链接原处。环境实测是有日期的观测，兼容性要求由依赖声明与实际验证支持。

## 工作与证据

- 按独立工作目标建立 `YYYYMMDD-short-topic/`。同一大阶段的步骤留在其中，小任务沿用已有文件；目录随内容增长。
- 交接材料说明问题缘由、必要证据、目标与范围、已定约束、待决事项和完成条件，让接手者按相关材料开工。
- `progress.md` 集中记录当前阶段、完成事项、阻碍和下一步。调查来源和适用范围放 `research/`，重要决定及理由放在相关计划或结果中。
- 研究或验证结束时，在现有文档的结案部分或 `result.md` 中写明结论、条件、实际检查、证据位置、限制及后续入口。区分已经交付、仅有开发证据和仍未解决的目标。
- 大型产物留在仓库外或忽略目录，结果文档保留定位、生成条件和必要版本信息。保持同一主题的材料与附件相邻。

## 变更记录

`major/` 记录整体方向、架构、关键能力或工作方式的重要变化，`minor/` 记录有意义的局部改进和修复，特别小的修改省略。每次变化一个文件，按记录创建时间（北京时间）命名为 `YYYYMMDD_HHMMSS_short-description.md`，记录变化、原因、影响、实际检查和必要依据。记录说明结果，详细证据链接到对应工作。

## 更新与归档

1. 先更新实际受影响的现行说明、任务材料和入口；保持每类内容的维护位置明确。
2. 检查改动涉及的路径、相对链接、标题锚点、UTF-8 和差异。迁移纲领或原始快照时核对原文及 Git 字节保护路径。
3. 工作完成、终止或被替代时，更新仍需维护的现行结论，记录结束原因，并将未完成事项交接到后续工作。
4. 将整个工作目录移入 `archive/`，保留目录名并修复链接。归档表示工作已结束，结论是否适用仍按证据判断。

产品模块落地时同时补充对应说明。只有模块级说明不足以表达某个复杂文件的契约时，才增加文件级文档。尚无内容的模块、归档和记录分类按需创建。
