# 开发文档组织与维护

`devDoc/` 服务于理解、修改和验证 basePack 的开发工作，读者包括开发者与 agent。根目录 AGENTS.md 是简短入口，按任务进入相关文档。当前 active 路线的用户与管理员流程位于 `experiments/20261106-basepack/docs/`，路线 README 给出产品与执行入口。

## 内容归属与读取条件

| 位置 | 内容与读取条件 | 更新时机 |
| --- | --- | --- |
| `project-charter.md` | 用户目标与长期要求；涉及目标和取舍时读 | 用户意图变化且同意修改正文时 |
| `terminology.md` | 项目特有概念的边界；遇到歧义时查 | 新概念或既有用词需要澄清时 |
| `system/overview.md`、`system/architecture.md` | 已有实现的总览、流程、职责、外部边界与不变量；了解现状或跨模块修改时读 | 实现、模块关系、数据所有权或边界变化时 |
| `system/deployment.md` | 当前 active 路线的源码、实例、配置与安装合同；修改布局或部署时读 | 合同实际变化时 |
| `system/environment.md` | 开发入口、环境实测及未核范围；准备运行或诊断环境时读 | 环境核验或开发入口变化时 |
| `system/modules/模块名.md` | 已实现模块的意图、行为、输入输出、数据责任和非显然设计；修改对应模块时读 | 模块职责、公共接口、关键约束或设计理由变化时 |
| `tasks/开始日期-主题/` | 开发任务的计划、调查、决定、进度与结果；执行对应任务时读 | 任务推进或范围、依据、决定变化时 |
| `archive/原任务目录名/` | 需保留的已结束任务材料；追溯理由或证据时读 | 任务结束后整体迁入；archive 始终存在，可为空 |
| `change_log/major/`、`minor/` | 已发生的重要变化；查找变化及影响时读 | 每次有意义的变更新建记录 |
| `../tmp/` | 一次性测试、临时脚本、夹具、构建缓存及其他一次性内容的默认位置；内容由 Git 忽略 | 按任务分组，任务结束后可随时清除 |
| `../artifacts/runs/<run-id>/` | 选留的运行、评测和迁移原证，包括输入、脚本快照、日志和输出；复核结果时读，Git 忽略 | 需要长期保留时从临时内容中选取 |

每个 project 只维护根目录这一套 devDoc。实验工程保存代码、依赖、配置、测试、用户文档和简短入口，计划、进度与结果正文在根任务材料维护；新路线短期比较后收敛 active，退出路线的必要结论与切换理由进入根历史。系统说明描述当前 active 路线的实际实现，待实施方案留在任务目录。源码、配置和命令帮助中易查的细节优先链接原处。环境实测是有日期的观测，兼容性要求由依赖声明与实际验证支持。

## 工作与证据

- 在 `tasks/` 按独立工作目标建立 `YYYYMMDD-short-topic/`。同一大阶段的步骤留在其中，小任务沿用已有文件；目录随内容增长。
- 交接材料说明问题缘由、必要证据、目标与范围、已定约束、待决事项和完成条件，让接手者按相关材料开工。
- `progress.md` 集中记录当前阶段、完成事项、阻碍和下一步。调查来源和适用范围放 `research/`，重要决定及理由放在相关计划或结果中。
- 研究或验证结束时，在现有文档的结案部分或 `result.md` 中写明结论、条件、实际检查、证据位置、限制及后续入口。区分已经交付、仅有开发证据和仍未解决的目标。
- 一次性内容优先放 `tmp/<task>/`，按任务结束后随时可能被清除使用，例如每日清理。源码、长期配置、服务状态和交付成果使用各自的稳定位置；任务结束前，将需要保留的结论写入文档，原始证据按长期复核需要选留到根 `artifacts/runs/<run-id>/`。结果文档保留证据位置、生成条件和必要版本信息，相关材料与附件相邻。

## 变更记录

`major/` 记录整体方向、架构、关键能力或工作方式的重要变化，`minor/` 记录有意义的局部改进和修复，特别小的修改省略。每次变化一个文件，按记录创建时间（北京时间）命名为 `YYYYMMDD_HHMMSS_short-description.md`，记录变化、原因、影响、实际检查和必要依据。记录说明结果，详细证据链接到对应工作。

## 更新与归档

1. 先更新实际受影响的系统说明、任务材料和入口；保持每类内容的维护位置明确。
2. 检查改动涉及的路径、相对链接、标题锚点、UTF-8 和差异。迁移纲领或原始快照时核对原文及 Git 字节保护路径。
3. 工作完成、终止或被替代时，更新仍需维护的现行结论，记录结束原因，并将未完成事项交接到后续工作。
4. 将需要保留的已结束任务目录整体移入 `archive/`，保留目录名并修复链接。归档表示任务已结束，结论是否适用仍按证据判断。

产品模块落地时同时补充对应说明。只有模块级说明不足以表达某个复杂文件的契约时，才增加文件级文档。`archive/` 始终保留，空目录通过 `.gitkeep` 纳入 Git；尚无内容的模块和记录分类按需创建。
