# 开发文档组织与维护

`devDoc/` 服务于理解、修改和验证 basePack 的开发工作，读者包括开发者与 agent。根目录 AGENTS.md 是简短入口，按任务进入相关文档。当前 active 路线的用户与管理员流程位于 `experiments/20261106-basepack/docs/`，路线 README 给出产品与执行入口。

## 内容归属与读取条件

| 位置 | 内容与读取条件 | 更新时机 |
| --- | --- | --- |
| `project-charter.md` | 用户目标与长期要求；涉及目标和取舍时读 | 用户意图变化且同意修改正文时 |
| `terminology.md` | 项目特有概念的边界；遇到歧义时查 | 新概念或既有用词需要澄清时 |
| `system/overview.md`、`system/architecture.md` | 已有实现的总览、流程、职责、外部边界与不变量；了解现状或跨模块修改时读 | 实现、模块关系、数据所有权或边界变化时 |
| `system/deployment.md` | 当前 active 路线的源码、实例、配置与安装合同；修改布局或部署时读 | 合同实际变化时 |
| `system/project-data-layout.md` | `.basepack` 内部推荐结构、运行数据与临时/选留材料边界；生成产物或清理本机数据时读 | 目录职责、生成位置或保留规则变化时 |
| `system/environment.md` | 开发入口、环境实测及未核范围；准备运行或诊断环境时读 | 环境核验或开发入口变化时 |
| `system/modules/模块名.md` | 已实现模块的意图、行为、输入输出、数据责任和非显然设计；修改对应模块时读 | 模块职责、公共接口、关键约束或设计理由变化时 |
| `tasks/开始日期-主题/` | 开发任务的计划、调查、决定、进度与结果；执行对应任务时读 | 任务推进或范围、依据、决定变化时 |
| `tasks/ongoing/` | 有期限、可随业务顺手处理的简单有界整改；主任务按[索引](tasks/ongoing/README.md)选择当前范围内的有效主题 | 创建、明确改期或归档时同步索引 |
| `archive/原任务目录名/` | 需保留的已结束任务及到期主题材料；追溯理由或证据时读 | 整体迁入并说明原因；archive 始终存在，可为空 |
| `change_log/major/`、`minor/` | 已发生的重要变化；查找变化及影响时读 | 每次有意义的变更新建记录 |
| `../tmp/` | 一次性测试、临时脚本、夹具、构建缓存及其他一次性内容的默认位置；内容由 Git 忽略 | 按任务分组，任务结束后可随时清除 |
| `../artifacts/runs/<run-id>/` | 选留的运行、评测和迁移原证，包括输入、脚本快照、日志和输出；复核结果时读，Git 忽略 | 需要长期保留时从临时内容中选取 |
| `../private/` | 因隐私、机密、版权或许可需限制分发的原件、附件及相关分析；需要这些依据时读，整体排除公共 Git 与发行 | 按资料实际变化维护独立本机 Git，备份入口见其本机 README |

每个 project 只维护根目录这一套公共 devDoc。实验工程保存代码、依赖、配置、测试、用户文档和简短入口，计划、进度与结果正文在根任务材料维护；新路线短期比较后收敛 active，退出路线的必要结论与切换理由进入根历史。系统说明描述当前 active 路线的实际实现，待实施方案留在任务目录。源码、配置和命令帮助中易查的细节优先链接原处。环境实测是有日期的观测，兼容性要求由依赖声明与实际验证支持。

## 私有资料

按内容、使用权限及用户公开意图确定分发边界。隐私、机密以及因版权或许可需限制分发的原件、附件、人工分析与摘录进入根 `private/`；可公开访问的论文原文也可归入，不要求含个人隐私。文献原件及来源、版本、获取时间、校验值放 `private/sources/<主题>/`，可公开的书目信息、链接与自主分析仍按其公开口径留在公共文档；本机保存不授予再分发权。任务依据可在 `private/devDoc/tasks/<同一task-key>/` 保存，公共计划、进度和交付结论仍在唯一维护源。先定分发边界，再按寿命选择 `private/tmp/` 或 `private/artifacts/` 等位置。通用布局、独立 Git 及迁移验收见 [private-context](../skills/file-structure/references/private-context.md)。

公开正文完整表达可公开的需求、决定与必要理由。需要追溯时，用中性项目相对路径标注“私有来源，可选”，按引用位置换算；文件名、标题和路径本身也须可公开。只有明确标记的可选私有引用可免于公开链接存在性检查。缺少私有区时，公开安装、构建、测试、文档生成与产品运行仍可独立使用。本机记忆发现及缺失来源处理沿 [记忆合同](../experiments/20261106-basepack/docs/memory.md#私有资料与分享边界)，已发布快照按原合同回读。

`private/.git/` 保持完整独立的本机历史，公共仓库忽略整个 `/private/`；两仓分别检查和提交，私有仓库维护自身忽略与独立备份，不复用公共 remote 或自动上传。迁移期临时路径检查在验收后撤除。受管记忆副本、图片 assets 和工作包仍在既有受忽略的 `.basepack/`、`tmp/` 等位置，按本机私有运行材料保管；根目录的忽略或私有 Git 均不代表加密、访问控制或独立备份。

## 工作与证据

- 在 `tasks/` 按独立工作目标建立 `YYYYMMDD-short-topic/`。同一大阶段的步骤留在其中，小任务沿用已有文件；目录随内容增长。
- 交接材料说明问题缘由、必要证据、目标与范围、已定约束、待决事项和完成条件，让接手者按相关材料开工。
- `progress.md` 集中记录当前阶段、完成事项、阻碍和下一步。调查来源和适用范围放 `research/`，重要决定及理由放在相关计划或结果中。
- 研究或验证结束时，在现有文档的结案部分或 `result.md` 中写明结论、条件、实际检查、证据位置、限制及后续入口。区分已经交付、仅有开发证据和仍未解决的目标。
- 一次性内容优先放 `tmp/<task>/`，按任务结束后随时可能被清除使用，例如每日清理。源码、长期配置、服务状态和交付成果使用各自的稳定位置；任务结束前，将需要保留的结论写入文档，原始证据按长期复核需要选留到根 `artifacts/runs/<run-id>/`。结果文档保留证据位置、生成条件和必要版本信息，相关材料与附件相邻。

## 变更记录

`major/` 记录整体方向、架构、关键能力或工作方式的重要变化，`minor/` 记录有意义的局部改进和修复，特别小的修改省略。每次变化一个文件，按记录创建时间（北京时间）命名为 `YYYYMMDD_HHMMSS_short-description.md`，记录变化、原因、影响、实际检查和必要依据。记录说明结果，详细证据链接到对应工作。

## 持续整改

`tasks/ongoing/README.md` 只列主题、到期时间投影、匹配职责／路径、状态和计划链接；每主题在 `YYYYMMDD-short-topic/plan.md` 维护一份短计划，写缘由、客观命中、范围、验证、结束条件及未完范围。主题只承接正常业务中可顺手处理的简单有界整改，不另设后台任务或问题数据库。

- **时间维护源：** 主题头的 `created_at`、`expires_at` 使用带 `+08:00` 的 ISO 8601 时间；默认实际创建后 7 天（168 小时），也可明确指定其他有限期限。`created_at` 保持不变，创建或明确改期时同步索引投影；普通编辑、命中或修复不续期，也不复制新条目规避期限。
- **按范围读取：** 主任务读一次索引，先按投影定位到期候选，只核其时间元数据和未完摘要，再按已定工作范围选择有效主题；子任务由 brief 交接相关主题。在本来需要的阅读、修改与验证中核具体命中，必要时核直接调用方、消费者及相邻测试和文档，以已有依据可确认、可独立验证的简单问题为边界，实际整改服从本次授权。无命中不写检查报告，也不在收尾审计全部主题或全仓扫描。
- **复杂问题交接：** 需要专门调查、跨任务共读历史判断哪些任务真正结束、批量整理迁移及链接修复、公共合同改变、运行数据变更或生产操作时，只将问题与必要依据记入普通任务，后续按其授权处理；这些工作不作为 ongoing 主题或顺手整改执行。
- **到期归档：** `now >= expires_at` 即失效。正常任务发现时，核源／目标及冲突，把整个主题目录移至现有 `devDoc/archive/<原主题目录名>/`，不覆盖已有归档；保留原时间，补 `archived_at`、归档原因及未完范围，未完成标“到期归档，未完成”。移除活动索引项，修复受影响的直接引用及目录内相对链接。到期不等于目标完成，归档材料仅作历史参考；记忆检索命中的旧主题同样核期限与活动状态。
- **其他结束与写入边界：** 用户撤销、合同替代或有边界目标真正完成时也可归档，分别说明原因。当前指令明确禁止文档写入／移动时，仅提示到期待归档，失效主题不再执行；正常允许文档维护时直接按上述规则归档。
- **单一记录源：** 具体处置、版本、复现条件和验证沿所属任务 progress／结果、现有 change_log 与 Git 保存，主题不复制事件台账；无所属任务沿总进度登记，记忆疑点仍走 memory feedback。主题的历史原证、恢复材料和真实协议身份按原职责保留。

## 更新与归档

1. 先更新实际受影响的系统说明、任务材料和入口；保持每类内容的维护位置明确。
2. 检查改动涉及的路径、相对链接、标题锚点、UTF-8 和差异。迁移纲领或原始快照时核对原文及 Git 字节保护路径。
3. 工作完成、终止或被替代时，更新仍需维护的现行结论，记录结束原因，并将未完成事项交接到后续工作。
4. 普通任务目录不因完成、终止或被替代而自动移动，也不例行扫描判断任务退役。用户明确要求归档判断或批量整理时，作为普通任务核实依据与范围；归档时整目录移入 `archive/`，保留目录名、说明原因并修复链接。持续整改主题另按上节处理；结论是否适用仍按证据判断。

产品模块落地时同时补充对应说明。只有模块级说明不足以表达某个复杂文件的契约时，才增加文件级文档。`archive/` 始终保留，空目录通过 `.gitkeep` 纳入 Git；尚无内容的模块和记录分类按需创建。
