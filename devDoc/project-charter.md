# 项目纲领

本项目的内容是搭建和测试几个工具，用于提升 AI agent 的能力，让人和 agent 更容易在实际项目中使用这些工具。

几个工具分别是

1. 记忆系统。让 agent 在开始工作时了解项目需要注意的事情，在需要时找到相关信息和原始依据。
2. 资源协调系统。协调多个项目同时做重任务时使用的计算资源，优先处理 GPU 和显存争用。
3. AI agent 的组织体系。主 agent 专注高层决策，协调 agent 负责管理与派工，执行 agent 处理具体工作。组织方式随任务而定。
4. 文件结构建议。以 skill 的形式提供可选的文件组织方式，供人和 agent 使用。

## 记忆系统

### 核心目的

1. 解决“不知道”。在“知道自己不知道”的时候，能检索到需要的信息，并沿依据回到原文、图片或聊天。
2. 解决“不知道自己不知道”。AI 没有主动检索的时候，也应当通过记忆系统收到项目的关键要求、线索和已知缺口，让它至少达到“知道自己不知道”的水平。这一条是核心中的核心。
3. 低成本。包括建库时的低成本，检索时的低成本，维护时的低成本。

### 额外要求

1. 局部且独立。项目知识、来源、任务状态和数据库保存在对应的 project 内，只在该项目生效。通用工具、依赖、模型和机器资源管理可以显式共用，避免重复安装和保存。
2. 项目私有资料默认纳入同一项目的本机记忆。私有来源及由它们派生的知识和关系应带有可识别的私有标记。
3. 避免过多小文件读写，应当能在机械硬盘上正常使用。

### 记忆系统相关的思想

1. 关于解决“不知道自己不知道”。逻辑上讲，解决这个问题，必然需要某种全局遍历。遍历的方法有：
   1. 低成本低性能的遍历，在每次检索的时候都执行。比如用脚本进行全库文字匹配搜索。
   2. 高成本高性能的遍历。比如用 ai agent 读取所有文件。
   3. 低成本高性能的遍历。这是本项目内容的核心。它是上两种的混合，先进行高成本高性能的遍历，建立数据库。已有的大项目可以分批进行。这个数据库包含特殊的内容和格式，使得它能被低成本的检索，并得到高性能的结果。

2. 关于图数据库的建立和维护。这个工作由ai agent执行。
   1. 如果想让ai agent发现两份材料之间的关系，那么这两份材料必须首先都同时在它的context里，否则不可能发现相关性。
   2. 某一个相关性在被发现之前，ai agent处在“不知道自己不知道”这个相关性的状态。所以如果目标是获取所有相关性，那么需要遍历所有关系。
   3. 遍历关系是不现实的。因为这个任务的复杂度是 N^2 的，N是材料的数量。遍历N个材料已经是很困难的了（否则也不用记忆系统了），遍历N^2则是不可能的。
   4. 所以最好是，从项目建立的一开始就建立图数据库。随着项目规模的成长，逐渐往图里添加节点和边。避免单次超大工作量。
   5. 对于为已有项目创建图数据库。可能需要基于逻辑推理，先猜出来一些关系的轮廓（消除N^2里的绝大部分），再根据项目内的实际材料，确定具体的节点和边。
   6. 应该保留一部分纯随机的材料读取和关系判断，用来捕捉没有被ai agent的逻辑推理猜中的关系，这部分关系可能反而是价值较高的。

3. 文件保存的路径（文件结构）和记忆系统是两个层次的东西。
   1. 文件结构是前一个层次，或者低一个层次的概念。
   2. 文件结构本身是一个图数据库，或者说是一个树。
   3. 文件结构包含信息，合理的文件结构能让记忆系统的创建和维护容易很多。

4. 本地运行与联网调用。
   1. 向量检索的embedding模型应该在本地运行。
      1. 建立vector database的时候，需要用embedding模型处理所有要建向量索引的材料。材料的总尺寸可能很大，有时是几GB乃至上百GB。如果调用联网的embedding模型，得把这些数据都上传一遍，网受不了。
   2. 检索结果的筛选和重排序用宿主提供的订阅agent，比如Codex。
      1. 检索出来的信息的尺寸不大，网能受得了。
      2. 我认为筛选和重排序最好用llm这种方式来做，本地运行的llm，和联网的模型比，往往是成本更高，性能更低的。
      3. 最终的检索结果是要发送给比较昂贵的 ai 模型的，比如 3 档、4 档。如果用很差的筛选和重排序，比如本地运行的 7b llm，则会发一些没有意义的数据给昂贵的模型。总成本会进一步的变高。

5. 筛选与重排序。我认为效果有两个，一个是节省成本，一个是提高性能。
   1. 节省成本主要通过使用 1 档实现。比如默认用 1 档做筛选与重排序，以及多轮检索，把结果发给 3 档或 4 档，这样 3 档或 4 档就只需要获取检索结果，高档模型的用量少，这部分成本就低。
   2. 提高性能是通过让context更干净实现。即使检索用的模型和实际工作的模型一样（默认不是这样的），额外使用负责检索的模型，也可以让实际工作的模型context里只有和工作有关的内容，让它更容易注意到有用的信息。

### 记忆系统具体内容

1. 部署之后应当有服务项目的常驻信息，比如项目核心目的、总体结构和长期要求。
   1. 必须保留的信息在任务开始时直接交付。需要核实的内容标明待核的地方。
   2. 其余信息按需要和预算选取。任务启动时给出可继续查找的线索和已知缺口。
2. 有检索系统，尽量采用成熟软件，具体包括以下能力。
   1. 传统检索，比如文字匹配。
   2. 本地图文向量检索。可以增加本地计算投入，采用较强的 embedding 模型换取更好的检索效果。
   3. 图检索。应能处理非结构化信息，比如论文写作时图片、数据、参考文献和正文之间的关系。
   4. 多层次的表示。长文件的整体、实际章节和原文块都可以成为检索成员，并能回到对应的原始依据。图片和聊天按各自的结构表示。项目聊天中的要求、决定和成果也是记忆来源。
   5. 文字块由 agent 智能分块。分块、摘要和语义关系(图检索的)尽量在同一次阅读中完成。
3. 创建和维护使用同一套流程。
   1. 程序检查材料的新增、修改和删除。agent 负责阅读、判断关系与适用条件。程序检查来源版本、原文范围和依据，将相互依赖的改动作为一批提交，更新受影响的知识与向量，复用未变的内容。
   2. 图数据库的修改应当留痕，尽量由程序自动记录修改时间、执行修改的聊天链接、相应的 turn 和根聊天名称。应当能回查知识的条件、关系、更正和退役，以及实际保留的原证版本。原证缺失或覆盖不全时应当标明。
   3. 工作量较大时，默认由 2 档协调者划分有限的工作范围并负责汇总发布，1 档读者在范围内自主领任务、阅读和交稿。读者人数按独立工作量和宿主实际可用容量确定，并留出协调和恢复所需的容量。
   4. 查询与自动维护各自运行。查询可以直接使用已经发布的知识，判断当前状态时按需要核对近期原件和缺口。自动维护在合适的任务开始时并行启动，通常面向全项目，任务结束后尽快收尾。短任务可以跳过。积压较多时可以提醒用户，手动维护由用户发起，按授权范围更全面地处理并报告余项。
   5. 普通建库和维护默认不需要ai审计，维护worker的可靠性够高（有错误但错误数量可以接受），可以直接入库。如果有用户明确触发，也可以启动额外语义审计。
   6. 使用记忆系统的过程本身可以作为审计。使用检索 worker 和调用它的 agent 在实际使用中发现问题时，记录所见版本和依据，交后续维护处理。
4. 检索结果的筛选和重排序。
   1. 默认用 1 档作为检索worker，完成多轮检索、回源、筛选和重排序。调用检索worker的 agent 通常一次调用就能得到结果，也可以按需要继续检索。
   2. 检索worker综合判断相关性、适用条件和依据后给出分数，程序负责排序、去重和按预算选取。交付时区分原文、摘要和判断，并附上能够继续查找的依据和缺口。
5. 有“遗忘机制”，按实际使用调权。
   1. 遗忘只看实际使用情况。检索worker最后把材料交给调用它的 agent，才算一次使用机会。程序根据交付记录自动调权。搜索、回读和评分是交付前的准备，空结果和重复登记也不增加使用次数。权重随实际使用变化，与经过多久无关。
   2. 实际交付的版本提高权重。比如检索过程中发布了新版，最后交付的是旧版，就把这一次使用记在旧版上。一直没用的材料，权重应该先降得快，后来慢。被交付过多次的材料，以后应该更不容易忘。用过哪个版本，应当能和当时的原证及图中的历史关系对照。
   3. 材料在使用上的相似性，由历史上实际共同交付的情况决定。正文的相似性仍由向量检索处理。用途之间的边界是模糊的。每次交付以后，其余材料都受影响，用 Gaussian 相似度规则，按它们与本次用途的相似程度连续降权。比如一直做 A，和 A 用途接近但没用到的材料降得多，用途相差较远的 B 也会慢慢降权。
   4. 权重可以给检索worker作为筛选和重排序的参考，也可以影响按需信息先提示什么。检索worker仍要根据本次问题、材料的适用条件和原证综合判断。必保信息继续直接交付。
   5. 权重可以降得很低。材料、原证、历史和图关系继续保留，基础检索仍能找到。比如换回 B 时，应该能把原来的材料重新找出来，再次实际交付就可以恢复权重。事实是否还有效，要看证据和适用条件。材料更正、来源删除和用户明确要求删除，仍按各自的规则处理。

## 资源协调系统

主要解决多个项目同时执行重任务时的资源争用，优先协调 GPU。GPU 任务通常较重，显存也比内存更紧张。

1. 记忆系统的 embedding 模型单独协调。同一机器上的多个项目和并发请求共用已经加载的模型实例，避免重复占用显存。
2. 其他重任务使用 HTCondor，包括矩阵计算等 GPU 任务，以及 CPU、内存、硬盘等资源的重任务。普通轻任务可以直接运行。
3. 资源准入、排队、时限和终态优先使用 HTCondor 原生能力。basePack 应当让 agent 容易提交、等待和查到结果，保留传入参数，并能核对结果不明的提交。
4. 两种机制应协调已接入负载的 GPU 占用，降低显存冲突。资源需求可以粗略估计，各作业按申报控制实际峰值。
5. htcondor只在有多个重任务同时进行时使用，如果只有一个thread在工作，则它不需要把重任务发到htcondor。

## AI agent 的组织体系

目的主要是提升性能。

1. 做原来做不了的事情。多个 agent 分工处理不同材料和子任务，再汇总成果，使团队能处理超出单个 agent context 容量的工作。
2. 把原来能做的事情做得更好。让各 agent 的 context 集中于自己的职责和相关信息，提高结果的正确性、完整性和判断质量。可以增加团队用量来换取更好的性能。
3. 主 agent 确定目标、做关键决策并对整体结果负责。协调 agent 负责分工、派工、依赖和成果汇总。上级提供目标和必要背景，执行 agent 完成具体工作，返回结论、依据和未解决的问题。上级按需要深入原文。
4. 根据整个任务的工作量、依赖、验证和交接来组织。简单任务可以由单个 agent 完成，也可以由主 agent 直接指挥执行者。复杂任务可以设置专职协调者。团队规模、角色和模型随任务及阶段调整，必要时留出空闲容量。

## 文件结构建议

以 skill 的形式提供，帮助人和 AI agent 选择、建立和维护适合项目的文件组织方式。它可以独立使用，也可以供记忆系统参考。

1. 提供多种可选择、可组合的推荐结构，比如开发文档、实验路线、临时材料、需要长期保留的证据和受限资料的组织方式。
2. 一个项目集中维护一套现行的公共开发文档。候选实验可以短期比较，之后尽快收敛。要长期独立演进的路线可以拆成不同项目。
3. 因隐私、机密、版权或许可需要限制分发的原件、附件、分析和摘录放在项目根的 `private/`。用独立的本机 Git 保存，另行备份。整个目录排除在公共 Git 和发行之外。
   1. 私有资料可以按主题或任务组织。和公共任务对应的私有依据沿用同一个任务标识。
   2. 公开文档应写清可公开的结论和必要理由，公开使用流程应当自足。私有资料可以作为可选引用，引用的名称和路径也要能公开。
4. 根据项目的类型、规模、阶段和已有组织方式选择或调整，保持结构与说明简洁，方便理解、读取和维护。

## 术语

1. 模型等级用数字档位表示，数字越大表示能力档位越高。日常任务默认 3 档，多轮检索、筛选和重排序默认 1 档。具体模型和推理强度由项目配置维护。

## 适用于所有项目的要求

1. 系统应尽量简洁，优先复用成熟组件和原生能力，减少需要自己实现和维护的代码。采用 let it crash 的思路，按明确契约运行，意外错误直接暴露。把必要的校验和恢复放在能处理问题的地方。
2. 文档和 prompt 应当从实际读者的角度写，给出工作需要的信息，保持简洁。选择长远来看更好用的做法。人和 agent 都是使用者，可以增加开发工作换取更方便的使用。命令应提供好用的默认参数。
3. 设计时以 Codex 等订阅 agent 为日常入口。使用该入口应当可以完成包括记忆检索和维护在内的常规工作。
4. 尽量减少高档 agent 为同一个目的多次调用工具。可以合并的调用尽量合并，返回结果控制在工作所需的范围内。评价成本时分别看主 agent 的往返和 context 开销、全队用量和耗时。
5. 要方便部署、升级和分发。通过 [GitHub](https://github.com/YS-Pan/basePack) 分发源码、skills、必要文档和小样例等。较大的模型和通用依赖按需要准备，项目数据和凭据由各项目保管。升级或迁移应保留知识和原证，并能验证恢复结果。
6. 关于权限。首次安装、接入和调整权限时，可以由人参与。接入时应当安排好日常由哪个账户运行、需要访问哪些资料和资源，并由 agent 说明默认做法。平时尽量让 agent 在用户授权的范围内，用普通权限自己处理，少占用用户的注意力。
   1. 比如重启后按需启动已接入的项目记忆库和共享 embedding，以及维护时采集本项目的新聊天。需要宿主审批时，可以把这一次要做的事交给宿主的自动审批功能，比如 Codex 的 Auto Review。获准后继续原来的工作。权限受阻时，说明卡在哪一步，以及哪些事情还没完成。
   2. 有些任务由另一个账户实际执行，比如 Condor 的作业。接入时应当用实际执行账户跑通需要的操作，确认它能运行程序、读取输入并写出结果，结果也能由使用者取到。
   3. 项目资料、凭据和共享资源各有访问范围。涉及其他项目或对外分发时，按用户已经同意的对象和范围做。
7. 工程验收应当跑通实际需要的流程。长期效果通过真实项目使用来判断，包括能否主动发现重要线索、能否找到和回读旧成果、协作质量、部署负担和完整使用成本。

## 本文档的维护方式

1. 项目纲领主要由人类（用户）编写。
2. 项目纲领保持简短，只记录用户明确表达的长期目标和要求，供人类经常完整阅读，整个项目以它为基准。
3. agent 认为有内容应当更新时，提出修改建议。正文由用户确认后更新。
