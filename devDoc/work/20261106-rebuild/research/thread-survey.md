## 可用于新计划的用户意图

以下是聊天中直接写出的用户要求，建议当作计划依据，而将其后续细化的技术实现标为 agent 提案：

> “让 agent 在知道自己缺少什么信息时，能够方便地找到对应资料”；“发现自己尚未意识到的必要信息与约束”；“减少无关内容的读取，避免污染或撑爆 context。”

用户提出两个互补维度：时间上“划分过去现在将来”；空间上捕捉大量资料的相关性，可先以较高成本全局处理、建库，再用较低成本检索。其后明确把文件持久化与检索区分开：“图检索和向量检索解决的是检索的问题，而‘文件保存在哪’‘以什么形式保存’则是另外的问题。”

用户期待一个通用内核和按任务选择的模块，模块形式为“skill+脚本+数据库”，每个业务项目局部生效；多个独立实验可放在各自目录并有独立 Git。新一代允许大改，不需要兼容旧项目，也暂不加入付费 LLM API；已用原话要求以“性能最好（最能给新项目的 ai agent 提供帮助）”为准，并希望尽量复用成熟组件。用户同时坚持其工作假设：“我倾向于认为图检索和向量检索都是有明确净收益的。但可能需要某种正确的实施方式才能得到明显净收益。”因此早期负结果应定位为特定表示、检索和预算配置的失败，不能直接据此否定图＋向量方向；也不能反过来把预期当成已经证实的收益。

用户明确要求将计划分成两种权威程度：简短的“用户计划”仅记用户明确表达的内容，不自动改写；认为有新内容应补充时主动询问。较长的 AI agent 研究计划用于技术细化。避免把 Atlas、某个图数据库、特定检索流程、模型档位或阶段预算倒写成用户要求。

组织方式也来自明确偏好，而不是仅为省 context 的实现猜测：主 agent 做战略和关键决策；协调者整理依赖、派工与检查点；执行 agent 接收窄范围输入、独立交付。用户反复要求“广泛读取—筛出直接相关信息或链接—避免无关内容混入”。相似 prompt 调查汇总到 288 条近期聊天、860 条用户消息，认为 29 条聊天出现 14 类相似做法（含三层组织、筛选后回传、默认先看线程元数据）；该调查只表明习惯存在，不证明该组织提高了质量。

## 读取到的测试证据与限制

1. **早期 Atlas / 词法对照没有证明 Atlas 优胜。** 已读项目汇总称：六题中每组 99 个关键判据，词法正确 57 项、Atlas 原文证据组 48 项、完整交付包组 43 项；虽减少输入字符，但未提高回答质量。另一批机械臂“从零”对照曾有 8 次运行，5 次完成所设流程，3 次未完成；普通文件与 Atlas 均能帮助新 agent 恢复状态，但没有证据说 Atlas 更好，也未充分测试“未知未知”。真实科学结果也不能拿来给记忆系统排名。关键故障教训是：关键词没命中不能说明条件不适用，必要证据可能在候选筛选或最终预算中丢失。上面这些旧 Atlas 指标来自线程总结，不是我独立重算原裁判数据。

2. **20261026 Lightgraph 的图＋向量配置在严格交付预算下落后。** 已读线程记载 17 份资料、221 条论断、26 条跨来源关系；37 个单测，72 次受控检索、8 份回答。八题必要信息覆盖宏平均：词法 85.10%、纯向量 80.73%、图＋向量 66.46%。系统能运行，首轮空证据失败后来修复，搬迁查询成功；网络审计最终断言未通过。结果见旧项目 [20261026 lightgraph/RESULTS.md](<D:/project/20261024 doc system/20261026 lightgraph/RESULTS.md>)。

3. **去掉 context 预算后覆盖率接近，但图＋向量很冗长。** 另一固定集仍为 72 次检索、8 份 fresh 回答；不做长度省略时，词法 97.71%、纯向量 96.46%、图＋向量 97.50%，图摘要的新增覆盖为 0，图＋向量交付包为词法的 7.13 倍字符。说明系统的候选能力与证据包在受限 context 下的交付能力是不同指标。结果与敏感性分析见 [unbounded RESULTS.md](<D:/project/20261024 doc system/test-runs/20261027 lightgraph-unbounded/RESULTS.md>)。比较应冻结同一题、同一来源、同一候选池和同一预算，并把普通文件 / 词法、向量、图扩展、重排作消融。

4. **试用版 6luna 排序先发生链路失败，之后有受限成功，但没有证明排序净收益。** 0.2.2 初始独立 A 阶段未通过：长 prompt 转发多一个空格而停止评分、维护脚本在建库前失败。保留原失败后，冻结新版本重测：A2 主测 7 题评分成功，D08 一题超时整题回退；四组重排一致性未触发异常，独立评价未见新增关键退化或严重错误。八题必要项宏平均双臂均为 97.5%。用户允许质量优先、等待可到 10 分钟；D08 随后 3 批真实评分用约 163 秒完成，低于旧 180 秒，因此无法证明更长等待带来收益。实际模型身份、会话、token 和费用未能独立确认，按 `null` 记录。报告分别见 [A1 RESULTS](<D:/project/20261024 doc system/test-runs/20261027 trial-stage-a/RESULTS.md>)、[A2 RESULTS](<D:/project/20261024 doc system/test-runs/20261027 trial-stage-a2/RESULTS.md>)、[A3 RESULTS](<D:/project/20261024 doc system/test-runs/20261027 trial-stage-a3-budget/RESULTS.md>)；恢复回归实际完成 4 次 build、14 次查询，未覆盖每一种损坏恢复路径。

## 可检验的重建方向

以下是调查者从旧试用中提出的候选办法；新项目实际采用的范围以 [AI 执行计划](../agent-plan.md) 为准，不直接继承旧项目的发布、审计和恢复流程。

- 将原件存储、来源登记与权限、版本和有效时间、知识抽取、图 / 向量索引、任务状态、检索交付和运行缓存分层设计；检索算法不能补救原件未登记、索引过期或权威来源不明。
- 用原件可追溯性和显式登记构成维护边界；新代次构建成功后原子发布。更新必须看见源变化；恢复检查必须确认实际图与向量可检索，而非只校验 sidecar。对 HDD 关注全量哈希、整库复制、重复整状态写盘、并发写入和缓存清理，报告纯系统开销与业务工作时间的不同口径。
- 查询时先保留完整候选池，之后再做预算选择；若证据被裁掉，提供可追踪的按需补读。显式标记 unknown；“历史 / 当前 / 将来”“修订 / 替代”“召回 / 交付 / 理解”保持不同语义。图摘要若想改善用户未主动提问时的信息发现，必须测量它实际新增的必要信息，而不能只测图是否建成。
- 测试输入冻结并记录哈希；设置普通文件 / 词法基线，再加向量、图扩展和重排消融；独立裁判只评原始必要项、遗漏、错误、来源和答案成效。指标应同时包括必要证据覆盖、未知项发现、无依据错误、交付字符 / token、端到端时延、重试与补读、索引维护成本、恢复成功率和 HDD 写入。开发集与留出题分离；真实项目作为后续外部效度证据。
- 测试 thread 应在独立 project/cwd 中创建并做启动审计。历史 `确认测试 thread 是否读取 AGENTS.md` 证实：曾有 8 个所谓从零 thread 被根 `AGENTS.md` 自动注入；prompt 写“不要读取”不能清掉已注入上下文。项目隔离应以实际初始上下文日志验证，不能仅看 thread 是新开的。模型配置、请求值、实测元数据分开记；没有独立证据就标 null。
