# 用户计划
本项目的内容是，搭建和测试三个工具，用于提升 ai agent 的能力。

三个工具分别是
1. 记忆系统。提供图检索和向量检索。
2. 资源协调系统。主要管理多个项目同时进行重任务时的计算资源协调，管理的资源包括GPU，内存，CPU。目前考虑基于HTCondor。
3. ai agent的组织体系。多种角色分层协作，主 agent 专注高层决策，协调 agent 负责管理与派工，执行 agent 处理具体工作。类似于deepseek的superagent。

## 记忆系统

### 核心目的

1. 解决“不知道”。在“知道自己不知道”的时候，能检索到需要的信息。
2. 解决“不知道自己不知道”。ai 没有主动检索的时候，也能通过记忆系统注入一些信息，让它至少达到“知道自己不知道”的水平。这一条是核心中的核心。
3. 低成本。包括建库时的低成本，以及使用时的低成本。


### 额外要求


1. 局部且独立。项目知识、来源、任务状态和数据库保存在对应的 project 内，只在该项目生效。通用工具、依赖、模型和机器资源管理可以显式共用，避免重复安装和保存；共享资源不意味着共享项目记忆。
2. 避免过多小文件读写。能够在机械硬盘上正常使用。


### 记忆系统相关的思想

1. 关于解决“不知道自己不知道”。逻辑上讲，解决这个问题，必然需要某种全局遍历。遍历的方法有：
   1. 低成本低性能的遍历，在每次检索的时候都执行。比如用脚本进行全库文字匹配搜索。
   2. 高成本高性能的遍历。比如用 ai agent 读取所有文件。
   3. 低成本高性能的遍历。这是本项目内容的核心。它是上两种的混合：先进行一次高成本高性能的遍历，建立数据库。这个数据库包含特殊的内容和格式，使得它能被低成本的检索，并得到高性能的结果。

2. 关于图数据库的建立和维护。这个工作由ai agent执行。
   1. 如果想让ai agent发现两份材料之间的关系，那么这两份材料必须首先都同时在它的context里，否则不可能发现相关性。
   2. 某一个相关性在被发现之前，ai agent处在“不知道自己不知道”这个相关性的状态。所以如果目标是获取所有相关性，那么需要遍历所有关系。
   3. 遍历关系是不现实的。因为这个任务的复杂度是 N^2 的，N是材料的数量。遍历N个材料已经是很困难的了（否则也不用记忆系统了），遍历N^2则是不可能的。
   4. 所以最好是，从项目建立的一开始就建立图数据库。随着项目规模的成长，逐渐往图里添加节点和边。避免单次超大工作量。
   5. 对于为已有项目创建图数据库。可能需要基于逻辑推理，先猜出来一些关系的轮廓（消除N^2里的绝大部分），再根据项目内的实际材料，确定具体的节点和边。
   6. 应该保留一部分纯随机的材料读取和关系判断，用来捕捉没有被ai agent的逻辑推理猜中的关系，这部分关系可能反而是价值较高的。

3. 文件保存的路径（文件结构）和记忆系统是两个层次的东西。
   1. 文件结构是前一个层次，或者低一个层次的概念。
   2. 文件结构本身是一个图数据库，或者说是一个树。
   3. 文件结构包含信息，合理的文件结构能让记忆系统的创建和维护容易很多。
   4. 记忆系统里应该包含对于文件结构的建议。用“给ai agent 的 prompt” 的形式保存。

4. 本地运行与联网调用。
   1. 向量检索的embedding模型应该在本地运行。
      1. 建立vector database的时候，需要用embedding模型处理所有材料。所有材料的总尺寸很大，经常是几GB乃至上百GB。如果调用联网的embedding模型，得把这些数据都上传一遍，网受不了。倒是不担心保密，隐私之类的事情。
   2. 检索结果的筛选和重排序应该用联网模型。
      1. 检索出来的信息的尺寸不大，网能受得了。
      2. 我认为筛选和重排序最好用llm这种方式来做，本地运行的llm，和联网的模型比，往往是成本更高，性能更低的。
      3. 最终的检索结果是要发送给比较昂贵的ai模型的，比如gpt6.1sol，gpt6astra之类的。如果用很差的筛选和重排序，比如本地运行的7b llm，则会发一些没有意义的数据给昂贵的模型。总成本会进一步的变高。

5. 筛选与重排序。我认为效果有两个，一个是节省成本，一个是提高性能。
   1. 节省成本主要通过“用便宜模型”实现。比如用廉价模型做筛选与重排序，以及多轮检索，把结果发给昂贵模型，这样昂贵模型就只需要获取检索结果，昂贵模型的用量少，成本就低。
   2. 提高性能是通过让context更干净实现。即使检索用的模型和实际工作的模型一样（默认不是这样的），额外使用负责检索的模型，也可以让实际工作的模型context里只有和工作有关的内容，让它更容易注意到有用的信息。


### 记忆系统具体内容

1. 部署之后应当有它服务的项目的常驻信息。比如几个.md文档，介绍项目核心目的、总体结构等，让 ai 大致了解项目的情况。这主要用来解决“不知道自己不知道”。

2. 有检索系统，采用成熟项目来实现，具体包括。
   1. 传统检索方式。比如文字匹配。
   2. 向量检索。
      1. 使用本地运行的embedding模型，需要支持图片的向量检索。
      2. 使用规模大一些的embedding模型。可以增加本地计算时间换取更好效果
   3. 图检索。应能应对非结构化信息，比如论文写作时的图片/数据/参考文献和正文的关系，不能只适用于代码这类有天然结构、可以用脚本直接建图的资料。

3. 图的创建和维护。核心是使用ai agent根据材料生成节点和边。
   1. 创建和维护也许可以合并为一套系统。
   2. 维护包括自动的维护，以及手动触发的维护。手动触发的维护要更全面深入。自动的维护是每次启动ai agent之后，如果有需要，由它或者它的subagent进行维护。
   3. 对于工作量较大的创建和维护，使用subagent团队进行。默认采用组织形式是：
     1. 中级模型负责管理协调以及审核，廉价模型负责广泛阅读并寻找相关性。
     2. 每个中级模型最多管理4个廉价模型。
     3. 审核应该是批量的，不要每找到一个关系就审核一次。
     4. 审核应该是可以省略的，也许可以考虑作为默认省略的。
     5. 使用图检索的过程，本身可以当作审阅过程。如果使用图检索的模型发现结果有问题，可以自行修正。
     6. 图数据库的修改应该留痕，比如包括修改时间，执行修改的agent的thread链接，对应的turn，对应的根thread名。这些留痕最好是用脚本自动实现的。

4. 检索结果的筛选和重排序。
   1. 目的是通过筛选减少context占用，降低成本。通过重排序将重要信息放到前面，提高性能。
   2. 默认使用廉价模型进行筛选和重排序，目的是节省成本。应该做到：负责干活的顶级和高级模型需要检索的时候，只需要一次工具使用，或者向subagent发一次消息。这次工具使用/subagent使用发出后，subagent进行检索，筛选和重排序，如果有必要的话，可以进行多轮检索，然后把结果返回给负责干活的模型。重点是记忆系统应该尽量实现，让负责干活的模型的调用次数少，最好只有一次。当然，对于负责干活的模型不做任何限制，记忆系统是它的工具，不应该反过来限制它，它如果想的话，可以任意使用，检索多少轮都行。
   3. 筛选和重排序也许可以用同一种机制实现，即只进行排序，然后把排名靠后的内容弃掉，作为筛选。
   4. 重排序的输出应该是内容的分数，而不是直接输出排名。让llm直接输出一串排名，还要保证每个数字只出现一次，对它来说是很困难的。应该输出分数，让脚本来根据分数排名。


## 资源协调系统

主要管理GPU任务。因为
1. GPU任务一般都比较重（不重的话就没必要用GPU了）
2. 显存比较紧张，比内存紧张很多



## ai agent的组织体系

支持分层协作，主 agent 专注高层决策，协调 agent 负责管理与派工，执行 agent 处理具体工作，分工随任务调整。由 subagent 广读并筛选直接相关的信息或链接，减少主 agent 的无关上下文。

目的主要是提升性能。具体有
1. 做原来做不了的事情。ai agent的context有限。对于大的项目，复杂的项目，一次需要做的事情会撑爆它的context，导致它干不了。
2. 把原来能做的事情做的更好。ai agent的注意力有限。即使context没有撑爆，往里塞杂乱的东西，也会降低ai的性能。比如塞入过多具体执行的细节，会让战略判断水平下降。


## 术语
1. 模型级别：顶级，高级，中级，廉价。在当前的时间点（2026年11月6日）对应GPT6Astra，GPT6.1Sol，GPT6.1Terra，GPT6Luna。


## 适用于所有项目的要求

1. 系统应尽量简洁。避免防御式编程，避免加入太多校验审阅，甚至加入校验的校验，审阅的审阅，以至于项目膨胀成屎山，无法操作。应该用let it crash的思想。
2. 文档和prompt应该避免废话。避免防御式写作。应该从“读文档的ai agent”的角度出发进行写作。
3. 目前没有api版的llm，只有基于订阅的agent，比如codex订阅。设计系统时要注意调用方式。


## 本文档的维护方式
1. 用户计划主要由人类（用户）编写。
2. 这份用户计划保持简短，只记录用户明确说过的信息，供人类经常完整阅读，整个项目以它为基准。
3. 用户计划不自动更新；agent 认为有内容应当更新进去时，应主动询问用户是否更新，获得同意后再修改。
