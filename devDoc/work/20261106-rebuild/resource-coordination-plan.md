# 计算资源协调实施计划

2026 年 11 月 7 日修订。下一阶段先做资源协调，独立于记忆系统交付。用户明确：embedding 与其他 GPU 任务采用独立机制，允许二者并行。本版据旧项目聊天和代码复核重写；上一版把模型进程放入 Condor、默认整卡轮流及持卡任务不得调用 embedding 的安排均被本版取代。目标依据为 [项目纲领](../../project-charter.md#资源协调系统)，复用证据见 [旧实现专项核对](research/resource-coordination.md)，状态统一记在 [工作进度](progress.md)。接口名和具体预算仍是工程建议。

## 已有能力与实际缺口

本仓库尚未交付运行工具，但旧项目已实现多模态模型加载、文本/图片预处理、向量归一化、批处理、loopback 服务、短时热复用、超时和 owned 进程清理，并有真实 GPU 回执；这些应提取和改造，不从零再写。

旧服务是项目局部复用，查询默认使用，建库却另起 owned worker；还沿用整卡文件锁和启动空闲至少 13 GiB 等门槛。真正待补的是跨项目同模型单实例、建库与查询共用服务、独立 GPU 工作负载的显存预算，以及普通重任务的统一 Condor 入口和完整生命周期。已有模型、共享 Python 与 Condor 部署优先复用；旧索引、业务授权和任务状态各自保留。

## 两条独立运行链

```text
项目 A / 项目 B
  ├─ embed ── 机器共享 embedding 服务 ── 已加载模型
  └─ run   ── HTCondor ──────────────── 普通 GPU / CPU 重任务
                   同一物理 GPU 可同时运行两类工作
```

embedding 自己管理实例、请求队列和批次，不提交为 Condor 作业，也不因普通重任务到来而默认卸载。普通 GPU 重任务先由 Condor 彼此串行；它们与 embedding 在显存预算容许时并行。首版先支持当前单机 Windows、一张 GPU，不引入多机或多个普通 GPU 作业的显存切分。

共享服务沿用已有客户端、传输和 runtime；把 endpoint/实例注册移到机器共享运行目录，实例键由固定模型、版本、精度、预处理和设备等运行配置决定，不含项目路径。保留实例创建锁，取消跨两条链的整卡排他锁。项目资料、索引、向量和结果留在项目内，机器共享目录只保存必要运行配置与状态。

## 显存与其他资源预算

先用固定预留把两条机制衔接起来，不另建 GPU 调度服务。定义单卡总显存 T、embedding 峰值预算 E、桌面/驱动及余量 S、普通 GPU 作业峰值估计 H：

```text
普通 GPU 作业可用预算 B = T - E - S
准入条件：H <= B
```

E 包含模型加载瞬时峰值、CUDA context、缓存及允许输入/批次的 workspace，始终保留，服务未加载时也不借给普通任务。这样普通任务先启动后，embedding 仍可冷启动，不依赖两边同时查询 free memory 再抢卡。旧合成图文回执的峰 reserved 约 4.08 GiB 仅是测量起点，不能直接作为 E。

预算由一份机器配置维护，生成或引用 Condor 的发布属性；wrapper 检查 H 并在作业 requirements 中匹配该属性。单个普通 GPU 作业仍申请 request_gpus=1；这只用于普通任务之间的设备分配。设备总显存门槛 gpus_minimum_memory 不能代替 B。官方支持自定义 slot 属性与作业匹配；本机具体配置由 R0/R2 验证。[自定义属性](https://htcondor.readthedocs.io/en/25.0/faq/admins/slot-attrs.html)、[资源声明](https://htcondor.readthedocs.io/en/25.0/man-pages/condor_submit.html)

预算是合作约束，agent 粗估用量并限制线程/框架预分配；声明额度不等于 Windows 驱动硬隔离。显存不足或估计失准时直接返回原始错误和测量，不静默改 CPU、不杀其他项目进程。监测 free 用于诊断，不代替预算。模型/输入上限增大前重新标定 E，并在当前重任务结束后应用预算变更。

CPU/RAM 同样先扣除 embedding 和桌面的用量，再交给 Condor 分配。磁盘空间用 request_disk 表达执行 scratch 需求，项目输出盘另查容量；实际出现机械盘 I/O 重任务争用时，可用 Condor 自定义 I/O token 限制同类任务并发。检查 START/SUSPEND/PREEMPT，避免 embedding 的 CPU 活动被误当成禁止运行普通任务的桌面策略。[执行点配置](https://htcondor.readthedocs.io/en/25.0/admin-manual/ep-policy-configuration.html)

并行验收要求两类工作在同一时间段均取得真实进展；驱动如何安排 kernel 不是本工具的低延迟或算力隔离承诺。启动时核本机支持多进程共同使用设备的模式。[NVIDIA 计算模式](https://docs.nvidia.com/deploy/mps/when-to-use-mps.html)

## 对外接口与状态责任

| 动作 | 输入 | 返回与职责 |
| --- | --- | --- |
| run | executable、参数数组、工作目录、显式环境、资源请求、排队/运行时限 | 一次提交并等待，返回 job ID、终态、应用退出码、耗时和产物/日志定位 |
| submit / status / wait / cancel | 任务配置或 job ID | 长任务接续、状态/等待原因、观察时限与作业撤销 |
| embed | 项目标识、文本/图片输入或路径、模型配置、请求截止时间 | 独立服务内部排队并复用模型，返回向量及模型/预处理标识，不建索引 |

普通 GPU 任务资源声明增加显式的峰值显存估计；超过已知 B 的请求立即说明无法满足，不让它无限空等。资源不足但未来可满足的任务由 Condor 排队。先交付 CLI/Python 调用；长任务可由执行 agent 内部等待，不要求主 agent 反复轮询。

Condor 队列、事件日志和历史维护普通作业状态；本地只保存提交参数、job ID 和输出位置。run 的排队/运行超时取消本作业并确认清理；wait 的观察时限只结束观察。排队截止与运行时限进入 Condor 策略，客户端消失后仍生效；周期策略存在检查间隔。condor_wait 成功只表示完成或中止，仍核应用退出码与产物。[等待语义](https://htcondor.readthedocs.io/en/25.0/man-pages/condor_wait.html)、[自动管理](https://htcondor.readthedocs.io/en/25.0/users-manual/automatic-job-management.html)

共享服务先保留内存请求队列和单实例，复用旧 runtime 内部批处理；多请求可共享模型，首版不要求同时 forward 或跨请求动态合批。单请求取消只移除排队输入，或结束等待并丢弃其在算结果；不得通过关闭整个 worker 取消其他项目。服务空闲时可卸载，客户端 close 仅关闭本客户端。服务崩溃明确结束受影响请求，重启先核对旧实例后再创建；不建设自动重试/恢复数据库。

## 实施批次

### R0 复用准备与预算标定

1. 沿 [复用清单](research/resource-coordination.md#代码复用清单) 提取 runtime、预处理、批处理、传输和进程清理；用最小适配替换旧发布/owner/attempt 绑定，不移入旧业务台账和完整审计层。
2. 复用系统 Python 和固定模型，核当前配置与设备映射；将 13/12/3 GiB 门槛、物理 GPU 0 和整卡锁依赖列为明确替换项，包括合同中的强制锁字段。
3. 用本工具拟支持的最长文本、图片尺寸和最大批次测加载/推理峰值，确定 E 与 S，同时记录 CPU/RAM 峰值；保留旧短图文回执作对照。
4. 沿已有 Condor smoke 样例核配置、认证、执行账户、中文/空格路径、真实 CPU/GPU 产物及取消释放；先修已存在部署，不先重装。embedding 运行入口不以 Condor 认证成功为前提。

**完成：** 可提取代码范围与薄接口确定，机器预算配置有测量依据；独立 embedding 小调用与 Condor 小作业分别可运行。不能仅靠目录可列出、调度返回 0 或 mock 通过结案。

### R1 将旧 embedding 服务改为跨项目共用

1. 提取现有 loopback 服务和客户端，实例注册改为机器级；同模型并发首请求只启动一个进程，排队/加载中的实例也纳入注册。
2. 建库与查询统一走此服务，消除旧 reuse=False 绕行；图片与文本沿用已核实的预处理和向量合同。
3. 取消跨机制整卡锁，保留单实例注册锁；用 E 和输入/批次上限替换旧整卡 free 门槛，监测区分自身占用和整卡其他进程。
4. 复用热模型、空闲退出和错误回传，补本请求的截止/取消；共享服务停止是独立管理动作。启动失败后保留原始错误与 stderr，不自动重试推理。

**完成：** 两个不同项目的建库/查询请求使用同一 PID 和模型实例；取消一个请求不结束另一个；文本与图片均返回有效向量。复用现有回归并修改受影响断言，不从头搭建测试框架。

### R2 普通重任务的 Condor 薄入口

1. 从已有 submit 样例与官方 CLI 建立可安装入口，集中实现 run/submit/status/wait/cancel、参数数组、路径与环境处理。
2. 发布 B，任务声明 H 并做准入匹配；普通 GPU 作业之间 request_gpus=1 串行，embedding 独立运行。补 CPU/RAM/磁盘声明与线程数配置。
3. 实现退出码/产物判断、held 原因、两类超时及取消；提交响应不确定时先按本次唯一标识查队列，不直接重复提交。
4. 事件等待优先，必要轮询设间隔，空闲无高频写盘；日志留项目内，主 agent 只接收短摘要和定位。

**完成：** 一次 run 得到真实结果；过大显存请求立即明确拒绝，暂时无配额的请求排队；正常、失败、取消与超时均正确释放本作业资源。

### R3 两机制并行与其他资源准入

1. embedding 已加载时运行 H<=B 的 GPU 重任务；反过来先运行普通任务，再冷启动 embedding。验证两个启动顺序都不因旧锁或 free 门槛退成串行。
2. 同时运行最长允许 embedding 输入/批次和已声明峰值的普通任务，核峰值、应用结果及 CPU/RAM 预留；记录两者吞吐与延迟变化，用实际结果调整预算。
3. embedding 保持可用时，提交第二个普通 GPU 作业，确认只有普通任务之间排队；不同项目请求仍共用模型。
4. 分别验证 CPU/RAM 超配排队、可容纳时并行；磁盘空间及实际启用的 I/O token 按声明工作。

**完成：** 两类 GPU 工作存在重叠执行区间且各有真实进展和正确结果；模型保持已加载。H>B 明确失败，第二个普通 GPU 作业等待，轻任务仍可操作。R1 和 R2 可分别交付，R3 是本工具的核心验收。

### R4 生命周期与故障回归

| 场景 | 必须观察的结果 |
| --- | --- |
| 普通 GPU 作业内部请求 embedding | 预算涵盖双方时请求能完成，不按“占卡”一概拒绝，也不等待本作业释放 GPU |
| 取消/超时一个普通作业 | 清理其进程树；共享模型及其他项目请求继续 |
| 单个 embedding 请求取消/过期 | 结束该请求，其他请求继续；在算结果可丢弃，不误杀整个模型进程 |
| 服务空闲退出后再有请求 | 在预留 E 内重新加载，不依赖普通任务先结束 |
| 服务崩溃/异常重启 | 请求明确失败；旧实例可定位清理，重启不重复加载 |
| 普通 worker 派生子进程或异常退出 | 整棵任务树正确回收，退出结果与日志可追溯 |

**完成：** 两个全新合成项目完成真实 GPU 联合流程，保留时间线、PID、job ID、加载次数、显存峰值和应用结果。测量是本版本证据，旧顺序复用/文件锁回执不能替代并行验收。

### R5 安装与使用交付

换路径安装后，两个项目共用一套服务、模型和 Python；面向使用者编写 README、resource skill 与短示例，说明粗估资源、一次调用、失败定位及管理动作。管理员文档负责共享服务、预算、Condor 配置与旧调用方切换；更新现行说明和模块边界。仅源码、skills、短文档和小样例入 Git。

**完成：** 新项目按说明能调用共享 embedding 和普通重任务，两者可并行；无需各自管理模型、编写 Condor 文件或复制环境。R3 核心可用，R4/R5 完成后形成可分发版本，远端发布按用户指令处理。

## 顺序与分工

R0 之后，R1（服务作用域与预算）和 R2（Condor 薄入口）可按约定接口并行，再执行 R3 → R4 → R5。主 agent 负责预算合同、复用取舍和联合结果；共享预算与实例状态各有一个 owner，不建设固定大团队。每个完整批次检查后在 main 提交相关代码、文档和变更记录。
