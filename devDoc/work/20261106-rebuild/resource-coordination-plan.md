本阶段交付两条可独立使用的链：

2. 共享 embedding：多个项目请求同一个模型实例；模型的加载、驻留和卸载均纳入 GPU 占用协调，不要求各项目自行启动模型。

## 建议架构与关键约束

```text
项目 A / 项目 B
  ├─ 重任务入口 ────────── HTCondor ── 普通 CPU / GPU worker
  └─ embedding 客户端 ── 共享服务前端 ── HTCondor ── 模型 worker
                         不持有 GPU                    持卡期间复用模型
```

embedding 的请求合并、模型单实例和批次管理由独立服务负责；建议把实际加载模型的 worker 作为 HTCondor vanilla 作业启动。HTCondor 统一授予 GPU/CPU/RAM，避免独立服务和普通作业分别认为自己已取得同一张卡。官方支持 GPU 请求与分配环境变量；该接法是本项目的设计建议，R0 必须实测。[GPU 作业](https://htcondor.readthedocs.io/en/25.0/users-manual/submitting-a-job.html#jobs-that-require-gpus)、[作业环境](https://htcondor.readthedocs.io/en/25.0/users-manual/env-of-job.html)

- **单实例覆盖驻留期。** 同一固定模型配置只允许一个已提交或运行中的 worker；排队和加载也计入实例状态，避免并发请求重复提交。取得 GPU 后加载，活跃期反复服务，退出时先结束 CUDA 进程再归还资源。模型版本、精度和预处理合同随配置固定。
- **有界占卡。** 先在同一 worker 内顺序处理有界批次。空闲宽限期后退出；有其他 GPU 重任务等待时停止领取新批次，完成当前批次后卸载退出。设置批次时限和连续占卡上限，避免持续请求永不让卡。可先试空闲 30 秒、争用时连续占卡 120 秒，再按加载耗时实测调整；这些不是用户指定值。
- **调度仍归 Condor。** worker 退出后的下一次启动重新排队。仅降低作业优先级不会驱逐正在运行的 worker，不能代替让卡；首版实测两类请求均能持续取得进展，不承诺严格 FIFO。[作业调度](https://htcondor.readthedocs.io/en/25.0/users-manual/job-scheduling.html)
- **避免持卡嵌套等待。** 一个已申请整卡的重任务不能再等待另一个 embedding GPU worker。把 embedding 放在重计算前置阶段；需要多阶段任务时在阶段间归还 GPU。由调用合同和入口检查直接报出已知冲突，不允许静默挂起。
- **一次资源所有权。** 新 worker 尊重 Condor 注入的 GPU 可见设备，不再强制 GPU 0 或重复获取旧的不可重入锁。迁移前列明仍用旧锁的调用方，选择停用其旧 GPU 入口或统一切换；两套入口未经协调不同时启用。显存观测用于验证释放与诊断，不充当另一套授予协议。
- **Windows 实测优先。** 前端只监听本机，worker 主动连接前端，并通过 Condor 匹配约束固定在前端所在机器。核实实际执行账户能读代码/模型、访问 GPU 并写结果；默认低权限作业账户和提交者不是同一个概念。账户、凭证和 ACL 复用现有配置按需处理。[Windows 运行账户与进程管理](https://htcondor.readthedocs.io/en/25.0/platform-specific/microsoft-windows.html)

若 Condor worker 不能满足本机服务会话或文件访问条件，R0 记录具体失败并修订接法，先解决准入所有权，再写 embedding 服务；不在失败分支中偷偷增加独立 GPU 调度器。

## 对外接口与状态责任

命令拼写在 R1 固定，先交付 CLI/Python 调用，不把 MCP 或图形界面作为可用条件。

| 动作 | 输入 | 返回与职责 |
| --- | --- | --- |
| `run` | 项目标识、executable、参数数组、工作目录、显式环境、资源请求、排队/运行时限 | 一次完成提交和等待，返回 job ID、终态、退出码、耗时和产物/日志定位 |
| `submit` | 与 `run` 相同 | 返回可继续等待、查询、取消的 job ID，适合超过宿主单次工具时限的任务 |
| `status` / `wait` | job ID、可选等待时限 | 当前状态、等待或 hold 原因、最终应用退出结果 |
| `cancel` | job ID | 撤销请求并确认进程和资源已释放；已经结束时返回实际终态 |
| `embed` | 项目标识、文本/图片输入或路径、固定模型配置、请求截止时间 | 服务内部排队、复用模型，返回向量及模型/预处理标识；不建立项目索引 |

资源字段统一采用有单位的 CPU 数、RAM、GPU 数、磁盘空间及可选 I/O 额度；agent 粗估即可。线程数依照已分配 CPU 配额设置。普通任务默认不进入这些入口，需要协调的重任务明确声明。

HTCondor 队列、事件日志和历史是作业状态的维护源；本地保留提交参数、job ID 和输出位置，不复制完整任务状态机。embedding 前端只管理未完成请求及唯一 worker 的关系，先采用内存队列；前端重启时请求明确失败，调用方决定重发，不建自动重试/恢复数据库。重启前端先核对带固定服务标识的现有 Condor worker，终止或明确接管后才能新建，防止重复加载。

区分提交失败、等待、运行、held、应用非零退出、排队超时、运行超时和取消。`condor_wait` 返回 0 只说明作业完成或中止，成功必须再核应用退出码和预期产物；其等待超时也不会自动移除作业。[condor_wait](https://htcondor.readthedocs.io/en/25.0/man-pages/condor_wait.html)

`run` 的排队或运行超时默认取消本次作业并等待释放；`wait` 的观察时限仅结束本次观察。排队截止时间和运行时限同时进入 Condor 作业策略，使客户端退出后仍生效；周期策略存在检查间隔，正常在线客户端负责及时取消，不承诺精确到秒的硬截止。[自动作业管理](https://htcondor.readthedocs.io/en/25.0/users-manual/automatic-job-management.html)

客户端连接断开不自动等于取消，job ID 能继续查询和接管；同步 CLI 在可处理的中断时执行取消。失败保留原始 Condor/应用错误和日志位置，不盲目重试。held 等待有明确错误时直接结束本次调用并清理其作业。

## 实施批次

### R0 核通真实运行与模型 worker 探针

1. 读取实际 Condor 配置来源、服务入口和本机 CLI 帮助，区分配置未加载、认证失败、执行账户失败。检查现有配置后做最小修正，不先重装或升级。
2. 查询队列、slot、GPU 与可配置 CPU/RAM/磁盘预算；为桌面和系统留出容量，依据实测设置调度预算。
3. 提交一个 CPU 小任务：输出实际账户、解释器、工作目录，读取小输入并写校验结果，验证含空格/中文路径和参数传递。
4. 提交一个真实 GPU 小任务：核分配设备，执行小矩阵计算并验证结果。再让一个占位 worker 连接本机前端，检查共享权重可读和进程取消；继而加载所选模型并处理一个文本和一张图片。
5. 取消运行中的 GPU worker，确认整个进程树退出、显存回落、下一任务可取得 GPU。确认旧入口的迁移办法。

**交付与完成：** 一页运行决定、可复现探针与实际日志定位；提交→执行→结果→释放均有证据，worker 接法可行。仅 CLI 成功、作业系统返回 0 或模型目录可列出均不够。失败先修具体接入问题，不进入大服务开发。

### R1 交付最薄的普通重任务入口

1. 建立可安装的资源工具骨架，依赖使用已有 Python 环境，机器路径经配置注入。
2. 实现 `submit/status/wait/cancel/run`，以 Condor CLI 为适配边界；参数以数组处理，集中解决 Windows 与 submit 文件的引号规则。
3. 为每个任务写必要的 stdout/stderr/事件日志，业务输出写回其项目；返回短摘要和路径，大日志不灌入主 agent。优先事件等待，必要轮询设间隔，空闲时无高频写盘。
4. 实现排队期限、运行期限、取消和非零退出；提交响应不确定时通过本次唯一提交标识查队列，不直接再提交。

**完成：** 一个新目录中一次 `run` 得到真实计算结果；失败、held、取消、两类超时均有可辨认结果；退出后能用 job ID 接续查询。先到这里形成可用的普通重任务版本。

### R2 验证 GPU 与 CPU 内存磁盘准入

1. 用 Condor 的 slot/partitionable slot 配置整卡 GPU 和 CPU/RAM/磁盘容量，不叠加自建队列。超过机器预算的请求明确显示不能匹配的原因。
2. 默认 GPU 请求整卡；显存需求只作设备能力匹配与估算，不把显存阈值解释成自动切分显存额度。CUDA 库遵守 Condor 分配。
3. CPU/RAM 按声明配额预留，线程主动限制；在 Windows 上按实际行为记录其强制限制能力，不把调度预留称为系统硬隔离。
4. 磁盘分开处理空间与吞吐：`request_disk` 管 Condor 执行 scratch 空间，项目盘输出另查容量；机械盘 I/O 密集任务需要互斥时，采用一个 Condor 自定义 I/O token，纳入同一准入。空间请求本身不限制 IOPS。[资源声明](https://htcondor.readthedocs.io/en/25.0/man-pages/condor_submit.html)、[机器资源](https://htcondor.readthedocs.io/en/25.0/admin-manual/ep-policy-configuration.html)
5. 用小规模实际计算配合较大的声明额度验证超预算排队，避免为测排队真的耗尽整机内存或磁盘。

**完成：** 两项目争同卡时串行；CPU/RAM 各自超总预算时不能同时准入，预算容得下时能并行；磁盘空间及启用后的 I/O token 行为有实测。等待期间普通轻任务仍可操作。

### R3 交付跨项目共享 embedding 服务

1. 仅接入一套确认可加载的固定多模态 embedding 模型，优先复用已有 Qwen3-VL-Embedding-2B 权重；核定 revision、精度、输入预处理和向量维度，不沿用旧项目数据库。
2. 提供本机服务前端、薄客户端和 Condor 模型 worker。前端绑定唯一固定本机端点，重复启动直接失败；并发首请求只提交一个 worker，多个项目共用已加载实例。先顺序批处理，不同时实现多模型切换和显存并发。
3. 输入支持文本和图片；输出携带稳定模型标识。服务处理瞬时输入，向量持久化和索引更新仍归项目。断开、请求过期和 worker 失败能结束受影响请求；单个请求取消只移除其排队输入或丢弃正在计算的结果，共享 worker 的停止仍由前端在批次边界处理。
4. 实现空闲卸载、有重任务等待时 drain、连续占卡上限；让卡后剩余请求保持截止时间并重新等资源，已完成批次不重复执行。单个请求不能无限扩展为一个批次。
5. 前端退出时结束所属 worker；异常重启按固定标识核对旧 worker 后再启动。用实际加载计数、PID、模型标识和显存观测验证单实例。

**完成：** 两个项目同时请求时只有一个加载实例，文本/图片均返回有效向量；重复请求复用加载；超过空闲期释放，后续请求能重新加载。等待与失败由程序处理，调用方只需一次 `embed`。

### R4 联合争用与生命周期验收

| 场景 | 必须观察的结果 |
| --- | --- |
| A 正在 embedding，B 提交 GPU 重任务 | A 当前批次结束并退出 worker；B 获卡完成；A 剩余请求继续且无重复模型 |
| B 占卡时 A/B 同时请求 embedding | 只排一个模型 worker；B 结束后请求完成，不另起 CUDA 进程绕队列 |
| embedding 持续流入，重任务也持续到达 | 两类工作在配置的批次/作业时限内均能推进，记录等待时间；不因常驻或重新提交长期饥饿 |
| 一个占卡任务试图再调 embedding | 已知冲突立即报错；把前置 embedding 与重计算拆开后能完成 |
| 普通作业排队/运行中取消或超时 | 本作业结束，进程与资源释放，下一项目继续 |
| 单个共享 embedding 请求取消或过期 | 本请求结束；其余项目请求继续，不直接取消整个共享 worker |
| worker 崩溃、前端崩溃或重启 | 请求有明确失败；旧 worker 可定位清理，重新启动不产生两个模型实例 |
| GPU 任务派生子进程 | 正常结束、超时和取消均清理整棵任务进程树，显存回落后下一任务可运行 |

**完成：** 使用两个全新合成项目和真实 CUDA/embedding 执行覆盖上表。报告 job ID、关键时间线、应用结果、加载次数、等待/加载耗时与失败，不用状态扫描或节点数替代验收。旧锁迁移前后各验证一次关键互斥关系。

### R5 安装试用与使用说明

1. 在开发目录外安装工具，换项目路径执行一次重任务及一次共享 embedding；第二个项目复用同一服务和权重。
2. 提供简短 resource skill：何时直接运行、何时提交重任务、如何粗估资源、如何一次调用得到结果，以及持卡阶段不能嵌套 embedding 的规则。长任务优先一次委托给执行 agent 内部等待，不要求主 agent 持续轮询。
3. 编写面向使用者的 README 和操作示例；机器管理员配置、服务启停、账户/ACL、GPU 预算和旧入口切换单独说明。共享工具部署与项目接入分开，不复制模型和环境。
4. 更新当前实现/模块说明、环境实测与进度；源码、skill、短文档、小样例入 Git，模型、密钥、数据库和大日志外置或忽略。

**完成：** 新路径能按说明完成两条使用链；普通项目 agent 无需手写 Condor 文件或管理模型进程；本地交付完成后再按用户指令处理远端发布。

## 顺序与工作分配

依赖为 `R0 → R1 → R2 → R3 → R4 → R5`。R0 中模型加载/账户探针提前完成，避免最后才发现服务进程不能访问 GPU；R1 可并行准备模型客户端合同，R2 通过后再实现持卡生命周期。

主 agent 负责资源所有权、接口取舍、联合验收和最终提交。需要分工时，将 Condor 接入与服务实现分给独立执行者，约定接口后并行；同一调度配置和生命周期状态由一个 owner 整合，不为此设长期固定团队。每完成一个可检查的批次，在 main 上提交相关代码、文档和变更记录。

首批实施从 R0 开始，第一项产品闭环是 R1 的一次普通重任务。R4 完成才称跨项目资源协调核心验收通过，R5 完成才称可分发版本；未来记忆工具直接接入 `embed`，无需等记忆数据库才验证本阶段。
