源码 `cache.py` 写入的是解析后的统计记录；`charts.py` 构造计数／时间／身份／来源等元数据，标题在缓存事件写入前去除。日志检查点保存后续增量解析需要的状态；运行区间也是结构化元数据。不能把减少文件体积等同于删去必要统计历史。

## 隔离原型

先用 SQLite backup 保留一致性临时副本。比较原副本、VACUUM 控制及最小去冗余版本；后者删除 record 内重复路径、六个可重算 token 构成字段和 fingerprint 列，读取时恢复，保留原事件顺序及全部四个显式索引。没有使用整库压缩或删除历史事件。

| 版本 | 字节 | 减少 |
| --- | ---: | ---: |
| 原副本 | 740,651,008 | — |
| VACUUM | 696,766,464 | 43,884,544 B，5.9% |
| 去冗余 | 419,110,912 | 321,540,096 B，43.4% |

按原读取顺序，414,872 个完整 record／fingerprint 及 37,750 个 interval 逐条比较零差异；原 sequence／路径均匹配，logs 检查点行差异为零，quick_check 均通过。

三轮旋转顺序的热读取包含 SQL 顺序扫描、JSON 解码、时间还原、fingerprint 处理和运行区间读取，中位为原副本 3.127 秒、VACUUM 3.100 秒、去冗余 2.735 秒。没有控制操作系统冷缓存。

较公平的追加实验预解码同一 4,096 条事件，计时间戳／JSON 序列化、INSERT 和 commit，并旋转三个版本的执行顺序：

| 版本 | 三轮秒数 | 中位秒数 |
| --- | --- | ---: |
| 原副本 | 5.885、3.250、1.603 | 3.250 |
| VACUUM | 3.205、3.245、1.424 | 3.205 |
| 去冗余 | 2.819、2.360、14.528 | 2.819 |

去冗余出现 14.528 秒长尾，原因未定，不能隐去或据中位数保证写性能无回退。较早顺序执行的追加结果有输入处理和执行顺序差异，不作为正式写性能依据。

## 结论与实施边界

当前样本支持“保留数据可明显缩小，热读取有改善空间”；不支持“所有场景性能无损”。未测冷读、完整统计／图表、峰值内存、文件追加／重建／删除／归档、并发及异常恢复。正式实现须走目标项目回归与一次性缓存迁移，不使用这里的实验数据库替换现用库。

先保留不同 collation 索引：简单删除可能使级联删除扫描，或令读取重新排序。路径整数化可在当前方案无法满足真实需求时再考虑。不能仅提升版本号触发旧库 invalid 备份及重扫，就把新库体积当无损升级结果；活动库与备份的总占用分开报告。
